# [레벨 디자인과 콘텐츠 제공 1/16] 레벨 디자인이란: 플레이어의 경험을 공간으로 설계하기

> **한 줄 요약** — 레벨 디자인은 게임 규칙 위에 공간을 배치해 플레이어가 무엇을 느끼고 배우고 결정할지 정하는 일이고, 그 출발점인 플레이어 메트릭은 공식으로 계산한 뒤 엔진에서 다시 재야 한다(공식으로 높이 3칸인 점프가 60fps에서는 2.875칸만 오른다).

## 이 글에서 다루는 것
- 레벨 디자인의 목표: 플레이어가 느끼고 배우고 결정하는 것
- 게임 디자인·아트·프로그래밍과의 경계, 기획 문서에서 아트 패스까지의 제작 과정
- 플레이어 메트릭으로 발판 간격과 턱 높이 정하기
- 점프를 프레임 단위로 시뮬레이션해 공식과 대조하고 ASCII 단면도로 보기

## 문제: 같은 규칙, 다른 경험
규칙(점프 높이 3칸, 달리기 초속 6칸)이 같아도 구덩이가 2칸이면 그냥 지나가는 길이고, 4.5칸이면 숨을 참는 도전이며, 6칸이면 넘을 수 없는 벽이다. 규칙을 정하는 일이 게임 디자인이라면, 그 규칙이 어떤 경험이 될지 공간으로 정하는 일이 **레벨 디자인**(level design)이다. 레벨 디자이너는 방과 발판마다 묻는다. 여기서 무엇을 느끼는가(긴장, 휴식, 놀람: 5편), 무엇을 배우는가(새 규칙을 안전하게 처음 보여 주나: 6편), 무엇을 결정하는가(갈림길, 위험한 지름길, 숨은 보상).

순진한 순서는 멋진 공간을 먼저 만들고 게임을 끼워 넣는 것이다. 그러면 캐릭터가 지나가지 못하는 문, 점프가 닿지 않는 발판, 길을 잃는 방이 생긴다. 숫자를 감으로 정하면 어떤 구덩이는 싱겁고 어떤 구덩이는 넘을 수 없다. 그래서 실무는 캐릭터의 치수를 먼저 정하고, 회색 상자로 공간을 세워 놀아 본 뒤, 마지막에 옷을 입힌다.

## 경계: 누가 무엇을 정하나
| 분야 | 정하는 것 | 점프의 예 |
|---|---|---|
| 게임 디자인 | 규칙과 수치 | 점프 높이 3칸 |
| 레벨 디자인 | 규칙이 놓일 공간 | 구덩이 폭, 발판 위치 |
| 아트 | 보이는 모습, 분위기 | 절벽 질감, 조명 |
| 프로그래밍 | 규칙이 도는 방식 | 물리 갱신, 충돌 |

경계는 겹친다. 점프 높이를 바꾸면 이미 만든 레벨의 간격이 모두 틀어지므로 메트릭은 일찍 고정한다. 조명과 색은 아트이면서 플레이어를 이끄는 도구이고(2편), 물리 갱신 방식이 메트릭을 바꾼다는 점은 아래에서 숫자로 본다.

## 제작 과정: 문서에서 아트 패스까지
```text
기획 문서: 목표, 흐름, 메트릭
        ↓
그레이박스: 회색 상자로 공간 세우기
        ↓
플레이테스트 → 고치기 → 다시 테스트
        ↓
아트 패스: 모델, 텍스처, 조명, 소리
```
기획 문서에는 레벨의 목적, 방의 순서(3편의 레벨 그래프), 쓸 메트릭을 적는다. **그레이박스**(greybox)는 화이트박스·블록아웃이라고도 하며, 텍스처 없는 상자로 공간만 세워 바로 걸어 보는 단계다. 상자는 몇 분이면 옮기지만 아트 패스가 끝난 벽은 모델·텍스처·조명을 다시 해야 하므로, 문제는 회색일 때 찾는다. 플레이테스트에서는 설명하지 않고 어디서 멈추고, 헤매고, 죽는지 지켜본다(15편의 텔레메트리는 이것을 숫자로 모은다). 유니티의 공식 학습 자료는 ProBuilder를 그레이박싱 도구로 소개한다. 에픽의 언리얼 문서는 BSP 지오메트리 브러시의 주역 자리를 스태틱 메시와 엔진 안의 모델링 도구가 이어받았지만 빠른 프로토타입에는 여전히 쓸모 있다고 설명한다. 고도의 공식 문서는 CSG 노드의 주된 용도를 레벨 프로토타이핑으로 설명한다.

## 플레이어 메트릭: 숫자에서 공간으로
**플레이어 메트릭**(player metrics)은 캐릭터의 키와 폭, 이동 속도, 점프 높이와 거리처럼 공간의 치수를 정하는 기준값이다. 통로 폭은 캐릭터 폭에 여유를 더하고, 넘어야 하는 구덩이는 최대 점프 거리보다 짧게, 넘으면 안 되는 구덩이는 확실히 길게 한다. 밸브 개발자 위키의 Dimensions 문서는 하프라이프 2와 카운터스트라이크: 소스의 플레이어 충돌 높이(서 있을 때 72유닛)와 함께 이동 상태별 최대 턱 높이와 최대 간격을 표로 정리하면서, 다른 게임에서는 값이 다를 수 있다고 밝힌다. 메트릭은 게임마다 재야 한다.

카일 피트먼의 GDC 2016 발표 「Math for Game Programmers: Building a Better Jump」는 중력을 먼저 박아 두지 말고 디자이너가 원하는 점프 높이와 거리에서 중력과 초기 속도를 역산하자고 제안한다. 최고 높이 H에 tₕ초 만에 닿게 하려면 등가속도 운동 식에서 다음이 나온다.
```text
g = 2H / tₕ²        v₀ = 2H / tₕ
평지 최대 간격 = vₓ · 2tₕ
높이 Δh 발판에 내릴 때:
  t = (v₀ + √(v₀² − 2gΔh)) / g
  최대 간격 = vₓ · t
```
H = 3칸, tₕ = 0.4초, vₓ = 6칸/s면 g = 37.5칸/s², v₀ = 15칸/s, 평지 최대 간격 4.8칸이다.

## 파이썬으로 재기: 공식 대 프레임
게임은 1/60초마다 속도와 위치를 고친다. 흔히 쓰는 **반-암시적 오일러**(semi-implicit Euler: 속도를 먼저, 새 속도로 위치를) 갱신을 그대로 돌리고, 같은 갱신을 합으로 푼 이산 닫힌 식 `yₙ = n·v₀·dt − g·dt²·n(n+1)/2`, 그리고 연속 공식과 대조한다. 캐릭터는 점으로 보고, 발판 윗면보다 위에 있는 마지막 프레임까지 간 거리를 최대 간격으로 친다.
```python
import math, random

H, TH, VX = 3.0, 0.4, 6.0          # 최고 높이 3칸에 0.4초, 달리기 6칸/s
G, V0 = 2 * H / TH**2, 2 * H / TH  # 높이와 시간에서 역산

def gap_formula(dh, vx=VX, v0=V0, g=G):   # 연속 공식
    d = v0 * v0 - 2 * g * dh
    return None if d < 0 else vx * (v0 + math.sqrt(d)) / g

def gap_sim(dh, fps, vx=VX, v0=V0, g=G):  # 프레임마다 갱신
    dt, y, v, n, last = 1 / fps, 0.0, v0, 0, None
    while v > 0 or y >= dh:
        n += 1
        v -= g * dt                       # 속도 먼저, 새 속도로 위치
        y += v * dt
        if y >= dh:
            last = n                      # 윗면보다 위인 마지막 프레임
    return None if last is None else vx * last * dt

def gap_discrete(dh, fps, vx, v0, g):     # 이산 닫힌 식의 근
    dt = 1 / fps
    a, b = g * dt * dt / 2, g * dt * dt / 2 - v0 * dt
    d = b * b - 4 * a * dh
    n = math.floor((-b + math.sqrt(d)) / (2 * a)) if d >= 0 else 0
    return vx * n * dt if n >= 1 else None

show = lambda x: "불가" if x is None else f"{x:.2f}"
print(f"g = {G:.1f}, v0 = {V0:.1f}")
print("착지 높이: 공식 / 60fps 최대 간격")
for dh in (-2, -1, 0, 1, 2, 2.5, 2.9, 3):
    print(f"{dh:+.1f}: {show(gap_formula(dh))} / {show(gap_sim(dh, 60))}")

rng, same, worst = random.Random(1), 0, {60: 0, 600: 0, 6000: 0}
for _ in range(300):
    vx, v0, g = rng.uniform(3, 10), rng.uniform(5, 20), rng.uniform(20, 60)
    dh = rng.uniform(-3, 0.9 * v0 * v0 / (2 * g))
    fps = rng.choice((30, 60, 120))
    same += gap_sim(dh, fps, vx, v0, g) == gap_discrete(dh, fps, vx, v0, g)
    for f in worst:
        err = gap_formula(dh, vx, v0, g) - gap_sim(dh, f, vx, v0, g)
        worst[f] = max(worst[f], round(err, 4))
print("무작위 300개, 프레임 시뮬 = 이산 닫힌 식:", same == 300)
print("공식과의 최대 차이:", worst)
```
```text

착지 높이: 공식 / 60fps 최대 간격
-2.0: 5.50 / 5.40
-1.0: 5.17 / 5.00
+0.0: 4.80 / 4.70
+1.0: 4.36 / 4.20
+2.0: 3.79 / 3.60
+2.5: 3.38 / 3.20
+2.9: 2.84 / 불가
+3.0: 2.40 / 불가
무작위 300개, 프레임 시뮬 = 이산 닫힌 식: True
공식과의 최대 차이: {60: 0.435, 600: 0.0384, 6000: 0.0041}
```
60fps에서는 간격이 0.1~0.2칸 짧고, 최고점이 2.875칸이라 2.9칸과 3칸 턱에는 올라설 수 없다. 이 설정에서 이산 식의 최고점은 정확히 `H − v₀·dt/2`, 곧 15/120 = 0.125칸 낮다. 무작위 300개 설정에서 프레임 시뮬레이션은 이산 닫힌 식과 정확히 같았고, 연속 공식과의 차이는 fps를 10배 올릴 때마다 약 10분의 1로 줄었다. 계산 실수가 아니라 프레임 간격에 비례하는 이산화 오차다. 위치에 ½·g·dt² 항을 더하는 적분을 쓰면 프레임 시점의 위치가 포물선 위에 놓이지만, 착지를 프레임 단위로 판정한다는 사실은 그대로다.

## 단면도로 보기
앞 코드에 이어서, 1칸 높은 발판까지 4.3칸 구덩이를 그린다. 공식의 최대 간격이 4.36칸이니 "아슬아슬한 도전"으로 놓기 좋아 보인다. 범례: `#` 땅의 단면, `o` 프레임마다의 발 위치, `S` 도약 지점. 한 글자는 가로 0.25칸, 한 줄은 세로 0.5칸이다.
```python
# 앞 코드에 이어서
def jump(gap, dh, fps=60, edge=1.5, w=8, draw=True):
    solid = lambda x, y: (x < edge and y < 0) or (
        edge + gap <= x < w and y < dh)
    dt, x, y, v, path, res = 1 / fps, edge, 0.0, V0, [], "추락"
    while y > -1:
        v -= G * dt
        x, y = x + VX * dt, y + v * dt
        if solid(x, y):                   # 이번 프레임에 땅 속으로
            ok = v < 0 and path[-1][1] >= dh
            res = "착지" if ok else "벽에 부딪힘"
            break
        path.append((x, y))
    if draw:                              # 한 글자 = 0.25칸, 한 줄 = 0.5칸
        rows = [["#" if solid(i / 4 + .1, 2.75 - j / 2) else " "
                 for i in range(w * 4)] for j in range(8)]
        for px, py in path:
            rows[5 - math.floor(py * 2)][math.floor(px * 4)] = "o"
        rows[5][int(edge * 4) - 1] = "S"
        print("\n".join("".join(r).rstrip() for r in rows))
    print(f"간격 {gap}칸, 높이 {dh:+}칸, {fps}fps: {res}")

jump(4.3, 1)
jump(4.2, 1, draw=False)
jump(4.3, 1, fps=600, draw=False)
```
```text
            ooooooo
          oo       oo
         oo         oo
        o            oo
       o               o########
     So                #########
######                 #########
######                 #########
간격 4.3칸, 높이 +1칸, 60fps: 벽에 부딪힘
간격 4.2칸, 높이 +1칸, 60fps: 착지
간격 4.3칸, 높이 +1칸, 600fps: 착지
```
60fps에서 4.3칸은 아무리 잘해도 발판 옆면에 부딪힌다. 공식만 믿고 놓으면 넘을 수 없는 "도전"이 생기고, 물리를 화면 프레임에 묶어 두면 기기 성능에 따라 넘을 수 있는 구덩이가 달라진다. 물리는 고정 간격으로 돌리고, 메트릭은 그 간격에서 잰 값을 쓴다.

## 메트릭에서 배치 규칙으로
아래 기준은 이 글의 모델에 맞춘 예시이고, 여유의 크기는 게임의 난이도 목표로 정한다.

| 용도 | 예시 기준 | 이 메트릭에서 |
|---|---|---|
| 넘어야 할 구덩이 | 60fps 최대의 80% | 평지 3.7칸 이하 |
| 넘으면 안 될 구덩이 | 공식 최대보다 길게 | 평지 5칸 이상 |
| 올라설 턱 | 60fps 최고점보다 낮게 | 2.5칸 이하 |
| 막는 벽 | 공식 최고점보다 높게 | 3.5칸 이상 |

평지 3.7~4.5칸은 "어려운 점프"로 의도할 때만 쓰고, 4.6~4.9칸처럼 프레임 간격과 콜라이더에 따라 넘기도 하고 못 넘기도 하는 간격은 쓰지 않는다. 누구는 넘고 누구는 못 넘는 구덩이는 도전이 아니라 우연이고, 넘으면 안 될 구덩이를 넘을 수 있으면 4편의 게이팅이 깨진다.

## 모델이 말해 주지 않는 것
- 캐릭터는 점이 아니다. 콜라이더 폭만큼 발판 끝에 걸쳐 뛸 수 있고, 발판을 벗어난 직후 잠깐 점프를 허용하는 코요테 타임(coyote time)이나 가변 점프, 공중 제어가 숫자를 또 바꾼다. 엔진 안에 간격과 높이를 한 칸씩 바꿔 늘어놓은 측정용 레벨을 두고 직접 뛰어 본다.
- 최대 간격은 완벽한 입력의 값이다. 난이도는 여유(최대 − 실제 간격)와 실패의 대가가 정하고, 플레이어마다 다른 실력은 8편에서 다룬다.
- 모델은 "넘을 수 있는가"에 답할 뿐 "넘고 싶은가"에는 답하지 못한다. 그 답은 플레이테스트에서 나온다.

## 어디에 쓰이나
- 미적분 2편 「미분: 순간 변화율」: 위치의 변화율이 속도, 속도의 변화율이 가속도라는 관계를 1/60초 간격으로 근사한 것이 프레임 갱신이고, 그 근사 오차가 이 글의 0.125칸이다.
- 게임 자원 관리 1편 「프레임 예산: 16.67ms 안에 모든 일을 끝내기」: 물리를 고정 간격으로 돌리면 프레임이 흔들려도 점프가 같아지고, 메트릭은 그 간격에서 잰 값이어야 한다.
- 2편 「동선과 시선 유도: 랜드마크, 시야, 공간의 문법」: 메트릭이 공간의 치수를 정하면, 2편은 그 공간에서 갈 곳을 스스로 알게 하는 장치를 다룬다.

## 정리
- 레벨 디자인은 규칙을 공간에 배치해 플레이어가 느끼고 배우고 결정할 것을 정하는 일이다.
- 기획 문서 → 그레이박스 → 플레이테스트 반복 → 아트 패스 순서로, 고치기 싼 단계에서 문제를 찾는다.
- 점프는 원하는 높이와 시간에서 g와 v₀를 역산하고, 최대 간격과 턱 높이를 메트릭으로 삼는다.
- 60fps 시뮬레이션은 이산 닫힌 식과 정확히 같았고, 공식보다 간격이 0.1~0.2칸, 최고점이 0.125칸 낮았다. 메트릭은 엔진에서 재고 애매한 값은 피한다.

## 시리즈 안내
1부(1~8편)는 레벨 디자인, 2부(9~16편)는 콘텐츠를 만들어 공급하는 일이다.

1. **레벨 디자인이란: 플레이어의 경험을 공간으로 설계하기** ← 지금 읽는 글
2. 동선과 시선 유도: 랜드마크, 시야, 공간의 문법
3. 레벨을 그래프로 보기: 임계 경로, 루프, 되돌아가기
4. 열쇠와 자물쇠: 게이팅과 막힘 없는 진행 구조
5. 페이싱과 난이도 곡선: 긴장과 이완의 리듬
6. 튜토리얼과 온보딩: 레벨이 가르치게 하기
7. 전투 공간 설계: 엄폐, 고저차, 스폰 배치
8. 플레이어 모델과 난이도 조절: 동적 난이도와 실력 평가
9. 절차적 생성 1: 던전과 동굴 만들기
10. 절차적 생성 2: 웨이브 함수 붕괴와 생성 문법
11. 진행 시스템: 경험치 곡선, 해금, 보상 일정
12. 확률형 보상: 기댓값, 천장, 확률 공개
13. 게임 경제: 재화의 원천과 소모처, 인플레이션
14. 라이브 서비스: 시즌, 배틀 패스, 콘텐츠 소비 속도

16. 콘텐츠 파이프라인: 데이터 주도 설계, 검증 도구, 패치 배포
