# [레벨 디자인과 콘텐츠 제공 13/16] 게임 경제: 재화의 원천과 소모처, 인플레이션

> **한 줄 요약** — 게임 재화는 사냥 보상 같은 원천(수도꼭지)으로만 생기고 수리비·수수료 같은 소모처(배수구)로만 사라지므로, 원천만 있는 경제는 통화량이 시간에 비례해 늘며 시세가 오르고, 지갑이나 거래액에 비례하는 소모처를 두어야 통화량이 정상 상태에 머문다.

- 플레이어 200명 경제 시뮬레이션: 소모처의 모양에 따른 통화량과 시세
- 정상 상태 공식과의 대조, 일부러 넣은 복사 버그를 원장 검사로 잡기
- 이브 온라인·밸브·디아블로 3의 사례와 모델의 한계

## 문제: 석 달 뒤 들어온 플레이어의 물가
거래소가 있는 게임에 출시 석 달 뒤 들어온 플레이어가 강화석 하나를 사려고 보니 사냥 12시간치 값이 붙어 있다. 첫 달에는 5시간치였다. 아무도 값을 올리라고 정하지 않았는데 이런 일이 생기는 이유는 재화가 어디서 생기고 어디로 사라지는지를 보면 알 수 있다. 11편이 보상을 언제 얼마나 주는가, 12편이 확률로 주는 보상의 수학이었다면, 이 글은 그렇게 준 재화가 쌓여서 생기는 일을 다룬다.

## 수도꼭지와 배수구
재화가 새로 생기는 곳을 **원천**(source, 흔히 수도꼭지 faucet)이라 한다. 몬스터 처치 보상, 퀘스트 보상, NPC 상점에 아이템을 판 대금이 원천이다. 재화가 게임에서 사라지는 곳은 **소모처**(sink, 배수구)다. 장비 수리비, 거래소 수수료, 순간 이동 비용, NPC에게서 사는 소모품과 꾸미기 아이템, 강화 비용이 그렇다. 플레이어끼리의 거래는 둘 다 아니다. 한 사람의 지갑에서 다른 사람의 지갑으로 옮길 뿐 총량은 그대로다. 그래서 전체 통화량 M은 물탱크처럼 움직인다.
```text
M(내일) = M(오늘) + 원천 − 소모
```
순진한 설계는 원천만 신경 쓴다. 사냥 보상은 플레이 시간에 비례해 끝없이 나오는데 소모처가 처음 한 번 사는 장비처럼 고정돼 있으면 통화량은 시간에 비례해 는다. 그 돈이 플레이어 간 시장에 들어가면 같은 물건에 더 많은 돈이 몰려 시세가 오른다. 이것이 게임 속 **인플레이션**이다. 오래 한 플레이어는 쌓아 둔 돈이 있어 괜찮지만, 신규·복귀 플레이어는 같은 사냥 시간으로 살 수 있는 것이 계속 줄어든다.

아이템에도 같은 장부가 있다. 강화석이 드롭(원천)되기만 하고 쓰여 없어지지(소모) 않으면 재고가 쌓여 아이템 값은 반대로 떨어진다. 아래 모델에서는 강화석을 쓰면 사라진다고 둔다.

## 플레이어 200명의 경제
하루 1·2·4시간 노는 플레이어 200명이 시간당 100골드를 벌고, 시간당 10% 확률로 강화석을 줍는다. 강화석은 모두 시장에 나오고, 모든 플레이어가 하루 하나를 원하며 지갑의 5%까지 낸다. 단일 가격 경매라서 지갑이 두둑한 순서대로 사고, 마지막으로 산 사람의 입찰가가 시세다. 소모처 조합 세 가지를 비교하고, 날마다 "지갑 합계의 변화 = 원천 − 소모"를 검사한다.
```python
import random

def run(repair, tax, lux, days=90, n=200, seed=13, bug=0.0):
    """repair: 시간당 수리비, tax: 거래 수수료 %, lux: 매일 지갑의 lux%를 쓰는 소모처"""
    rng = random.Random(seed)
    hours = [rng.choice([1, 2, 4]) for _ in range(n)]   # 하루 플레이 시간
    gold, log, bad = [0] * n, [], []
    for day in range(1, days + 1):
        before, src, snk, stones = sum(gold), 0, 0, []
        for i in range(n):
            gold[i] += 100 * hours[i]                    # 원천: 사냥 보상
            src += 100 * hours[i]
            cut = repair * hours[i]                      # 소모처: 수리비
            cut += (gold[i] - cut) * lux // 100          # 소모처: 지갑 비례
            gold[i] -= cut
            snk += cut
            stones += [i] * sum(rng.random() < 0.1 for _ in range(hours[i]))
        # 시장: 모두 강화석 1개를 원하고 지갑의 5%까지 낸다(단일 가격 경매)
        buyers = sorted(range(n), key=lambda i: -gold[i])[:len(stones)]
        price = gold[buyers[-1]] // 20 if stones else 0
        for b, s in zip(buyers, stones):                 # 강화석은 쓰면 사라진다
            fee = price * tax // 100
            if not (bug and rng.random() < bug):         # 버그: 대금이 안 빠짐
                gold[b] -= price
            gold[s] += price - fee
            snk += fee
        if sum(gold) - before != src - snk:              # 원장 검사
            bad.append(day)
        log.append((sum(gold), price))
    return log, bad, sum(hours)

for name, args in (("소모처 없음", (0, 0, 0)), ("수리비만", (30, 0, 0)),
                   ("수리비+수수료 5%+지갑 3%", (30, 5, 3))):
    log, bad, H = run(*args)
    print(f"{name} / 원장 불일치 {len(bad)}일")
    for d in (30, 60, 90):
        m, p = log[d - 1]
        print(f"  {d}일 통화량 {m:>9,} 시세 {p:>5,} = 사냥 {p / 100:.1f}시간")
```
```text
소모처 없음 / 원장 불일치 0일
  30일 통화량 1,470,000 시세   481 = 사냥 4.8시간
  60일 통화량 2,940,000 시세   887 = 사냥 8.9시간
  90일 통화량 4,410,000 시세 1,269 = 사냥 12.7시간
수리비만 / 원장 불일치 0일
  30일 통화량 1,029,000 시세   337 = 사냥 3.4시간
  60일 통화량 2,058,000 시세   621 = 사냥 6.2시간
  90일 통화량 3,087,000 시세   891 = 사냥 8.9시간
수리비+수수료 5%+지갑 3% / 원장 불일치 0일
  30일 통화량   658,747 시세   224 = 사냥 2.2시간
  60일 통화량   918,215 시세   294 = 사냥 2.9시간
  90일 통화량 1,020,608 시세   315 = 사냥 3.1시간
```
소모처가 없으면 통화량은 하루 정확히 49,000씩 늘고 시세도 따라 올라, 강화석 하나가 사냥 4.8시간에서 12.7시간이 된다. 수리비처럼 플레이 시간에 비례하는 소모처는 원천의 30%를 덜어 낼 뿐이라 기울기만 줄인다. 거래 수수료와 지갑에 비례하는 소모처(돈이 많을수록 더 쓰게 되는 꾸미기·강화 같은 것)를 더하면 통화량이 100만 근처로 수렴하고 시세도 사냥 3시간 남짓에 머문다. 차이를 만드는 것은 소모처의 크기보다 **모양**이다. 고정 소모처는 원천처럼 일정하게 빠지고, 비례 소모처는 쌓인 양이 클수록 많이 빠지므로 물탱크에 수위가 생긴다.

## 대조: 정상 상태 공식과 원장 검사
비례 소모처가 있는 경제는 식으로 풀린다. 수수료를 빼면 시장은 돈을 옮기기만 하므로 하루 순 원천 F와 지갑 비율 s만 남는다.
```text
M(t+1) = (M(t) + F)(1 − s)
정상 상태 M* = F(1 − s)/s
M(t) = M*(1 − (1 − s)ᵗ),  M(0) = 0
```
앞 코드에 이어서, 소모처가 없을 때의 직선 공식과 정상 상태 공식을 시뮬레이션과 맞춰 보고, 거래 1%에서 구매자 대금이 빠지지 않는 버그를 일부러 넣어 원장 검사가 잡는지 본다.
```python
log, bad, H = run(0, 0, 0)
print("소모처 없음, 통화량 = 100·H·t:",
      all(m == 100 * H * t for t, (m, _) in enumerate(log, 1)))
log, bad, H = run(30, 0, 3, days=180)
s, F = 0.03, 70 * H                       # 하루 순 원천 = (100 − 30)·H
star = F * (1 - s) / s                    # 정상 상태 M* = F(1 − s)/s
for t in (30, 90, 180):
    f = star * (1 - (1 - s) ** t)         # M(t) = M*(1 − (1 − s)^t)
    m = log[t - 1][0]
    print(f"{t}일 공식 {f:,.0f} 시뮬 {m:,} 차이 {(m - f) / f:+.2%}")
log, bad, H = run(30, 5, 3, bug=0.01)
print(f"대금 누락 버그 1%: 원장 불일치 {len(bad)}일, 첫날 {bad[0]}일째")
```
```text
소모처 없음, 통화량 = 100·H·t: True
30일 공식 664,303 시뮬 666,204 차이 +0.29%
90일 공식 1,037,518 시뮬 1,040,621 차이 +0.30%
180일 공식 1,104,422 시뮬 1,107,716 차이 +0.30%
대금 누락 버그 1%: 원장 불일치 34일, 첫날 8일째
```
소모처가 없으면 통화량은 90일 내내 공식과 정확히 같다. 비례 소모처 쪽은 0.3% 차이가 나는데, 지갑의 3%를 정수로 내림해서 걷느라 시뮬레이션이 조금씩 덜 걷기 때문이다. 수렴 속도는 (1 − s)ᵗ가 정하므로 s = 3%면 90일 뒤에도 정상 상태까지 6%가 남는다. 식에서 보듯 `M*`는 원천 F에 비례하므로, 사냥 보상을 올리는 패치는 소모처를 같이 보지 않으면 물가를 올리는 패치다. 버그를 넣으면 8일째부터 원장이 맞지 않는다. 아이템·골드 복사 버그나 봇이 찍어 내는 재화는 설계하지 않은 원천이고, 서버가 원천과 소모를 종류별로 날마다 집계해 통화량 변화와 맞춰 보면 이런 구멍을 일찍 찾는다.

## 실제 게임의 사례
- 이브 온라인: CCP는 2007년 6월 경제학자 Eyjólfur Guðmundsson 박사를 게임 내 수석 경제학자로 영입한다고 발표했고(공식 보도 자료), 분기 경제 보고서를 냈다. 첫 보고서를 다룬 보도에 따르면 그는 게임 속 경제가 현실보다 빨리 변하므로 고정된 장바구니 대신 연쇄 가격 지수(chained price index)로 물가를 쟀다.
- 밸브: 2012년 경제학자 야니스 바루파키스를 상주 경제학자(economist-in-residence)로 영입해 블로그에 분석을 연재하게 했다(당시 보도). 게임들이 화폐를 공유하는 밸브의 문제를 독일과 그리스 사이의 문제에 빗댄 게이브 뉴얼의 연락이 계기였다고 보도되었다.
- 디아블로 3: 블리자드는 2013년 9월 골드 경매장과 현금 경매장 폐쇄를 발표하고 2014년 3월 18일 닫았다. 경매장이 "몬스터를 잡아 멋진 전리품을 얻는" 핵심 재미를 해친다는 것이 공식 설명이었다(공식 블로그 발표를 다룬 보도). 거래가 너무 쉬우면 드롭이라는 원천 자체의 의미가 옅어진다는 사례로 읽을 수 있다.

## 흔한 오해와 한계
- "거래를 막으면 인플레이션도 없다": NPC 가격이 고정이면 물가는 그대로지만, 쌓인 돈으로 무엇이든 살 수 있게 되면 골드 보상이 더는 동기가 되지 못한다. 통화량 문제는 거래가 아니라 원천과 소모의 균형에서 온다.
- 소모처가 벌칙처럼 느껴지면 플레이어가 떠난다. 과한 사망 페널티나 수리비보다 플레이어가 원해서 쓰는 소모처(꾸미기, 편의, 꾸민 집)가 오래 간다는 것이 흔히 말하는 원칙이다.
- "지갑의 3%를 매일 걷는" 소모처는 실제로 없다. 거래액에 붙는 수수료나 수준에 따라 비싸지는 강화 비용처럼 부유할수록 더 쓰게 되는 장치가 이를 근사한다.
- 모델에서는 입찰가가 지갑의 5%로 고정이지만, 실제 플레이어는 시세를 예상하고 사재기하고 투기한다. 모델은 원천·소모의 모양이 통화량에 주는 영향을 보여 줄 뿐이고, 실제 시세와 체감은 라이브 데이터와 플레이어 의견으로 확인해야 한다.
- 현금으로 재화를 살 수 있다면 그것도 원천이다. 현금과 연결된 경제는 물가가 곧 지출 압력이 되므로, 플레이어 보호 관점에서 더 보수적으로 설계해야 한다.

- 11편 「진행 시스템: 경험치 곡선, 해금, 보상 일정」: 레벨이 오를수록 커지는 사냥 보상은 원천의 기울기를 키우므로 보상 곡선과 소모처 곡선을 함께 설계해야 한다.
- 15편 「데이터로 판단하기: 텔레메트리, 퍼널, 히트맵, A/B 테스트」: 원천·소모 이벤트를 종류별로 기록해야 라이브에서 통화량이 왜 늘었는지 답할 수 있다.

## 정리
- 재화는 원천으로만 생기고 소모처로만 사라지며, 플레이어 간 거래는 총량을 바꾸지 않는다.
- 원천만 있으면 통화량이 시간에 비례해 늘어 시세가 오르고, 가장 손해를 보는 쪽은 신규·복귀 플레이어다.
- 고정 소모처는 기울기만 줄이고, 지갑·거래액에 비례하는 소모처가 정상 상태 `M* = F(1 − s)/s`를 만든다.
- 날마다 원천 − 소모 = 통화량 변화를 맞춰 보는 원장 검사가 복사 버그 같은 설계 밖 원천을 잡는다.
