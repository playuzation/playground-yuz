# [PostgreSQL 실무 13/16] 스키마 마이그레이션: 운영 중인 테이블을 안전하게 바꾸기

> **한 줄 요약** — 운영 중 스키마 변경의 위험은 대부분 잠금이므로, 트랜잭션 DDL로 실패를 되돌리고, 오래 잠그는 변경은 `NOT VALID` → `VALIDATE`, `CONCURRENTLY`, 확장-축소처럼 약한 잠금 단계로 쪼개며, DDL마다 `lock_timeout`을 건다.

- 잠금 대기열 사고를 재현하고 `lock_timeout`으로 막기
- NOT NULL·외래 키·인덱스·열 이름 바꾸기의 안전한 순서와 나눠서 하는 백필

## 문제: ALTER TABLE 한 줄이 서비스를 멈춘다
배포 중 `ALTER TABLE` 한 줄에 API 전체가 멈추는 일은 흔하다. 원인은 둘이다. 테이블을 통째로 다시 쓰는 변경은 크기에 비례하는 시간 동안 가장 강한 ACCESS EXCLUSIVE 잠금을 쥔다. 그리고 변경 자체는 순식간이어도 앞에 오래 도는 쿼리가 있으면 그 잠금을 **기다리는 동안** 뒤에 오는 SELECT까지 줄을 선다. 잠금 충돌표는 11편 「락과 동시성: 행 잠금, SKIP LOCKED 작업 큐, 교착 상태」에서 봤다.

## 마이그레이션 도구와 트랜잭션 DDL
마이그레이션 도구(Flyway, Alembic 등)는 변경을 번호 붙은 파일로 두고, DB 안의 버전 테이블(Flyway는 `flyway_schema_history`, Alembic은 `alembic_version`)에 적용 기록을 남겨 아직 적용되지 않은 파일만 순서대로 실행한다. 그래서 모든 환경의 DB가 같은 순서로 같은 변경을 겪는다.

PostgreSQL에서는 DDL 대부분이 트랜잭션 안에서 돈다. 파일 하나를 트랜잭션 하나로 실행하면 실패해도 반쯤 바뀐 스키마가 남지 않는다. 실습 테이블을 만들고 오타 난 마이그레이션을 실행해 본다.
```sql
CREATE TABLE schema_migrations (version int PRIMARY KEY);
CREATE TABLE customers (id int PRIMARY KEY, email text);
INSERT INTO customers SELECT g, 'c' || g || '@example.com' FROM generate_series(1, 500) g;
UPDATE customers SET email = 'c499@example.com' WHERE id = 500;
CREATE TABLE orders (id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  customer_id int, amount numeric(10,2), status varchar(20));
INSERT INTO orders (customer_id, amount, status)
SELECT g % 500 + 1, g % 97 + 0.5, 'paid' FROM generate_series(1, 30000) g;
```
```sql
BEGIN;
CREATE TABLE coupons (code text PRIMARY KEY);
ALTER TABLE orders ADD COLUMN coupon text REFERENCES coupon (code);
INSERT INTO schema_migrations VALUES (2);
COMMIT;
\dt coupons
```
```text
BEGIN
CREATE TABLE
ERROR:  relation "coupon" does not exist
ERROR:  current transaction is aborted, commands ignored until end of transaction block
ROLLBACK
Did not find any tables named "coupons".
```
먼저 만든 `coupons`까지 사라졌고 버전 기록도 없다. 실패한 트랜잭션의 `COMMIT`은 `ROLLBACK`이 된다. 예외는 `CREATE INDEX CONCURRENTLY`, `VACUUM`, `CREATE DATABASE`처럼 트랜잭션 블록 안에서 돌 수 없는 명령이다.

## 어떤 변경이 테이블을 다시 쓰나
테이블을 다시 쓰면 새 파일이 생겨 `pg_relation_filenode()`가 바뀐다. 네 가지 변경 전후를 비교한다.
```sql
SELECT pg_relation_filenode('orders') AS f0 \gset
ALTER TABLE orders ADD COLUMN currency text NOT NULL DEFAULT 'KRW';
SELECT pg_relation_filenode('orders') AS f1 \gset
ALTER TABLE orders ADD COLUMN token uuid DEFAULT gen_random_uuid();
SELECT pg_relation_filenode('orders') AS f2 \gset
ALTER TABLE orders ALTER COLUMN customer_id TYPE bigint;
SELECT pg_relation_filenode('orders') AS f3 \gset
ALTER TABLE orders ALTER COLUMN status TYPE varchar(50);
SELECT :f0 = :f1 AS const_default, :f1 = :f2 AS volatile_default,
       :f2 = :f3 AS int_to_bigint, pg_relation_filenode('orders') = :f3 AS widen_varchar;
```
```text
ALTER TABLE
ALTER TABLE
ALTER TABLE
ALTER TABLE
 const_default | volatile_default | int_to_bigint | widen_varchar
---------------+------------------+---------------+---------------
 t             | f                | f             | t
(1 row)
```
상수 기본값 열 추가는 파일을 건드리지 않는다. PostgreSQL 11부터 기본값을 카탈로그(`pg_attribute.attmissingval`)에 한 번 적어 두고 옛 행을 읽을 때 채우기 때문이다. 행마다 값이 다른 휘발성 기본값과 int→bigint 같은 타입 변경은 전체 행을 다시 쓰며 그동안 ACCESS EXCLUSIVE 잠금을 쥔다. varchar 길이 늘리기는 저장 형식이 같아 다시 쓰지 않는다. 처음 보는 변경은 복사본 DB에서 이렇게 확인하고 시간을 재 본다.

## 잠금 대기열을 재현하고 lock_timeout으로 막기
A가 트랜잭션을 연 채 `orders`를 읽고(ACCESS SHARE), B가 열을 추가하려 하고, C가 SELECT를 보낸다. 접속 정보는 libpq 환경 변수(`PGHOST` 등)로 준다.
```python
import threading, time, psycopg
a = psycopg.connect()                      # 트랜잭션을 연 채 쉰다
a.execute("SELECT count(*) FROM orders")

def run(name, setting, sql):
    with psycopg.connect(autocommit=True) as c:
        c.execute(setting)
        try: c.execute(sql)
        except psycopg.errors.OperationalError as e:
            print(f"{name}: {e.diag.message_primary}")

mon = psycopg.connect(autocommit=True)
def wait_for(n):                           # 잠금 대기 연결이 n개가 될 때까지
    while mon.execute("SELECT count(*) FROM pg_stat_activity"
                      " WHERE wait_event_type = 'Lock'").fetchone()[0] < n:
        time.sleep(0.05)

b = threading.Thread(target=run, args=("B 마이그레이션", "SET lock_timeout = '2s'",
                     "ALTER TABLE orders ADD COLUMN note text"))
c = threading.Thread(target=run, args=("C 평범한 SELECT", "SET statement_timeout = '1s'",
                     "SELECT count(*) FROM orders WHERE id = 1"))
b.start(); wait_for(1); c.start(); wait_for(2)
for w, by in mon.execute("""SELECT w.query, b.query FROM pg_stat_activity w
        JOIN pg_stat_activity b ON b.pid = ANY (pg_blocking_pids(w.pid))
        ORDER BY w.backend_start"""):
    print(f"{w}\n  ← {by}")
b.join(); c.join(); a.rollback()
```
```text
ALTER TABLE orders ADD COLUMN note text
  ← SELECT count(*) FROM orders
SELECT count(*) FROM orders WHERE id = 1
  ← ALTER TABLE orders ADD COLUMN note text
C 평범한 SELECT: canceling statement due to statement timeout
B 마이그레이션: canceling statement due to lock timeout
```
C는 A와 충돌하지 않지만 먼저 줄 선 B 뒤에서 기다린다. `lock_timeout`이 없으면 A가 끝날 때까지 모든 읽기·쓰기가 멈추지만, 걸면 B가 2초 만에 포기해 줄이 풀린다. 마이그레이션은 실패해도 서비스는 살고, 재시도하면 된다.

## 안전한 순서: NOT NULL, 외래 키, 인덱스
`SET NOT NULL`과 외래 키 추가는 기존 행을 모두 검사하는 동안 강한 잠금을 쥔다. `NOT VALID`로 걸면 새 행만 바로 검사하고 기존 행 검사는 미루며, 나중의 `VALIDATE CONSTRAINT`는 읽기·쓰기를 막지 않는 SHARE UPDATE EXCLUSIVE 잠금만 잡는다. NOT NULL을 `NOT VALID`로 추가하는 문법은 PostgreSQL 18에 들어왔다. 고아 주문을 하나 넣고 진행한다.
```sql
SET lock_timeout = '3s';
INSERT INTO orders (customer_id, amount, status) VALUES (9999, 1, 'paid');
ALTER TABLE orders ADD CONSTRAINT orders_customer_id_nn NOT NULL customer_id NOT VALID;
ALTER TABLE orders ADD CONSTRAINT orders_customer_fk
  FOREIGN KEY (customer_id) REFERENCES customers (id) NOT VALID;
```
```sql
BEGIN;
ALTER TABLE orders VALIDATE CONSTRAINT orders_customer_id_nn;
SELECT mode FROM pg_locks WHERE relation = 'orders'::regclass AND pid = pg_backend_pid();
COMMIT;
ALTER TABLE orders VALIDATE CONSTRAINT orders_customer_fk;
```
```text
BEGIN
ALTER TABLE
           mode
--------------------------
 ShareUpdateExclusiveLock
(1 row)

COMMIT
ERROR:  insert or update on table "orders" violates foreign key constraint "orders_customer_fk"
DETAIL:  Key (customer_id)=(9999) is not present in table "customers".
```
검증이 실패해도 제약은 `NOT VALID`로 남아 새 고아 행을 막으니, 데이터를 고치고 다시 검증하면 된다. 17 이하에서는 `CHECK (customer_id IS NOT NULL) NOT VALID` → `VALIDATE` → `SET NOT NULL` 순서로 한다. 유효한 CHECK가 NULL이 없음을 보장하면 `SET NOT NULL`이 스캔을 건너뛴다.

`CREATE INDEX`는 SHARE 잠금으로 쓰기를 막으므로 `CONCURRENTLY`로 만든다. 테이블을 두 번 훑어 느리지만 쓰기를 막지 않는다. 대신 실패하면 흔적이 남는다.
```sql
DELETE FROM orders WHERE customer_id = 9999;
CREATE UNIQUE INDEX CONCURRENTLY customers_email_key ON customers (email);
SELECT indexrelid::regclass, indisvalid FROM pg_index WHERE indrelid = 'customers'::regclass;
```
```text
DELETE 1
ERROR:  could not create unique index "customers_email_key"
DETAIL:  Key (email)=(c499@example.com) is duplicated.
     indexrelid      | indisvalid
---------------------+------------
 customers_pkey      | t
 customers_email_key | f
(2 rows)
```
실패한 인덱스는 `INVALID`로 남아 조회에는 안 쓰이면서 쓰기 비용만 든다. `DROP INDEX CONCURRENTLY`로 지우고 중복을 고친 뒤 다시 만든다.

열 이름 바꾸기는 순식간이지만 배포 중에는 옛 이름을 쓰는 앱 버전이 아직 돌아 바로 오류가 난다. 그래서 **확장-축소**(expand/contract)로 나눈다. ① 새 열 추가 ② 앱이 두 열에 쓰기 ③ 옛 행 백필 ④ 읽기를 새 열로 ⑤ 옛 열 쓰기 중단 ⑥ 옛 열 삭제. 단계마다 따로 배포하니 언제든 되돌릴 수 있다.

## 대량 백필은 나눠서
백필을 `UPDATE` 한 번으로 하면 행 잠금과 죽은 튜플이 한 트랜잭션에 몰리고 복제본 지연도 커진다(15편). `id` 범위로 나눠 배치마다 커밋한다. 트랜잭션 블록 밖의 `DO` 블록은 안에서 `COMMIT`할 수 있다.
```sql
ALTER TABLE orders ADD COLUMN amount_cents bigint;
DO $$
DECLARE lo bigint := 0; hi bigint; n int;
BEGIN
  SELECT max(id) INTO hi FROM orders;
  WHILE lo < hi LOOP
    UPDATE orders SET amount_cents = round(amount * 100)
     WHERE id > lo AND id <= lo + 10000 AND amount_cents IS NULL;
    GET DIAGNOSTICS n = ROW_COUNT;
    RAISE NOTICE 'id % 초과: % 행', lo, n;
    lo := lo + 10000;
    COMMIT;
  END LOOP;
END $$;
```
```text
ALTER TABLE
NOTICE:  id 0 초과: 10000 행
NOTICE:  id 10000 초과: 10000 행
NOTICE:  id 20000 초과: 10000 행
DO
```
배치 사이에 VACUUM이 죽은 튜플을 치울 수 있고(10편 「MVCC와 VACUUM: 행 버전, 팽창, 트랜잭션 ID 고갈」), `amount_cents IS NULL` 조건 덕분에 끊겨도 다시 돌리면 이어서 한다.

## 숫자로 보기
| 변경 | 잠금 / 다시 쓰기 |
|---|---|
| 상수 기본값 열 추가 | ACCESS EXCLUSIVE(짧게) / 없음 |
| 휘발성 기본값 열 추가 | ACCESS EXCLUSIVE / 있음 |
| int → bigint | ACCESS EXCLUSIVE / 있음 |
| `VALIDATE CONSTRAINT` | SHARE UPDATE EXCLUSIVE / 없음(스캔만) |

## 흔한 실수와 권장 설정
- `CREATE INDEX CONCURRENTLY cannot run inside a transaction block`: 도구가 파일을 트랜잭션으로 감싸서 난다. 그 파일만 트랜잭션 밖에서 실행하는 도구 설정을 쓴다.
- `canceling statement due to lock timeout`: 보호 동작이다. 막는 세션을 `pg_blocking_pids()`로 찾고 재시도한다.
- 마이그레이션 세션에는 `lock_timeout`(서비스가 견딜 정지 시간, 보통 몇 초)을 건다. 스키마 변경과 대량 데이터 변경은 다른 파일로 나누고, 다시 쓰기를 피할 수 없는 타입 변경은 새 열로 확장-축소한다.

## 정리
- DDL이 트랜잭션 안에서 돌아 실패한 마이그레이션은 통째로 되돌아간다.
- 상수 기본값 열 추가는 즉시 끝나고, 휘발성 기본값과 타입 변경은 테이블을 다시 쓴다.
- 짧은 DDL도 잠금 대기열을 만들므로 `lock_timeout`을 걸고 재시도한다.
- 제약은 `NOT VALID` → `VALIDATE`, 인덱스는 `CONCURRENTLY`, 이름 바꾸기는 확장-축소, 백필은 배치로 나눈다.
