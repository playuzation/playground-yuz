# [카프카 이벤트 스트리밍 1/12] 카프카란: 지워지지 않는 로그로 만든 메시지 시스템

> **한 줄 요약** — 카프카는 이벤트를 토픽이라는 추가 전용 로그에 차례로 덧붙이고, 읽어도 지우지 않은 채 정해진 기간 보관하는 분산 시스템으로, 소비자마다 "어디까지 읽었나"(오프셋)를 따로 기억하기 때문에 같은 이벤트를 여러 시스템이 각자의 속도로 읽고, 필요하면 처음부터 다시 읽을 수 있다.

## 이 글에서 다루는 것
- 시스템 사이에 이벤트를 나르는 문제
- 큐와 로그의 차이: 꺼내면 사라지는가
- 카프카의 낱말: 브로커, 토픽, 파티션, 오프셋, 프로듀서, 컨슈머, 컨슈머 그룹
- 직접 해 보기: 브로커를 띄우고, 이벤트를 쓰고, 두 그룹이 각자 다 읽기
- 짧은 역사와 다른 도구와의 비교

## 이벤트를 나르는 문제
쇼핑몰에서 주문 하나가 생기면 결제, 재고, 배송, 메일 발송, 추천, 매출 분석이 모두 그 사실을 알아야 한다. 주문 서비스가 이들을 하나하나 직접 부르면, 받는 쪽 하나가 느리거나 죽을 때 주문 자체가 막히고, 새 시스템이 생길 때마다 주문 서비스를 고쳐야 한다. 시스템이 N개, 받는 쪽이 M개면 연결이 N×M개로 늘어난다. 그래서 가운데에 이벤트를 받아 두는 곳을 둔다. 주문 서비스는 "주문이 생겼다"는 **이벤트**를 한곳에 쓰기만 하고, 관심 있는 시스템이 각자 가져간다.

## 큐와 로그
가운데 둘 곳은 크게 두 모양이 있다. Redis 실무 3편의 리스트나 전통적인 메시지 큐는 **큐**다. 소비자가 메시지를 꺼내면 사라진다. 한 메시지를 여러 시스템이 받게 하려면 시스템마다 큐를 따로 만들어 복사해 넣어야 하고, 지난 메시지를 다시 볼 수 없다.

**카프카**(Apache Kafka)는 **로그**다. 이벤트는 파일 끝에 차례로 덧붙여지고, 읽어도 지워지지 않는다. 대신 정해진 보존 기간(기본 7일)이나 크기가 지나면 오래된 것부터 지운다. 각 이벤트에는 로그 안의 위치 번호인 **오프셋**(offset)이 붙고, 소비자는 "어디까지 읽었나"만 기억한다. 그래서 결제 시스템과 분석 시스템이 같은 로그를 각자의 속도로 읽고, 분석 코드에 버그가 있었다면 오프셋을 되돌려 처음부터 다시 처리할 수 있다.
```text
topic "orders" (one partition)
offset: 0    1    2    3    4
       [o1] [o2] [o3] [o4] [o5] ← new
             ↑              ↑
     analytics @1    payment @4
```

## 카프카의 낱말
- **브로커**(broker): 로그를 저장하고 읽기·쓰기 요청을 받는 서버. 보통 여러 대가 클러스터를 이룬다.
- **토픽**(topic): 이벤트의 종류별 로그 이름. `orders`, `payments`.
- **파티션**(partition): 토픽을 나눈 조각. 각 파티션이 독립된 로그이고 여러 브로커에 흩어진다. 처리량을 늘리는 단위이자, 순서가 지켜지는 단위다(3편).
- **프로듀서**(producer): 이벤트를 쓰는 쪽(5편).
- **컨슈머**(consumer): 이벤트를 읽는 쪽. 같은 **컨슈머 그룹**(consumer group)의 컨슈머들은 파티션을 나눠 읽고(6편), 서로 다른 그룹은 각자 전부를 읽는다.

## 직접 해 보기: 첫 브로커
카프카는 자바 프로그램이다(자바 17 이상). 공식 사이트에서 내려받은 바이너리를 `/opt/kafka`에 풀었다고 하자. 이 시리즈의 출력은 카프카 4.4 기준이다. 4.0부터 카프카는 ZooKeeper 없이 **KRaft** 모드로만 돈다(9편). 예제 설정을 복사해 데이터 폴더만 바꾸고, 저장소를 초기화한 뒤 띄운다.
```bash
export PATH="$PATH:/opt/kafka/bin"
sed "s#^log.dirs=.*#log.dirs=$PWD/kafka-data#" /opt/kafka/config/server.properties > server.properties
kafka-storage.sh format --standalone -t "$(kafka-storage.sh random-uuid)" -c server.properties > /dev/null
kafka-server-start.sh server.properties > broker.log 2>&1 &
until kafka-topics.sh --bootstrap-server localhost:9092 --list > /dev/null 2>&1; do sleep 0.5; done
kafka-topics.sh --bootstrap-server localhost:9092 --create --topic orders --partitions 1 --replication-factor 1
```
```text
Created topic orders.
```
`format`은 이 클러스터의 고유 ID로 데이터 폴더를 초기화하는 단계다. 이제 콘솔 프로듀서로 주문 이벤트 세 개를 쓴다. 표준 입력의 한 줄이 이벤트 하나다.
```bash
printf '%s\n' '{"order":1,"item":"coffee"}' '{"order":2,"item":"tea"}' '{"order":3,"item":"cake"}' \
  | kafka-console-producer.sh --bootstrap-server localhost:9092 --topic orders
read_all() {   # 그룹 이름을 받아 처음부터 끝까지 읽는다
  kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders --group "$1" \
    --from-beginning --timeout-ms 4000 --formatter-property print.offset=true 2>/dev/null
}
echo '--- 결제 그룹'; read_all payment
echo '--- 분석 그룹'; read_all analytics
```
```text
--- 결제 그룹
Offset:0	{"order":1,"item":"coffee"}
Offset:1	{"order":2,"item":"tea"}
Offset:2	{"order":3,"item":"cake"}
--- 분석 그룹
Offset:0	{"order":1,"item":"coffee"}
Offset:1	{"order":2,"item":"tea"}
Offset:2	{"order":3,"item":"cake"}
```
결제 그룹이 다 읽은 뒤에도 분석 그룹이 처음부터 전부를 읽었다. 큐였다면 두 번째 그룹에는 아무것도 남아 있지 않았을 것이다. 각 그룹이 어디까지 읽었는지는 카프카가 그룹별로 따로 기억한다.
```bash
echo '--- 결제 그룹 다시'; read_all payment; echo '(새 이벤트 없음)'
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group payment 2>/dev/null \
  | awk '$1 == "payment" { print "결제 그룹: 커밋한 오프셋", $4, "/ 로그 끝", $5, "/ 남은 양(lag)", $6 }'
kafka-server-stop.sh > /dev/null 2>&1
```
```text
--- 결제 그룹 다시
(새 이벤트 없음)
결제 그룹: 커밋한 오프셋 3 / 로그 끝 3 / 남은 양(lag) 0
```
같은 그룹으로 다시 읽으면 이미 읽은 곳(오프셋 3) 다음부터라 새 이벤트가 없다. 그룹이 커밋한 오프셋과 로그 끝의 차이가 **지연**(lag)이고, 소비자가 따라가지 못하고 있는지를 보는 가장 중요한 운영 지표다(12편).

## 짧은 역사
카프카는 링크드인에서 제이 크렙스, 네하 나크헤데, 준 라오 등이 사용자 활동 이벤트와 시스템 지표를 대량으로 나르려고 만들어 2011년에 공개했고, 이듬해 아파치 재단의 최상위 프로젝트가 되었다. 오랫동안 클러스터의 메타데이터를 ZooKeeper라는 별도 시스템에 맡겼지만, 2025년 3월의 4.0부터는 카프카 스스로 Raft 합의로 관리한다(9편).

## 무엇이 다른가
| 도구 | 읽으면 | 잘 맞는 곳 |
| --- | --- | --- |
| Redis 리스트 | 사라짐 | 단순한 작업 큐 |
| Redis 스트림 | 메모리에 남음 | 짧은 이벤트, 작업 분배 |
| 전통적 메시지 큐 | 확인 후 사라짐 | 작업 분배, 복잡한 라우팅 |
| 카프카 | 디스크에 남음 | 대용량, 여러 소비자, 다시 읽기 |

카프카는 대량의 이벤트를 디스크에 순서대로 쓰고 순서대로 읽는 데 최적화되어 있어 초당 수십만~수백만 건을 처리한다. 대신 메시지 하나하나를 골라 지우거나, 메시지마다 다른 곳으로 보내는 복잡한 라우팅은 전통적인 메시지 큐가 낫다.

## 흔한 오해
- "카프카는 메시지 큐다": 큐처럼 쓸 수 있지만 본질은 로그다. 읽어도 지워지지 않고, 소비자가 위치를 기억한다.
- "카프카에 쓰면 영원히 남는다": 보존 기간(기본 7일)이나 크기가 지나면 지운다. 키마다 마지막 값만 남기는 압축 토픽(10편)도 있다.
- "이벤트를 다 읽으면 끝난 것이다": 처리 중 장애가 나면 어디까지 처리했는지(커밋한 오프셋)와 실제 처리 결과가 어긋날 수 있다. 7편의 전달 보장이 그 이야기다.

## 어디에 쓰이나
- Redis 실무 6편 「메시징: Pub/Sub과 스트림」: 같은 "로그와 컨슈머 그룹"이라는 생각을 메모리 안에서 작게 구현한 것이 Redis 스트림이다.
- 웹 앱의 원리 14편 「오래 걸리는 업무 처리: 작업 큐, 재시도, 멱등 키」: 주문 접수와 처리를 나누는 구조의 가운데에 카프카가 들어간다.
- 추상 데이터 타입 심화 21편 「LSM 트리: 쓰기를 모았다가 정렬해서 내려보내기」: 추가 전용 로그에 순서대로 쓰는 것이 왜 빠른지 저장 구조 쪽에서 본다.

## 정리
- 카프카는 이벤트를 토픽이라는 추가 전용 로그에 덧붙이고, 읽어도 지우지 않고 보존 기간 동안 둔다.
- 소비자는 오프셋으로 위치만 기억한다. 서로 다른 컨슈머 그룹은 같은 이벤트를 각자 다 읽고, 다시 읽을 수도 있다.
- 브로커가 로그를 저장하고, 토픽은 파티션으로 나뉘며, 프로듀서가 쓰고 컨슈머가 읽는다.
- 커밋한 오프셋과 로그 끝의 차이(lag)가 소비자가 따라가고 있는지를 보여 준다.
