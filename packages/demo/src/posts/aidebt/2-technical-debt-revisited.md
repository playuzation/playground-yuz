## 문제: 모든 불만이 "기술 부채"가 되었다
오늘날 기술 부채는 마음에 들지 않는 코드를 통틀어 부르는 말이 되었다. 오래된 프레임워크, 테스트 없는 모듈, 이름이 이상한 변수까지 모두 기술 부채라고 부른다. 말이 모든 것을 뜻하면 무엇부터 갚을지 정할 수 없다. 1편의 지도에서 기술 부채를 인지·의도 부채와 나누려면 먼저 이 말의 원래 뜻을 정확히 해 둬야 한다.

## 커닝햄의 비유(1992)
Ward Cunningham은 OOPSLA 1992의 경험 보고 「The WyCash Portfolio Management System」에서 이 비유를 내놓았다. 포트폴리오 관리 시스템을 반복적으로 개발한 경험을 설명하는 글이다. 원문 사본과 여러 2차 자료가 인용하는 첫 문장은 이렇다(번역): "처음 쓴 코드를 내보내는 것은 빚을 지는 것과 같다." 이어서 그는 약간의 빚은 개발을 빠르게 하지만 재작성으로 빨리 갚아야 하고, 위험은 갚지 않을 때 생긴다고 쓴다. 그리고 제대로 되지 않은 코드에 쓰는 매분이 그 빚의 이자라고 덧붙인다.

여기서 빚진 것은 "지저분한 코드"가 아니라 "아직 덜 자란 이해로 쓴 코드"다. 커닝햄은 2009년 영상에서 나쁘게 짜는 것을 찬성한 적이 없다고 해명했다. 그가 말한 것은 지금의 이해를 반영하는 코드를 쓰고, 이해가 자라면 코드도 그 이해에 맞게 고쳐 쓰라는 것이었다. 이 시리즈의 관점에서 보면 기술 부채는 처음부터 이해와 맞닿아 있었다. 코드가 팀의 이해를 따라가지 못하는 것이 커닝햄의 기술 부채라면, 1편의 인지 부채는 반대로 팀의 이해가 코드를 따라가지 못하는 상태다.

## 흔한 오해와 파울러의 사분면
비유가 퍼지면서 "나중에 갚으면 되니 지금은 대충 짜도 된다"는 면죄부로도 쓰이기 시작했다. Martin Fowler는 2009년 블로그 글 「Technical Debt Quadrant」에서 빚을 두 축으로 나눴다. 무모한(reckless) 빚인가 신중한(prudent) 빚인가, 의도적(deliberate)인가 부주의한(inadvertent)가다. 칸 안의 말은 이 사분면을 소개하는 글들이 흔히 인용하는 예다.

| 구분 | 의도적 | 부주의한 |
|---|---|---|
| 무모한 | "설계할 시간 없어" | "계층화가 뭔데?" |
| 신중한 | "지금 내고 결과는 감당한다" | "이제야 어떻게 했어야 했는지 안다" |

Fowler는 신중하면서 부주의한 빚, 곧 다 만들고 나서야 더 나은 설계를 깨닫는 경우가 뛰어난 설계자 팀에게도 흔할 뿐 아니라 피할 수 없다고 본다. 커닝햄의 원래 비유에 가장 가까운 칸이 여기다. 무모한 두 칸은 비유가 정당화하려던 것이 아니다.

AI 시대에 이 표를 다시 보면 질문이 하나 생긴다. 에이전트가 쓴 코드를 아무도 읽지 않고 병합했다면 그 빚은 어느 칸인가? 빨리 내기로 한 결정은 의도적이었지만 무엇을 빚졌는지는 아무도 모르니, 의도적이면서 부주의한 빚이다. 3편은 이런 빚의 흔적을 데이터로, 5편은 그 뒤에 남는 이해의 공백을 다룬다.

## 이자의 정체: 원금, 이자, 상환
비유를 셈으로 바꿔 보자. **원금**은 그 코드를 제대로 고쳐 쓰는 비용이고, **이자**는 고치지 않은 채 그 코드를 건드릴 때마다 더 드는 시간이다. 장난감 모형을 만든다. 기능 하나를 깔끔하게 만들면 10, 빨리 만들면 6이 걸리지만 빨리 만들 때마다 부채가 1단위 쌓인다. 그 뒤의 모든 기능은 부채 1단위당 0.5씩 더 걸리고, 부채 1단위를 갚는 데는 3이 든다. 실제 팀의 수치가 아니라 개념을 보이려는 가정이다.
```python
CLEAN, QUICK, RATE, REPAY = 10, 6, 0.5, 3   # 깔끔하게, 빨리, 이자율, 상환비

def run(n, borrow, repay_every=0):
    debt, t, done, costs = 0, 0.0, [], []
    for i in range(1, n + 1):
        cost = RATE * debt + (QUICK if borrow else CLEAN)  # 이자 + 기능
        debt += borrow
        t += cost; costs.append(cost); done.append(t)      # i번째 완료 시각
        if repay_every and i % repay_every == 0:
            t += REPAY * debt; debt = 0                    # 원금 상환
    return done, t, costs

plans = {"깔끔하게만": (False,), "빚만 쌓기": (True,), "5개마다 갚기": (True, 5)}
for name, args in plans.items():
    done, total, costs = run(30, *args)
    print(f"{done[4]:5.1f} {total:6.1f} {costs[-1]:5.1f}  {name}")

clean, _, _ = run(30, False)
quick, _, qcost = run(30, True)
print("누적 시간이 뒤집히는 기능:", next(i for i in range(30) if quick[i] > clean[i]) + 1)
print("한 기능 비용이 10을 넘는 기능:", next(i for i in range(30) if qcost[i] > CLEAN) + 1)
```
```text
 50.0  300.0  10.0  깔끔하게만
 35.0  397.5  20.5  빚만 쌓기
 35.0  300.0   8.0  5개마다 갚기
누적 시간이 뒤집히는 기능: 18
한 기능 비용이 10을 넘는 기능: 10
```
열은 차례로 5번째 기능이 끝난 시각, 30개를 끝내기까지의 총시간(상환 포함), 30번째 기능 하나의 비용이다. 빨리 만드는 쪽은 다섯 번째 기능을 35에 내놓아 깔끔한 쪽(50)보다 빠르다. 빚을 지는 이유가 여기 있다. 그러나 갚지 않으면 10번째 기능부터는 기능 하나가 깔끔한 쪽보다 비싸지고, 18번째부터는 누적 시간까지 뒤처진다. 30번째 기능은 20.5로 두 배가 넘고, 총시간은 397.5로 약 1.3배다. 5개마다 갚는 쪽은 출시를 앞당기면서도 총시간이 깔끔한 쪽과 같다. 커닝햄이 말한 "제때 갚는 약간의 빚"이 이런 모습이다. 물론 결론은 숫자 가정에 달려 있어서, 상환 비용이 더 크면 빌리는 쪽이 손해가 된다.

이 모형에는 가정이 하나 숨어 있다. 모든 기능이 빚진 코드를 건드린다는 가정이다. 실제로는 그 코드를 건드릴 때만 이자를 낸다. 부채가 4단위씩 있는 세 모듈이 있고, 기능 30개 중 21개는 결제, 6개는 알림, 3개는 관리자 화면을 건드린다고 하자. 원금 12를 들여 한 모듈만 갚을 수 있다면 어디를 갚아야 할까?
```python
RATE, REPAY = 0.5, 3
debt = {"결제": 4, "알림": 4, "관리자": 4}                  # 모듈마다 부채 4단위
touches = (["결제"] * 7 + ["알림"] * 2 + ["관리자"]) * 3   # 기능 30개가 건드리는 곳

def total_cost(repaid=None):
    d, cost = dict(debt), 0.0
    if repaid:
        cost += REPAY * d[repaid]; d[repaid] = 0    # 원금 12를 먼저 갚는다
    for m in touches:
        cost += RATE * d[m]                         # 건드릴 때만 이자를 낸다
    return cost

print({m: touches.count(m) for m in debt})
for repaid in [None, "결제", "알림", "관리자"]:
    print(f"{total_cost(repaid):5.1f}  {repaid or '갚지 않음'}")
```
```text
{'결제': 21, '알림': 6, '관리자': 3}
 60.0  갚지 않음
 30.0  결제
 60.0  알림
 66.0  관리자
```
같은 원금을 갚아도 결제 모듈을 갚으면 총비용이 60에서 30으로 반이 되고, 알림은 본전이며, 거의 건드리지 않는 관리자 모듈을 갚으면 66으로 오히려 손해다. 빚의 크기보다 그 코드를 얼마나 자주 건드리는지가 이자를 정한다. 그래서 "가장 지저분한 코드"보다 "자주 바뀌면서 지저분한 코드"부터 갚는 것이 합리적이고, 자주 바뀌는 정도를 재는 지표가 다음 절의 변동이다.

## 측정의 어려움과 대리 지표
이자는 "부채가 없었다면 걸렸을 시간"과의 차이라서 직접 잴 수 없다. 그래서 팀은 대리 지표를 쓴다.

| 지표 | 재는 것 | 함정 |
|---|---|---|
| 변동(churn) | 자주·많이 바뀌는 곳 | 활발한 개발과 구분이 어렵다 |
| 중복 | 같은 코드 여러 벌 | 의도한 중복도 있다 |
| 복잡도 | 분기·중첩의 양 | 문제 자체가 복잡할 수 있다 |
| 결함 밀도 | 코드 크기당 결함 | 늦게, 보고된 만큼만 보인다 |

변동이 결함을 예고한다는 고전적 근거로 Nagappan과 Ball의 ICSE 2005 연구가 있다. 윈도 서버 2003을 사례로, 바뀐 줄 수 같은 절대 변동은 결함 밀도를 잘 예측하지 못했지만 변동량을 전체 크기 같은 기준에 비춘 상대 변동 지표는 잘 예측했고, 결함이 많은 바이너리와 적은 바이너리를 89.0%의 정확도로 구분했다고 보고했다. 상용 시스템 하나의 사례라서 다른 프로젝트에 그대로 옮길 수는 없다.

어떤 지표든 목표가 되면 왜곡된다. 중복을 줄이라는 목표는 억지 추상화를 낳고, 복잡도 상한은 함수를 의미 없이 쪼개게 만든다. 대리 지표는 대화를 시작하는 신호로 쓰고, 위 모형처럼 "자주 바뀌는가"와 "바꾸기 어려운가"를 함께 보는 편이 낫다. 3편은 이 지표들이 AI 보조 개발에서 어떻게 움직였는지 본다.

## 코드 밖의 부채: 스컬리 외(2015)
구글의 D. Sculley 외는 NeurIPS 2015 논문 「Hidden Technical Debt in Machine Learning Systems」에서 이 비유를 머신러닝 시스템으로 넓혔다. 초록이 꼽는 위험 요인은 경계 침식, 얽힘, 숨은 피드백 루프, 선언되지 않은 소비자, 데이터 의존성, 설정 문제, 외부 세계의 변화, 시스템 수준의 안티패턴이다. 얽힘의 예로 논문은 특징 x₁…xₙ을 쓰는 모델에서 x₁의 입력 분포가 바뀌면 나머지 n−1개 특징의 중요도와 가중치가 모두 바뀔 수 있다고 설명하고, 이를 CACE(Changing Anything Changes Everything) 원리라고 부른다. 피드백 루프는 모델의 출력이 돌고 돌아 미래의 학습 데이터에 영향을 주는 고리다.

이 논문이 이 시리즈에 중요한 이유는 코드 리뷰로는 보이지 않는 곳에도 빚이 쌓인다는 것을 보였기 때문이다. 코드 한 줄 바뀌지 않아도 데이터 분포가 바뀌면 시스템이 나빠지고, 누가 어떤 출력을 쓰는지 모르면 안심하고 바꿀 수 없다. 빚이 데이터와 설정과 시스템 사이의 관계에 살 수 있다면, 사람의 머릿속(인지 부채, 5편)과 기록되지 않은 이유(의도 부채, 8편)에도 살 수 있다. LLM 시대의 프롬프트·설정 파일에 쌓이는 부채(3·4편)도 그 연장선에 있다.

## 팀의 실천
- 빚을 질 때 사분면의 어느 칸인지 말하고, 의도적인 빚은 이유와 갚을 조건을 이슈로 남긴다. 기록되지 않은 의도적 빚은 시간이 지나면 부주의한 빚과 구별되지 않는다(9편).
- 갚을 곳은 변동과 바꾸기 어려움을 함께 보고 고른다. 거의 건드리지 않는 코드의 빚은 급하지 않다.
- 커닝햄의 처방대로 작게, 자주 갚는다. 오래 둔 빚은 그동안의 이자가 이미 나간 뒤다.
- 대리 지표는 목표가 아니라 신호로 쓰고, 숫자가 움직이면 그 코드를 아는 사람과 먼저 이야기한다.

## 정리
- 커닝햄의 기술 부채는 지금의 이해로 빨리 내놓고 이해가 자라면 고쳐 쓰는 빚이었지, 나쁜 코드의 면죄부가 아니었다.
- 파울러의 사분면은 빚을 무모한/신중한, 의도적/부주의한으로 나누고, 신중하면서 부주의한 빚은 좋은 팀에게도 피할 수 없다고 본다.
- 이자는 빚진 코드를 건드릴 때만 내므로, 같은 원금이라도 자주 바뀌는 곳을 갚는 것이 가장 이득이다(모형에서 60 → 30).
- 이자는 직접 잴 수 없어 대리 지표를 쓰고, 스컬리 외는 빚이 데이터·설정처럼 코드 밖에도 산다는 것을 보였다.
