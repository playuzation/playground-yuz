## 상환 비용이 내려갔다
2편에서 본 커닝햄의 비유에서 이자는 제대로 되지 않은 코드 때문에 매번 더 드는 시간이고, 원금을 갚는 방법은 리팩터링이나 재작성이다. 상환은 늘 기능 개발과 시간을 다퉜다. 이름을 고치고 중복을 합치고 테스트를 보강하는 일은 중요하지만 급하지 않아서 미뤄진다. 3편의 데이터는 LLM이 부채를 더 빨리 쌓는 쪽을 보여 주었다. 이 글은 반대 질문을 다룬다. 같은 도구가 상환 비용까지 낮춘다면 어떻게 될까?

Storey(2026)는 삼중 부채 모델을 제안하면서 생성형 AI가 기술 부채를 줄여 줄 수도 있다고 본다. 다만 AI 시대에는 기술 부채가 더 이상 가장 중요한 제약이 아닐 수 있고, 그 대신 인지 부채와 의도 부채가 빨리 쌓일 수 있다고 경고한다. 2026년 4월 16일 리우데자네이루에서 열린 ICSE 2026 패널 「Technical Debt in the AI Era」(사회 Paris Avgeriou·Ipek Ozkaya, Storey도 패널로 참여)는 이 양면을 "양날의 검"으로 소개했다. AI는 기술 부채를 자동으로 찾고, 재고, 우선순위를 매기고, 갚는 도구를 줄 수 있지만, 코드 생성과 에이전트 개발로 부채를 더한다는 증거도 있다는 것이다.

## 초기 데이터: 에이전트는 리팩터링을 하는가
Horikawa 외(2025, arXiv 프리프린트)는 공개 데이터셋 AIDev에 담긴 오픈 소스 자바 프로젝트의 에이전트 PR 1만 2,256개에서 리팩터링 1만 5,451건을 찾았다. 에이전트 커밋의 26.1%가 명시적으로 리팩터링을 겨냥했고, 내세운 동기는 유지보수성(52.5%)과 가독성(28.1%)이 많았다. 다만 변경은 변수 타입 바꾸기, 이름 바꾸기 같은 저수준 정리에 치우쳐 사람이 하는 고수준 설계 변경과는 성격이 달랐다. 클래스 크기와 복잡도 같은 구조 지표는 작지만 통계적으로 유의하게 좋아졌다. 에이전트가 정리 작업을 꽤 한다는 근거이지, 3편에서 본 중복과 설계 수준의 부채까지 갚는다는 근거는 아직 아니다.

안전성은 다른 문제다. Liu 외(2024년 arXiv 공개, 2025년 학술지 Automated Software Engineering 게재)는 자바 프로젝트 20개의 실제 리팩터링 180건을 두고 범용 LLM에게 해법을 내게 했다. ChatGPT가 낸 176건 중 13건, Gemini가 낸 137건 중 9건이 기능을 바꾸거나 문법 오류를 넣은 "안전하지 않은" 해법이었다. 저자들은 범용 LLM이 입력과 출력의 의미가 같은지 확인하지 않는다는 점을 원인으로 들고, LLM이 고른 리팩터링을 검증된 리팩터링 엔진으로 다시 적용하는 방법(RefactoringMirror)을 제안했다. 이 방법은 LLM이 한 리팩터링의 94.3%를 재적용하면서 버그 있는 해법은 모두 피했다고 보고한다. 모델은 그 뒤로 여러 세대가 바뀌었으니 비율보다 구조를 기억하자. "리팩터링"이라는 이름은 동작 보존을 보장하지 않으며, 보존을 확인하는 장치는 모델 밖에 있어야 한다.

## 안전하게 갚는 조건
- **안전망이 먼저**: 바꾸기 전에 지금의 동작을 고정하는 테스트가 있어야 한다. 없으면 아래의 특성 테스트부터 만든다.
- **작은 단위**: 한 PR에는 한 종류의 변환만 담고 기능 변경과 섞지 않는다. 사람이 읽을 수 있는 diff여야 리뷰가 의미를 가진다.
- **결정적 도구 우선**: 이름 바꾸기나 메서드 추출처럼 IDE의 리팩터링 엔진이 할 수 있는 변환은 엔진에 맡기고, 에이전트에게는 무엇을 바꿀지 고르는 일을 맡긴다.
- **설명할 수 있는 검토**: 승인하는 사람이 새 구조를 남에게 설명할 수 있어야 한다(5·7편).
- **이유와 함께**: 의존성을 올린 이유와 깨질 수 있는 지점을 PR 설명에 남긴다. 기록되지 않은 이유는 8편의 의도 부채가 된다.

## 특성 테스트: 지금의 동작을 사진 찍기
마이클 페더스(Michael Feathers)는 『Working Effectively with Legacy Code』(2004)에서 **특성 테스트**(characterization test)라는 이름을 썼다. 코드가 해야 하는 일이 아니라 지금 실제로 하는 일을 기록하는 테스트다. 페더스는 레거시 코드를 테스트가 없는 코드로 보았고, 특성 테스트는 그런 코드를 바꾸기 전에 까는 안전망이다. 골든 마스터, 스냅숏 테스트도 같은 발상이다. 아래는 개념을 보이기 위한 장난감 예다. 오래된 배송비 함수가 있다.
```python
# 파일: legacy.py
def shipping_fee(weight, region, member):
    fee = 3000
    if weight > 5:
        fee = fee + (weight - 5) * 500
    if region == "jeju":
        fee = fee + 3000
    if member and fee > 3000:
        fee = fee - 1000
    return int(fee)
```
입력 조합 24개에 대한 지금의 출력을 기록하고, 다른 구현이 같은 출력을 내는지 비교하는 스크립트를 만든다. 기록할 때는 그 값이 옳은지 묻지 않는다.
```python
# 파일: characterize.py
import importlib, itertools, json, sys

CASES = list(itertools.product([1, 5, 5.5, 10], ["seoul", "jeju", "JEJU"], [False, True]))
mode, name = sys.argv[1], sys.argv[2]
fee = importlib.import_module(name).shipping_fee
now = [fee(*c) for c in CASES]
if mode == "record":                  # 지금의 동작을 그대로 기록한다
    json.dump(now, open("golden.json", "w"))
    print(f"기록: {len(CASES)}개 사례")
else:
    golden = json.load(open("golden.json"))
    diff = [(c, g, n) for c, g, n in zip(CASES, golden, now) if g != n]
    for c, g, n in diff[:3]:
        print(f"  {c}: 기록 {g} → 지금 {n}")
    print(f"{name}: {len(CASES) - len(diff)}/{len(CASES)} 일치")
```
에이전트에게 "읽기 쉽게 정리해 줘"라고 맡겨 다음 판이 나왔다고 하자. 상수에 이름을 붙이고 조건문을 줄였다. 리뷰에서 승인하기 쉬운 모양이다.
```python
# 파일: refactored.py
BASE, PER_KG, JEJU, DISCOUNT = 3000, 500, 3000, 1000

def shipping_fee(weight, region, member):
    extra = max(0, weight - 5) * PER_KG
    surcharge = JEJU if region.lower() == "jeju" else 0
    discount = DISCOUNT if member else 0
    return int(BASE + extra + surcharge - discount)
```
```bash
python3 characterize.py record legacy
python3 characterize.py check refactored
```
```text
기록: 24개 사례
  (1, 'seoul', True): 기록 3000 → 지금 2000
  (1, 'JEJU', False): 기록 3000 → 지금 6000
  (1, 'JEJU', True): 기록 3000 → 지금 5000
refactored: 14/24 일치
```
정리된 판은 24개 중 10개에서 기록과 다르다. 하나는 회원 할인 조건이다. 원래 코드는 요금이 기본료보다 클 때만 1,000원을 깎는데, 군더더기처럼 보이던 `fee > 3000`이 정리 중에 사라졌다. 다른 하나는 `"JEJU"`처럼 대문자로 들어온 지역이다. 원래 코드는 추가 요금을 붙이지 않는데 정리된 판은 `lower()`로 "친절하게" 고쳤다. 둘 다 개선처럼 보이지만 동작 변경이다. 특성 테스트는 무엇이 옳은지 알려 주지 않고 바뀐 곳을 보여 줄 뿐이다. 할인 조건에 이유가 있었는지는 코드에 적혀 있지 않다(8편의 주제다). 대문자 지역이 버그라면 고치되, 리팩터링과 분리된 PR에서 기록을 갱신하고 이유를 남긴다. 동작을 보존한 판은 기록과 모두 맞는다.
```python
# 파일: fixed.py
BASE, PER_KG, JEJU, DISCOUNT = 3000, 500, 3000, 1000

def shipping_fee(weight, region, member):
    fee = BASE + max(0, weight - 5) * PER_KG
    if region == "jeju":          # 대소문자 구분: 버그인지는 따로 결정한다
        fee += JEJU
    if member and fee > BASE:     # 이 조건의 이유는 기록되어 있지 않다
        fee -= DISCOUNT
    return int(fee)
```
```bash
python3 characterize.py check fixed
```
```text
fixed: 24/24 일치
```
입력 목록에 `"JEJU"`가 없었다면 두 번째 차이는 잡히지 않았다. 트랜지스터에서 자연어까지 13편에서 약한 테스트를 통과한 식이 오답이었던 것처럼, 특성 테스트도 고른 입력만큼만 지켜 준다. 운영 로그에서 실제 입력을 뽑고 경계값을 넣고, 커버리지 도구로 빠진 분기를 확인한다. 에이전트는 이런 테스트를 빨리 많이 만드는 데 능하지만, 어떤 입력이 중요한지는 도메인을 아는 사람이 정한다.

## 새로 생기는 부채: 에이전트 기술 부채
2편에서 본 스컬리 외(2015)는 머신러닝 시스템의 부채가 코드 밖(데이터 의존성, 숨은 피드백 루프)에도 산다는 것을 보였다. Tukur 외(2026, arXiv 프리프린트)는 이를 한 걸음 더 밀었다. 이 체계적 매핑 연구는 앞선 검토에서 정리한 AI 기술 부채 31종(근본 원인 7범주)을 에이전트 시스템에 맞게 다시 해석하고 **에이전트 기술 부채**(agentic technical debt, AgTD)라고 부른다. 예로 드는 양상은 메모리 불일치, 오케스트레이션 취약성, 연쇄 실패, 안전하지 않은 자율 결정이고, 부채가 에이전트의 행동과 조정, 에이전트·도구·실행 환경 사이의 상호작용으로 번진다고 본다. 실패 양상을 부채 자체로 표기했다는 지적도 있어, 정립된 분류라기보다 제안으로 읽는 편이 맞다.

에이전트 제품을 만들지 않는 팀도 무관하지 않다. 코딩 에이전트를 쓰는 팀의 지침 파일, 프롬프트 모음, 도구 권한과 훅 설정도 하나의 시스템이다. 3편의 다성 문헌 검토가 프롬프트 부채를 새 범주로 꼽은 것과 같은 선에서, 이름이 바뀐 스크립트를 여전히 가리키는 지침, 서로 충돌하는 규칙, 왜 생겼는지 아무도 모르는 금지 조항이 쌓인다. 이런 설정도 코드처럼 버전 관리하고 리뷰하고, 가능하면 CI에서 검사한다(지침에 적힌 명령이 실제로 있는지 같은 것).

## 갚았는데 왜 더 어려워졌나
에이전트가 큰 모듈을 깔끔하게 재구성했다고 하자. 중복은 줄고 지표는 좋아졌다. 그런데 이전 구조를 머릿속에 갖고 있던 사람에게 지금 구조는 처음 보는 코드다. 이 구조를 지으며 고민한 사람이 없으니 왜 이렇게 나뉘었는지 설명할 사람도 없다. 기술 부채를 갚은 자리에 인지 부채가 생긴 것이다. 그래서 에이전트 리팩터링 PR에는 "무엇을 바꿨나"보다 "새 구조를 어떻게 이해하면 되나"를 적게 하고, 병합 전에 작성자가 아닌 사람이 새 구조를 설명해 보게 한다. 이 이동이 왜 조용히 일어나는지는 5편에서, 팀이 진단하고 갚는 법은 7편에서 다룬다. 아직 모르는 것도 크다. 여기서 본 자료는 PR 단위의 단면 분석이고, 에이전트 리팩터링이 몇 년에 걸쳐 결함과 변경 비용을 줄이는지 추적한 자료는 찾지 못했다.

## 어디에 쓰이나
- 트랜지스터에서 자연어까지 13편 「AI 에이전트와 자연어 프로그래밍: 명세와 검증의 시대」: 검증기가 약하면 오답이 통과한다는 그 글의 실험이 특성 테스트의 입력을 고르는 일이 왜 중요한지 보여 준다.

- 5편 「인지 부채 1: 프로그램은 사람 머릿속의 이론이다」: 이해 없이 갚은 기술 부채가 어디로 옮겨 가는지 이어서 본다.

## 정리
- Storey와 ICSE 2026 패널은 AI를 기술 부채를 갚는 도구이자 새 부채의 원천으로 본다.
- 에이전트는 리팩터링을 실제로 많이 하지만 저수준 정리에 치우치고, 범용 LLM의 리팩터링 제안 일부는 동작을 바꾼다. 동작 보존은 모델 밖의 테스트와 엔진이 확인한다.
- 특성 테스트는 지금의 동작을 기록해 바뀐 곳을 드러내지만, 옳고 그름은 사람이 정하고 고른 입력만큼만 지켜 준다.
- 에이전트 설정과 프롬프트도 부채가 되고, 이해 없이 갚은 기술 부채는 인지 부채로 옮겨 간다.
