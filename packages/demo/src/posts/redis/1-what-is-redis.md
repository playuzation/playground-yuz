# [Redis 실무 1/10] Redis란: 메모리 위의 자료 구조 서버

> **한 줄 요약** — Redis는 데이터를 메모리에 두고 문자열·리스트·해시·셋·정렬된 셋 같은 자료 구조를 네트워크 너머에서 명령 하나로 다루게 해 주는 서버로, 명령을 한 줄로 차례차례 실행하기 때문에 빠르고 원자적이며, 캐시·세션·카운터·순위표·레이트 리밋·간단한 큐에 널리 쓰인다.

## 이 글에서 다루는 것
- 데이터베이스가 있는데 왜 또 Redis인가: 메모리와 디스크의 거리
- "키-값 저장소"가 아니라 "자료 구조 서버"인 이유
- 명령을 하나씩 실행하는 이벤트 루프와 원자성
- 직접 해 보기: 서버 띄우기, 첫 명령, 글자로 된 프로토콜(RESP), 초당 처리량 재기
- 짧은 역사와 라이선스 이야기

## 왜 또 하나의 저장소인가
웹 앱(웹 앱의 원리 4편)은 요청마다 데이터베이스에 묻는다. 인기 상품 목록이나 로그인 세션처럼 1초에 수천 번 읽히는 값을 매번 디스크 기반 데이터베이스에서 꺼내면, 쿼리 해석과 디스크 접근과 잠금이 쌓여 느려진다. **Redis**(REmote DIctionary Server)는 데이터를 **메모리**에 두고, 단순한 명령 하나로 읽고 쓰게 해서 이 문제를 푼다. 메모리 접근은 SSD보다 수백 배 이상 빠르다(메모리 시스템 1편). 그래서 Redis는 보통 데이터베이스를 **대체**하기보다 그 **앞이나 옆**에 선다. 원본은 PostgreSQL 같은 데이터베이스가 지키고, Redis는 자주 쓰는 사본(캐시)과 잠깐 쓰고 버리는 값(세션, 카운터)을 맡는다.

## 키-값이 아니라 자료 구조 서버
Redis를 흔히 키-값 저장소라고 부르지만, 값이 단순한 글자만은 아니다. 값의 자리에 **자료 구조**가 들어간다.
- 문자열(string): 글자, 숫자, 바이너리. `INCR`로 숫자를 원자적으로 올린다(2편).
- 리스트(list): 양 끝에 넣고 빼는 줄. 작업 큐에 쓴다.
- 해시(hash): 필드-값 묶음. 사용자 프로필 한 명분.
- 셋(set): 중복 없는 모음. 태그, 좋아요 누른 사람.
- 정렬된 셋(sorted set): 점수 순으로 정렬된 셋. 순위표, 시간순 목록(3편).
- 스트림(stream): 추가만 되는 로그와 컨슈머 그룹(6편).

핵심은 **연산이 서버 안에서 일어난다**는 점이다. "순위표 상위 10명"을 원하면 전체를 받아 와 정렬하지 않고, 서버에 `ZREVRANGE` 한 번만 보내면 정렬된 결과 10개만 돌아온다. 자료 구조와 그 연산을 서버에 둔 것이 Redis의 정체성이다.

## 한 줄로 실행하기
Redis 서버는 클라이언트 수천 개의 연결을 운영체제의 이벤트 알림(리눅스의 epoll)으로 지켜보다가, 도착한 명령을 **한 번에 하나씩** 실행한다. 웹 앱의 원리 2편의 이벤트 루프와 같은 구조다(6.0부터는 네트워크 읽기·쓰기를 돕는 I/O 스레드를 켤 수 있지만, 명령 실행 자체는 여전히 한 줄이다). 여기서 두 가지가 나온다.
- **원자성**: 명령 하나가 실행되는 동안 다른 명령이 끼어들지 않는다. 두 클라이언트가 동시에 `INCR visits`를 보내도 값이 정확히 2 늘어난다. 잠금 없이 카운터와 레이트 리밋을 만들 수 있는 이유다(5편).
- **느린 명령의 위험**: 반대로 명령 하나가 오래 걸리면 그동안 모든 클라이언트가 기다린다. 키 수백만 개를 훑는 `KEYS *` 같은 명령이 운영에서 금기인 이유다(9편).

## 직접 해 보기 1: 서버와 첫 명령
우분투라면 `sudo apt install redis-server`로 설치한다(이 글의 출력은 우분투 24.04 패키지의 Redis 7.0 기준). 기본 포트 6379의 서비스와 겹치지 않게 6390번 포트에 실습용 서버를 따로 띄운다. `--save ""`는 디스크 저장을 끄는 옵션이다(7편).
```bash
redis-server --port 6390 --save "" --appendonly no > redis.log 2>&1 &
until redis-cli -p 6390 ping > /dev/null 2>&1; do sleep 0.1; done
redis-cli -p 6390 info server | grep -E '^(redis_version|multiplexing_api|tcp_port)'
```
```text
redis_version:7.0.15
multiplexing_api:epoll
tcp_port:6390
```
이제 값을 넣고 읽는다. 스크립트에서 `redis-cli`를 부르면 값만 출력하고, 터미널에서 직접 치면 `(integer) 1`처럼 종류 표시가 붙는다.
```bash
r() { redis-cli -p 6390 "$@"; }
r set greeting "안녕, Redis"
r get greeting
r incr visits
r incr visits
r dbsize
```
```text
OK
안녕, Redis
1
2
2
```
`visits`는 만든 적이 없지만 `INCR`이 없는 키를 0으로 보고 1로 만들었다. 키 두 개(`greeting`, `visits`)가 생겼다.

## 직접 해 보기 2: 글자로 된 프로토콜
Redis 클라이언트와 서버는 **RESP**(REdis Serialization Protocol)라는 단순한 글자 형식으로 대화한다. 웹 앱의 원리 9편의 HTTP처럼 사람이 읽을 수 있다. `nc`로 바이트를 직접 보내 보자. `*3`은 "세 조각짜리 배열", `$3`은 "3바이트짜리 문자열"이라는 뜻이다.
```bash
printf 'PING\r\n' | nc -N 127.0.0.1 6390
printf '*3\r\n$3\r\nSET\r\n$4\r\ncity\r\n$5\r\nSeoul\r\n*2\r\n$3\r\nGET\r\n$4\r\ncity\r\n' \
  | nc -N 127.0.0.1 6390 | tr '\r' '~'
```
```text
+PONG
+OK~
$5~
Seoul~
```
`+`로 시작하면 짧은 성공 응답, `$5`는 "다음 5바이트가 값"이라는 뜻이다(`~`는 보이지 않는 `\r`을 표시하려고 바꾼 글자다). 길이를 먼저 알려 주니 값 안에 줄바꿈이 있어도 경계가 헷갈리지 않는다. 형식이 이렇게 단순해서 거의 모든 언어에 클라이언트 라이브러리가 있다.

## 직접 해 보기 3: 얼마나 빠른가
`redis-benchmark`는 함께 설치되는 부하 측정 도구다. 연결 50개로 `SET`과 `GET`을 2만 번씩 보낸다. 숫자는 컴퓨터마다 다르다.
```bash
redis-benchmark -p 6390 -q -n 20000 -t set,get --csv | cut -d, -f1,2
```
```text
"test","rps"
"SET","…"
"GET","…"
```
이 실습 환경에서는 둘 다 초당 10만 건 안팎이 나왔다. 같은 컴퓨터 안이라 네트워크 왕복이 거의 없는 값이고, 실제 서비스에서는 왕복 시간이 처리량을 좌우한다. 그래서 명령 여러 개를 한 번에 보내는 파이프라이닝(9편)이 중요하다. 마지막으로 서버를 끈다.
```bash
r shutdown nosave
sleep 0.5; r ping 2>&1 | head -1
```
```text
Could not connect to Redis at 127.0.0.1:6390: Connection refused
```

## 짧은 역사와 라이선스
Redis는 이탈리아의 살바토레 산필리포(antirez)가 실시간 웹 분석 서비스를 만들다 MySQL의 성능 한계에 부딪혀 만들었고, 2009년 2월 처음 공개했다. 오랫동안 BSD 라이선스의 오픈 소스였지만, 2024년 3월 Redis 회사가 RSALv2와 SSPLv1이라는 제한적 라이선스로 바꾸었다. 그 직후 리눅스 재단이 마지막 BSD 버전(7.2.4)을 이어받은 포크 **Valkey**를 출범시켰고, 2025년 5월 Redis 8은 AGPLv3를 선택지에 더해 다시 오픈 소스 라이선스를 갖게 되었다. 이 시리즈의 명령은 Redis 7과 Valkey에서 대부분 그대로 동작한다. 회사에서 쓸 때는 버전과 라이선스를 확인해 두자.

## 흔한 오해
- "Redis는 캐시라서 껐다 켜면 다 날아간다": 저장을 켜면 스냅숏(RDB)과 명령 기록(AOF)으로 디스크에 남긴다(7편). 다만 메모리보다 큰 데이터는 담지 못하고, 마지막 저장 이후의 쓰기는 잃을 수 있다.
- "멀티스레드라서 빠르다": 빠른 이유는 메모리, 단순한 자료 구조, 이벤트 루프다. 명령 실행이 한 줄이라 원자적이고, 그래서 느린 명령 하나가 전체를 막는다.
- "Redis가 있으면 데이터베이스가 필요 없다": 복잡한 질의, 조인, 대용량, 엄격한 트랜잭션은 관계형 데이터베이스의 일이다. Redis는 그 옆에서 빠른 사본과 짧은 수명의 값을 맡는다.

## 어디에 쓰이나
- 웹 앱의 원리 11편 「상태 없는 HTTP 위의 로그인: 쿠키, 세션, 토큰」: 서버 여러 대가 함께 보는 세션 저장소로 Redis가 가장 흔히 쓰인다.
- 웹 앱의 원리 19편 「과부하를 막는 장치: 혼잡 제어, 레이트 리밋, 서킷 브레이커」: 토큰 버킷과 요청 수 세기를 서버 여러 대가 공유하려면 Redis 같은 공유 저장소가 필요하다.
- 메모리 시스템 1편 「메모리 계층 지도: 레지스터에서 SSD까지 지연과 대역폭」: Redis가 빠른 근본 이유인 메모리와 디스크의 지연 차이를 숫자로 본다.

## 정리
- Redis는 데이터를 메모리에 두고 자료 구조와 그 연산을 네트워크로 제공하는 서버다.
- 명령을 하나씩 실행하므로 명령 하나는 원자적이고, 느린 명령은 모두를 막는다.
- 프로토콜(RESP)은 길이를 앞에 붙인 단순한 글자 형식이다.
- 보통 데이터베이스를 대신하지 않고 그 앞뒤에서 캐시·세션·카운터·순위표·큐를 맡는다.
