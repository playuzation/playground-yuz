# [언어 기초 8/8] 자바와 JVM: 한 번 작성하면 어디서나 실행

> **한 줄 요약** — 자바는 소스 코드를 플랫폼 중립적인 바이트코드로 컴파일하고, 각 운영체제의 JVM이 그 바이트코드를 해석하고 JIT 컴파일해 실행하는 구조로 "한 번 작성하면 어디서나 실행"을 실현한 정적 타입 객체지향 언어다.

## 이 글에서 다루는 것
- 자바의 특징과 "Write Once, Run Anywhere"
- 소스 → 바이트코드 → JVM으로 이어지는 실행 흐름
- JVM 내부: 클래스 로딩과 검증, 계층형 JIT, 가비지 컬렉터
- JVM 위에서 도는 다른 언어들
- 장단점

## Write Once, Run Anywhere
C 프로그램은 운영체제와 CPU마다 따로 컴파일해야 한다(5편 참고). 자바는 그 사이에 **가상 머신**이라는 층을 하나 더 두었다.
```text
Hello.java
   ↓ javac (컴파일)
Hello.class  ← 플랫폼과 무관한 바이트코드
   ↓ java (실행)
윈도우용 JVM / 리눅스용 JVM / macOS용 JVM
   ↓
각 플랫폼의 기계어로 실행
```

같은 `.class` 파일을 JVM이 설치된 어느 컴퓨터에서든 그대로 실행할 수 있다. 플랫폼마다 새로 만들어야 하는 것은 각각의 프로그램이 아니라 JVM 하나뿐이다.

## 코드로 보기
```java
// Hello.java
import java.util.List;

public class Hello {
    record Post(String title, int likes) {}

    public static void main(String[] args) {
        List<Post> posts = List.of(new Post("자바 입문", 12), new Post("JVM 이야기", 30));
        int total = posts.stream().mapToInt(Post::likes).sum();
        System.out.println("좋아요 합계: " + total);
    }
}
```
```sh
javac Hello.java   # Hello.class와 Hello$Post.class가 생긴다
java Hello         # 좋아요 합계: 42
```

`record`는 데이터를 담는 불변 클래스를 짧게 선언하는 문법이고(자바 16부터), `stream()`은 컬렉션을 함수형 스타일로 처리하는 API다. 클래스 안에 선언한 `Post`도 별도의 `.class` 파일로 컴파일된다.

바이트코드는 JDK에 들어 있는 `javap`로 직접 볼 수 있다.
```java
public class Calc {
    static int add(int a, int b) {
        return a + b;
    }
}
```
```text
$ javap -c Calc
  static int add(int, int);
    Code:
       0: iload_0
       1: iload_1
       2: iadd
       3: ireturn
```

JVM 바이트코드는 3편에서 만든 장난감 VM처럼 **스택 기반**이다. `iload`로 두 값을 스택에 올리고, `iadd`가 둘을 꺼내 더한 결과를 다시 올리면, `ireturn`이 그 값을 반환한다.

## JVM 안에서 일어나는 일
### 클래스 로딩과 검증
JVM은 프로그램 시작 시 모든 코드를 읽지 않고, 클래스가 처음 필요해지는 순간에 불러온다(**클래스 로더**). 불러온 바이트코드는 실행 전에 **검증기**가 스택이 넘치지 않는지, 타입이 맞게 쓰이는지 확인한다. 네트워크에서 받은 코드도 안전하게 실행하려던 초기 설계의 흔적이다.

### 계층형 JIT 컴파일
HotSpot JVM은 처음에는 바이트코드를 인터프리터로 실행하면서 메서드마다 호출 횟수를 센다. 자주 호출되는 메서드는 **C1 컴파일러**가 빠르게 기계어로 바꾸고, 더 자주 쓰이면 **C2 컴파일러**가 실행 중에 모은 정보(어떤 분기를 많이 타는지, 실제로 어떤 타입이 들어오는지)를 바탕으로 공격적으로 최적화한다. 그래서 자바 프로그램은 시작 직후보다 한동안 실행된 뒤에 더 빨라진다(**워밍업**).

### 가비지 컬렉터
자바에서는 메모리를 직접 해제하지 않는다. **가비지 컬렉터**(GC)가 더 이상 참조되지 않는 객체를 찾아 회수한다. 대부분의 객체는 만들어지자마자 금방 버려진다는 관찰(**세대 가설**)을 이용해, 힙을 젊은 세대와 늙은 세대로 나누어 젊은 세대를 자주, 빠르게 정리한다. 요즘 JVM은 기본값인 G1, 멈춤 시간을 아주 짧게 줄인 ZGC 등 여러 GC 중에서 골라 쓸 수 있다.

## JVM 위의 언어들
JVM은 자바 전용이 아니다. 바이트코드만 만들어 내면 어떤 언어든 JVM의 JIT, GC, 방대한 자바 라이브러리를 그대로 쓸 수 있다.
- **코틀린**: 간결한 문법과 널 안전성을 갖춘 언어. 안드로이드 공식 권장 언어다.
- **스칼라**: 함수형과 객체지향을 결합한 언어. Spark가 스칼라로 작성되었다.
- **클로저**(Clojure): JVM 위에서 도는 리스프 계열 언어.

참고로 안드로이드 앱은 자바나 코틀린으로 작성하지만, 기기에서는 JVM이 아니라 바이트코드를 변환해 실행하는 ART 런타임에서 돌아간다. 반대로 시작 속도가 중요한 서버에서는 GraalVM 네이티브 이미지처럼 자바 코드를 미리 기계어로 컴파일(AOT)하는 방법도 쓴다.

## 장점과 단점
| 장점 | 단점 |
|---|---|
| 바이트코드 하나로 여러 플랫폼에서 실행된다 | JVM이 필요하고 메모리를 많이 쓰는 편이다 |
| 정적 타입과 성숙한 IDE·빌드 도구로 대규모 개발에 강하다 | 시작이 느리고 최고 성능까지 워밍업이 필요하다 |
| JIT 덕분에 오래 실행되는 서버에서 빠르다 | 문법이 장황하다는 평이 있다 (최근 버전에서 많이 개선) |
| 하위 호환성이 뛰어나고 라이브러리 생태계가 넓다 | GC 멈춤을 신경 써야 하는 경우가 있다 |

## 정리
- 자바는 바이트코드와 JVM이라는 층을 두어 플랫폼 독립성을 얻었다.
- JVM은 인터프리터로 시작해 자주 쓰는 코드를 JIT로 최적화하고, 메모리는 GC가 관리한다.
- 3편(인터프리터)과 5편(컴파일)의 아이디어가 한데 모인 구조라고 볼 수 있다.
