# [언어 기초 6/8] 어셈블리와 컴파일·링크: 소스 코드가 실행 파일이 되기까지

> **한 줄 요약** — `gcc hello.c` 한 줄 뒤에는 전처리 → 컴파일 → 어셈블 → 링크의 네 단계가 숨어 있고, 그 중간에 사람이 읽을 수 있는 형태의 기계어인 어셈블리가 있다.

## 이 글에서 다루는 것

- C 프로그램이 실행 파일이 되는 네 단계를 직접 따라가기
- 링커가 하는 일과 "undefined reference" 오류
- 정적 링크와 동적 링크

## 어셈블리와 기계어
기계어는 CPU가 실행하는 바이트의 나열이고, **어셈블리**는 그 명령을 사람이 읽을 수 있는 이름(니모닉)으로 거의 1:1로 옮겨 적은 것이다. 어셈블리를 기계어로 바꾸는 프로그램을 **어셈블러**라고 한다.

| 어셈블리 (x86-64) | 기계어 (16진수) | 의미 |
|---|---|---|
| `mov eax, 55` | `b8 37 00 00 00` | eax 레지스터에 55를 넣는다 |
| `add eax, ebx` | `01 d8` | eax에 ebx를 더한다 |
| `ret` | `c3` | 함수를 호출한 곳으로 돌아간다 |

어셈블리는 CPU의 **명령어 집합 구조**(ISA)마다 다르다. 5편에서 본 `sum_to_10` 함수를 ARM64용으로 컴파일하면 모양이 완전히 달라진다.
```asm
// ARM64
sum_to_10:
    mov  w0, #55
    ret
```

어셈블리를 읽을 때 자주 만나는 개념은 세 가지다.
- **레지스터**: CPU 안의 아주 빠른 저장 공간. x86-64에는 `rax`, `rdi`, `rsp` 같은 범용 레지스터가 16개 있다.
- **명령어**: `mov`(옮기기), `add`(더하기), `cmp`(비교), `jmp`(이동), `call`·`ret`(함수 호출과 복귀)
- **호출 규약**: 함수의 인자와 반환값을 어느 레지스터로 주고받을지에 대한 약속. 리눅스 x86-64에서는 첫 번째 인자를 `rdi`로, 반환값을 `rax`로 전달한다.

## hello.c가 실행 파일이 되기까지
```c
// hello.c
#include <stdio.h>
#define GREETING "Hello, linker!"

int main(void) {
    puts(GREETING);
    return 0;
}
```

`gcc hello.c -o hello` 한 줄은 사실 아래 네 단계를 차례로 실행한다. 단계마다 옵션을 주면 중간 결과물을 직접 확인할 수 있다.
```text
hello.c   소스 코드
  ↓ 전처리   gcc -E
hello.i   매크로와 헤더가 펼쳐진 C 코드
  ↓ 컴파일   gcc -S
hello.s   어셈블리
  ↓ 어셈블   gcc -c
hello.o   목적 파일 (기계어 + 심볼 정보)
  ↓ 링크     gcc
hello     실행 파일
```

### 1단계: 전처리 (.c → .i)
```sh
gcc -E hello.c -o hello.i
```
`#include`는 헤더 파일의 내용을 그 자리에 그대로 붙여 넣고, `#define`으로 정의한 매크로는 글자 그대로 치환한다. `hello.i`를 열어 보면 `stdio.h`에서 온 수백 줄의 선언 뒤에 다음 코드가 남아 있다.
```c
int main(void) {
    puts("Hello, linker!");
    return 0;
}
```

### 2단계: 컴파일 (.i → .s)
```sh
gcc -S -O1 -masm=intel hello.i -o hello.s
```
C 코드가 어셈블리로 바뀐다. 핵심 부분만 추리면 다음과 같다(GNU 어셈블러 문법이라 주석은 `#`로 시작한다).
```asm
.LC0:
    .string "Hello, linker!"
main:
    sub   rsp, 8
    lea   rdi, .LC0[rip]   # 첫 번째 인자(rdi) = 문자열 주소
    call  puts@PLT         # 외부 함수 puts 호출
    mov   eax, 0           # 반환값(rax) = 0
    add   rsp, 8
    ret
```

여기서 `puts`는 우리 코드 어디에도 없는 함수다. 컴파일러는 "puts라는 함수가 어딘가에 있을 것"이라고 기록만 해 두고 넘어간다. 실제 주소는 아직 아무도 모른다.

### 3단계: 어셈블 (.s → .o)
```sh
gcc -c hello.s -o hello.o
nm hello.o
```
```text
0000000000000000 r .LC0
0000000000000000 T main
                 U puts
```
어셈블러가 어셈블리를 기계어로 바꿔 **목적 파일**(object file)을 만든다. 목적 파일에는 기계어와 함께 **심볼 테이블**이 들어 있다. `nm` 출력에서 `T`는 "이 파일 안에 정의된 코드", `r`은 "이 파일 안의 읽기 전용 데이터"(여기서는 문자열 상수 `.LC0`, 소문자는 파일 밖에서 보이지 않는 지역 심볼), `U`는 "정의되지 않음(undefined), 다른 곳에서 찾아야 함"을 뜻한다. 이 시점의 `hello.o`는 `puts`가 어디 있는지 모르므로 혼자서는 실행할 수 없다.

### 4단계: 링크 (.o → 실행 파일)
```sh
gcc hello.o -o hello
./hello
```
```text
Hello, linker!
```
**링커**(`ld`)는 여러 목적 파일과 라이브러리를 하나로 합치고, `U`로 남아 있던 심볼을 실제 정의와 연결한다. `puts`는 C 표준 라이브러리(libc)에 들어 있으므로 링커가 libc와 연결해 준다. 이때 gcc는 `main`을 호출해 주는 프로그램 시작 코드(`_start` 등)도 함께 붙인다.

## 링커가 하는 일
### 심볼 해석
각 목적 파일이 "정의한 심볼"과 "필요한 심볼"을 짝지어 본다. 끝까지 정의를 찾지 못하면 그 유명한 오류가 난다.
```c
// main.c
void greet(void);   // 선언만 있고 정의는 없다

int main(void) {
    greet();
    return 0;
}
```
```text
$ gcc main.c -o main
/usr/bin/ld: /tmp/cc….o: in function `main':
main.c:(.text+0x…): undefined reference to `greet'
collect2: error: ld returned 1 exit status
```
이 오류는 **컴파일은 성공했지만 링크에서 실패**한 것이다. 선언 덕분에 컴파일러는 통과시켰지만, 링커가 `greet`의 실제 코드를 어디에서도 찾지 못했다. 정의가 들어 있는 파일을 함께 넘기면(`gcc main.c greet.c -o main`) 해결된다. 오류 메시지에 `ld`가 보이면 링크 단계의 문제라고 기억해 두자.

### 재배치
목적 파일 안의 주소는 0부터 시작하는 임시 주소다. 링커는 모든 조각을 최종 위치에 배치한 뒤, 함수 호출과 변수 접근에 들어갈 실제 주소를 채워 넣는다. 이 작업을 **재배치**(relocation)라고 한다.

### 섹션 합치기
각 파일의 코드(`.text`), 읽기 전용 데이터(`.rodata`), 초기화된 데이터(`.data`)를 같은 종류끼리 모아 실행 파일 형식에 맞게 배치한다. 리눅스는 ELF, 윈도우는 PE, macOS는 Mach-O 형식을 쓴다.

## 정적 링크와 동적 링크
| 항목 | 정적 링크 | 동적 링크 |
|---|---|---|
| 라이브러리 코드 위치 | 실행 파일 안에 복사된다 | 실행할 때 공유 라이브러리(.so, .dll)에서 불러온다 |
| 실행 파일 크기 | 크다 | 작다 |
| 배포 | 파일 하나로 끝난다 | 대상 시스템에 맞는 라이브러리가 있어야 한다 |
| 라이브러리 보안 패치 | 다시 빌드해야 반영된다 | 라이브러리만 교체하면 반영된다 |

리눅스의 gcc는 기본적으로 동적 링크를 한다. `ldd`로 실행 파일이 의존하는 공유 라이브러리를 볼 수 있다.
```text
$ ldd ./hello
	linux-vdso.so.1 (0x…)
	libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x…)
	/lib64/ld-linux-x86-64.so.2 (0x…)
```
마지막 줄의 `ld-linux-x86-64.so.2`가 **동적 로더**다. 프로그램을 실행하면 동적 로더가 libc를 메모리에 올리고 `puts`의 실제 주소를 연결한다. 2단계 어셈블리에 있던 `puts@PLT`가 바로 이 연결에 쓰이는 장치(PLT, Procedure Linkage Table)다. 반대로 `gcc -static hello.o -o hello-static`으로 정적 링크하면 libc 코드가 실행 파일 안으로 들어가 파일 크기가 수십 배로 커진다(환경에 따라 다르다).

## 정리
- 어셈블리는 기계어를 사람이 읽을 수 있게 옮긴 것으로, CPU의 명령어 집합마다 다르다.
- `gcc` 한 번은 전처리 → 컴파일 → 어셈블 → 링크의 네 단계로 이루어진다.
- 목적 파일은 "아직 외부 주소가 비어 있는 기계어"이고, 링커가 심볼을 연결하고 주소를 채워 실행 파일을 만든다.
- "undefined reference"는 컴파일이 아니라 링크 단계의 오류다.
