## 같은 계산, 여러 얼굴

위로 갈수록 기계의 사정(레지스터, 점프 주소)이 사라지고 사람의 생각(반복, 재귀, 문장, "범위의 합")이 드러난다. 아래에서 그 층이 하나씩 생긴 순서를 따라간다.

## 포트란(1957): 수식을 그대로 쓰기
1950년대 초 프로그래밍은 기계어나 어셈블리로 했고, 프로그램을 짜고 고치는 사람의 시간이 큰 비용이 되었다. IBM의 존 배커스 팀이 만든 포트란(FORTRAN, FORmula TRANslation)은 `ISUM = ISUM + I` 같은 수식과 `DO` 반복문을 그대로 쓰게 했고, 첫 컴파일러는 1957년 4월 IBM 704 사용자에게 전달되었다. 당시 개발자들은 컴파일러가 만든 코드가 손으로 짠 것보다 느릴 것이라 의심했으므로 포트란 팀은 최적화에 공을 들였다. 수식을 트리로 읽어 명령어로 바꾸는 일은 9편에서 직접 해 보았다.

## 리스프(1958): 기호, 재귀, 자동 메모리 관리
MIT의 존 매카시는 1958년 인공지능 연구를 위해 리스프(LISP)를 시작했고, 1960년 「Recursive Functions of Symbolic Expressions and Their Computation by Machine, Part I」로 발표했다. 숫자 대신 기호의 리스트를 다루고, 반복 대신 재귀로 생각하며, 함수를 값처럼 넘긴다. 더 큰 유산은 **가비지 컬렉션**(garbage collection)이다. 리스트를 마음대로 만들고 버리게 하려면 더 이상 닿을 수 없는 메모리를 시스템이 알아서 회수해야 했다. 파이썬은 참조 횟수와 순환 수집기를 함께 쓴다.
```python
import gc, weakref

class Node: pass
a, b = Node(), Node()
a.other, b.other = b, a               # 서로를 가리키는 순환
probe = weakref.ref(a)
del a, b                              # 이름은 사라졌지만 서로 참조 중
print("del 직후 살아 있나:", probe() is not None)
print("gc.collect() 회수:", gc.collect())
print("collect 후 살아 있나:", probe() is not None)
```
```text
del 직후 살아 있나: True
gc.collect() 회수: 2
collect 후 살아 있나: False
```
두 객체는 이름이 사라진 뒤에도 서로를 가리켜 참조 횟수가 0이 되지 않는다. 순환 수집기가 "프로그램에서 닿을 수 없다"는 것을 알아내 두 객체를 회수했다. 프로그래머는 `free`를 부르지 않는 대신 수집기가 쓰는 CPU 시간과 여유 메모리를 낸다. 언어 기초 8편의 JVM 세대별 GC가 같은 거래를 더 정교하게 한다.

## 코볼(1959): 사무 처리를 영어처럼
1959년 5월 미국 국방부가 펜타곤에서 연 회의에서 제조사·사용자·학계가 모인 CODASYL 위원회가 생겼고, 이듬해 1960년 코볼(COBOL, COmmon Business-Oriented Language)의 첫 명세가 나왔다. 그레이스 호퍼의 FLOW-MATIC에게서 긴 영어 변수 이름, 영어 단어 명령, 데이터 기술과 처리 절차의 분리를 물려받았다. `ADD I TO TOTAL.`처럼 관리자도 읽을 수 있는 코드를 지향했고, 서로 다른 제조사의 기계에서 같은 프로그램이 도는 것을 목표로 했다.

## C와 구조적 프로그래밍
1968년 3월 에츠허르 데이크스트라는 Communications of the ACM에 「Go To Statement Considered Harmful」을 실어, `goto`가 많을수록 프로그램의 흐름을 따라가기 어렵다고 주장했다. 순차·선택·반복과 블록만으로 짜자는 **구조적 프로그래밍**이 여기서 힘을 얻었다. `while`도 결국 9편의 컴파일러가 `JZ`와 `JMP`로 바꾸지만, 사람은 점프를 보지 않게 되었다. 벨 연구소의 데니스 리치가 1972년 무렵 유닉스를 쓰려고 만든 C는 구조적 제어문과 포인터, 기계에 가까운 정수 타입을 함께 가졌다(리치 자신은 C가 1969~1973년에 걸쳐 생겼다고 적었다). 1973년 유닉스 커널이 C로 다시 쓰이면서(10편) 운영체제도 다른 기계로 옮길 수 있는 코드가 되었다.

## 객체 지향
노르웨이 컴퓨팅 센터의 올레요한 달과 크리스텐 뉘고르는 시뮬레이션 언어 Simula I에 이어 Simula 67에서 클래스, 객체, 상속을 도입했고, 이 두 언어로 2001년 튜링상을 받았다. 데이터와 그것을 다루는 함수를 한 단위로 묶어 내부를 숨기고(캡슐화), 공통 부분을 물려받아 재사용하는 방식은 C++, 1995년 공개된 자바(언어 기초 8편), 파이썬으로 이어졌다. 기계는 메서드를 찾는 간접 호출을 치르고, 사람은 큰 프로그램을 나눠 생각할 단위를 얻었다.

## 인터프리터, VM, 그리고 파이썬
1991년 귀도 반 로섬이 공개한 파이썬은 기계어로 컴파일하지 않는다. CPython은 소스를 바이트코드로 바꾸고 C로 짠 가상 머신이 그것을 하나씩 해석한다(언어 기초 3편). 같은 합을 파이썬으로 쓰고 무엇이 실행되는지 세어 보자.
```python
import dis, sys

def total():
    s = 0
    for i in range(1, 11):
        s += i
    return s

print("\n".join(f"{i.opname} {i.argrepr}".strip()
                 for i in dis.get_instructions(total) if i.offset >= 38))
count = 0
def tracer(frame, event, arg):          # 바이트코드 하나마다 불린다
    global count
    if frame.f_code is total.__code__:
        frame.f_trace_opcodes = True
        count += event == "opcode"
    return tracer
sys.settrace(tracer); result = total(); sys.settrace(None)
print(sys.version.split()[0], "결과", result, "실행한 바이트코드", count)
```
```text
FOR_ITER to 54
STORE_FAST i
LOAD_FAST s
LOAD_FAST i
BINARY_OP +=
STORE_FAST s
JUMP_BACKWARD to 38
LOAD_FAST s
RETURN_VALUE
3.11.15 결과 55 실행한 바이트코드 81
```
반복 한 번이 바이트코드 7개이고 전체로 81개를 실행했다(바이트코드는 파이썬 버전마다 다르다). 토이 CPU의 기계어로는 34개 명령이면 되었다. 게다가 `BINARY_OP` 하나도 피연산자의 타입을 확인하고 알맞은 덧셈 함수를 찾아 부르는 C 코드를 거친다. 대신 사람은 타입 선언도, 빌드도 없이 한 줄씩 실행해 보며 생각을 바로 확인한다. 이 느림을 다시 메우려고 자주 도는 코드를 실행 중에 기계어로 바꾸는 JIT가 나왔다(언어 기초 3·8편).

## 패키지 생태계
마지막 층은 언어 밖에 있다. 1995년 10월 문을 연 펄의 CPAN, 2010년 1월 처음 나온 Node.js의 npm, 파이썬의 PyPI 같은 저장소 덕분에 `pip install` 한 줄로 남이 만든 큰 라이브러리를 가져온다. 재사용의 단위가 서브루틴에서 라이브러리를 거쳐 버전이 붙은 패키지가 되었고, 대가로 의존성 충돌과 공급망 보안이라는 새 문제가 생겼다(언어 기초 7편의 SemVer 범위).

## 매 단계의 거래
| 단계 | 사람이 얻은 것 | 기계·생태계가 치른 것 |
|---|---|---|
| 어셈블리 | 이름과 레이블 | 거의 없음 |
| 포트란·C | 수식, 제어문, 이식성 | 컴파일 시간, 최적화 부담 |
| 리스프·GC | 자동 메모리 관리 | 수집 시간, 여유 메모리 |
| 객체 지향 | 캡슐화, 재사용 | 간접 호출 |
| 파이썬·VM | 동적 타입, 즉시 실행 | 해석 비용(바이트코드 81개) |
| 패키지 | 남의 코드 한 줄 설치 | 의존성 관리 |

거래가 대체로 이득이었던 것은 기계의 시간은 무어의 법칙(1편)과 7편의 기술로 꾸준히 싸졌지만 사람의 시간은 그렇지 않았기 때문이다. 그래서 성능이 정말 중요한 곳(운영체제, 데이터베이스, GPU 커널)에는 여전히 C·C++·러스트가 남고, 그 위에 파이썬 같은 언어가 얹히는 이중 구조가 흔하다. 딥러닝 프레임워크가 파이썬으로 모델을 쓰게 하고 실제 행렬 곱은 C++·CUDA 커널이 하는 것이 대표적이다.

## 이 층의 변환
```text
입력: 수식·재귀·객체로 쓴 프로그램
출력: 기계어, 또는 바이트코드 + VM
보존: 언어 명세가 정한 프로그램의 의미
숨김: 레지스터, 주소, 메모리 해제
```
새 층이 설 때마다 그 아래에는 컴파일러나 런타임이라는 변환기가 하나씩 추가되었다. 언어 명세가 각 구문의 의미를 정하고 컴파일러·인터프리터·GC가 그 의미를 기계어 수준에서 지키므로, 사람은 아래 층을 모른 채 위 층의 언어로만 생각할 수 있다. 숨긴 것의 비용은 사라지지 않고 실행 시간과 메모리로 옮겨 갈 뿐이다.

## 어디에 쓰이나
- 언어 기초 3편 「인터프리터 언어: 실행하면서 번역하기」: 이 글의 `dis` 출력이 그 글의 스택 기반 바이트코드 VM이 실제로 해석하는 명령이다.
- 언어 기초 8편 「자바와 JVM: 한 번 작성하면 어디서나 실행」: 리스프에서 시작된 가비지 컬렉션과 JIT가 JVM에서 어떻게 다듬어졌는지 이어서 볼 수 있다.
- 12편 「자연어에서 코드로: 언어 모델이 프로그램을 쓰는 원리」: 사람의 생산성을 위해 추상화를 올려 온 이 흐름의 다음 단계가 자연어로 프로그램을 쓰는 것이다.

## 정리
- 포트란(1957)은 수식, 리스프(1958)는 재귀와 가비지 컬렉션, 코볼(1959)은 영어 같은 사무 처리 코드, C(1972 무렵)는 이식 가능한 시스템 코드를 가져왔다.
- 구조적 프로그래밍과 객체 지향은 점프와 데이터 배치를 숨기고 생각의 단위를 키웠다.
- 파이썬은 1~10의 합에 바이트코드 81개를 쓰지만, 그 비용으로 사람의 시간을 아낀다.
- 각 단계는 기계의 효율을 사람의 생산성과 바꾼 거래이고, 그 거래를 성립시킨 것은 의미를 보존하는 변환기다.
