## 이 글에서 다루는 것
- 실행 시간 = 명령 수 × CPI × 클록 주기

## 실행 시간의 세 인수
```text
실행 시간 = 명령 수 × CPI × 클록 주기
```
명령 수는 프로그램과 ISA, 컴파일러가 정한다. CPI(cycles per instruction, 명령당 평균 클록 수)와 클록 주기는 마이크로아키텍처가 정한다. 6편의 단일 사이클 구현은 CPI가 1이지만 주기가 길었고, 다중 사이클 구현은 주기가 짧은 대신 CPI가 3.7(125 ÷ 34)이었다. 이 글의 기술은 모두 기계어를 그대로 둔 채 뒤의 두 인수를 줄인다.

## 파이프라인
다중 사이클 구현에서 명령 하나가 실행 단계에 있는 동안 인출 회로는 놀고 있다. **파이프라인**(pipeline)은 단계 사이에 레지스터를 두어, 앞 명령이 다음 단계로 넘어가자마자 다음 명령을 그 단계에 들인다. 인출(IF)·해독(ID)·실행(EX)·메모리(ME)·쓰기(WB)의 5단계라면 최대 다섯 명령이 동시에 진행되고, 이상적인 CPI는 1이면서 클록 주기는 한 단계 분량으로 짧다.
```text
cycle  1  2  3  4  5  6  7
ADD    IF ID EX ME WB
ADDI      IF ID EX ME WB
JNZ          IF ID EX ME WB
```

겹쳐 실행하면 두 가지 **해저드**(hazard)가 생긴다.
- **데이터 해저드**: `JNZ`는 바로 앞 `ADDI`가 만든 Z를 읽어야 한다. 값이 WB에서 레지스터에 쓰일 때까지 기다리면 두 클록이 빈다. **전달**(forwarding)은 EX에서 나온 결과를 레지스터를 거치지 않고 다음 명령의 EX 입력으로 바로 넘겨 이 대기를 없앤다.
- **제어 해저드**: `JNZ`가 뛸지는 EX에서야 안다. 그동안 다음 명령 두 개를 이미 인출했으므로, 틀렸다면 그것들을 버리고 다시 인출한다(두 클록 손해). **분기 예측**(branch prediction)은 과거 결과로 다음 결과를 맞힌다. 흔한 방식인 2비트 포화 카운터는 한 번 틀렸다고 바로 뒤집지 않고, 연속으로 틀려야 예측을 바꾼다.

기준 프로그램(1~10 합)이 실제로 실행하는 34개 명령에 이 규칙을 적용해 클록을 세어 보자.
```python
# 기준 프로그램의 명령: (이름, 쓰는 것, 읽는 것). Z 플래그도 레지스터처럼 본다
S = [("LOADI R0,0", "R0", ""), ("LOADI R1,10", "R1", ""),
     ("ADD R0,R1", "R0 Z", "R0 R1"), ("ADDI R1,255", "R1 Z", "R1"),
     ("JNZ 2", "", "Z"), ("OUT R0", "", "R0"), ("HALT", "", "")]
trace = [0, 1] + [2, 3, 4] * 10 + [5, 6]       # 실제 실행 순서 34개

def cycles(forward, predict):
    """5단계(IF ID EX MEM WB) 순차 파이프라인. d = 명령이 ID에 있는 사이클"""
    made, d, after, ctr, miss = {}, 1, 0, 1, 0  # ctr: 2비트 카운터(0~3)
    for k, s in enumerate(trace):
        name, writes, reads = S[s]
        d = max(d + 1, after)
        for x in reads.split():                 # 데이터 해저드
            if x in made:
                d = max(d, made[x] + (1 if forward else 3))
        for x in writes.split():
            made[x] = d
        if name.startswith("JNZ"):              # 제어 해저드
            taken = trace[k + 1] != s + 1
            guess = {"never": False, "2bit": ctr >= 2,
                     "oracle": taken}[predict]
            if guess != taken:                  # EX에서 알고 다시 인출
                miss, after = miss + 1, d + 3
            ctr = min(ctr + 1, 3) if taken else max(ctr - 1, 0)
    return d + 3, miss                          # 마지막 명령의 WB

print("파이프라인 없음:", len(trace) * 5)
for fw, pr in [(True, "oracle"), (False, "never"),
               (True, "never"), (True, "2bit")]:
    c, m = cycles(fw, pr)
    print(f"전달={fw!s:5} 예측={pr:6} → {c}클록, 예측 실패 {m}, CPI {c / 34:.2f}")
```
```text
파이프라인 없음: 170
전달=True  예측=oracle → 38클록, 예측 실패 0, CPI 1.12
전달=False 예측=never  → 78클록, 예측 실패 9, CPI 2.29
전달=True  예측=never  → 56클록, 예측 실패 9, CPI 1.65
전달=True  예측=2bit   → 42클록, 예측 실패 2, CPI 1.24
```

해저드가 없다면(`oracle`은 결과를 미리 아는 가상의 예측기) 34개 명령에 파이프라인을 채우는 4클록을 더한 38클록이다. 전달이 없고 늘 "안 뜀"으로 예측하면 반복마다 데이터 대기와 분기 손해가 겹쳐 78클록이 된다. 전달을 넣으면 56클록, 2비트 카운터를 더하면 첫 번째와 마지막 `JNZ`만 틀려 42클록이다. 파이프라인이 없을 때의 170클록과 같은 기계어, 같은 결과다.

## 메모리 장벽과 캐시
파이프라인이 매 클록 명령을 하나씩 끝내려면 메모리도 매 클록 답해야 한다. 그런데 프로세서는 메모리(DRAM)보다 훨씬 빠르게 빨라졌다. 울프와 매키는 1995년 「Hitting the Memory Wall」에서 두 속도가 모두 지수적으로 좋아지지만 프로세서 쪽 지수가 훨씬 커서, 결국 메모리가 성능을 결정하게 된다고 지적했다. 이것이 **메모리 장벽**(memory wall)이다.

답은 **캐시**(cache)다. 4편의 SRAM으로 만든 작고 빠른 메모리를 CPU 곁에 두고, 최근에 쓴 데이터를 64바이트 같은 **줄**(line) 단위로 복사해 둔다. 1968년 발표된 IBM System/360 모델 85가 흔히 첫 상용 캐시로 꼽힌다. 캐시가 통하는 이유는 프로그램의 **지역성**(locality)이다. 방금 쓴 주소를 곧 다시 쓰고(시간 지역성: 반복문 변수), 방금 쓴 주소 근처를 곧 쓴다(공간 지역성: 배열 순회). 오늘날에는 레지스터 → L1 → L2 → L3 → DRAM으로 갈수록 크고 느려지는 계층을 이룬다.

512×512 int32 행렬을 행 우선과 열 우선으로 한 번씩 훑을 때, 32KiB 8웨이 LRU 캐시의 실패율을 시뮬레이션해 보자.
```python
def miss_rate(order, n=512, line=64, sets=64, ways=8):   # 32KiB, 8웨이
    cache = [[] for _ in range(sets)]    # 집합마다 태그 목록(앞쪽이 오래된 것)
    miss = 0
    for i in range(n):
        for j in range(n):
            r, c = (i, j) if order == "행 우선" else (j, i)
            block = (r * n + c) * 4 // line    # int32 행렬을 행 우선으로 저장
            s, tag = block % sets, block // sets
            if tag in cache[s]:
                cache[s].remove(tag)            # 적중: 최근 사용으로 옮김
            else:
                miss += 1
                if len(cache[s]) == ways:
                    cache[s].pop(0)             # LRU 교체
            cache[s].append(tag)
    return miss / n**2

for order in ("행 우선", "열 우선"):
    m = miss_rate(order)
    amat = 4 + m * 100                  # 가정: 적중 4클록, 실패 벌점 100클록
    print(f"{order}: 실패율 {m:.2%}, 평균 접근 {amat:.2f}클록")
```
```text
행 우선: 실패율 6.25%, 평균 접근 10.25클록
열 우선: 실패율 100.00%, 평균 접근 104.00클록
```

행 우선 순회는 64바이트 줄 하나에 든 원소 16개를 차례로 쓰므로 16번에 한 번만 실패한다(1/16 = 6.25%). 열 우선 순회는 한 걸음이 2,048바이트라 접근마다 다른 줄을 건드린다. 다음 열도 같은 줄을 다시 쓰지만, 한 열의 512줄이 집합 두 개(16줄 자리)에 몰려 서로를 밀어내므로 그때까지 남아 있지 않다. 같은 원소를 같은 횟수만큼 읽는데 메모리 접근 비용이 10배 차이 난다(적중·실패 클록은 설명을 위한 가정값이다). 기계어의 의미에는 없는 차이라서, 성능을 원하면 프로그래머가 메모리 배치를 알아야 한다.

## 데나드 스케일링의 끝과 멀티코어
1974년 로버트 데나드 등은 MOSFET의 길이·전압을 같은 비율로 줄이면 트랜지스터 밀도가 올라가도 단위 면적당 전력은 그대로라는 규칙을 발표했다. 이 **데나드 스케일링**(Dennard scaling) 덕분에 공정이 작아질 때마다 클록도 공짜로 올라갔다. 그런데 문턱 전압과 누설 전류 때문에 전압을 더 내리지 못하게 되자, 업계에서는 이 규칙이 2005~2007년 무렵 깨졌다고 본다. 동적 전력 `P ∝ C·V²·f`로 계산해 보면 차이가 분명하다.
```python
k = 2 ** 0.5                  # 세대마다 길이를 1/√2(약 0.7배)로 줄인다
for g in range(4):
    C, f, area = k**-g, k**g, k**(-2 * g)  # 트랜지스터당 용량·클록·면적
    d = [C * V**2 * f / area for V in (k**-g, 1.0)]  # 전력 밀도 ∝ CV²f/면적
    print(f"{g}세대: 클록 ×{f:.2f}, 전력 밀도",
          f"데나드 {d[0]:.2f} / 전압 고정 {d[1]:.2f}")

def amdahl(p, n):             # p: 병렬화되는 비율, n: 코어 수
    return 1 / ((1 - p) + p / n)

for p in (0.5, 0.9, 0.99):
    print(f"p={p}:", "  ".join(f"{n}코어 ×{amdahl(p, n):.1f}"
                               for n in (2, 8, 64)))
```
```text
0세대: 클록 ×1.00, 전력 밀도 데나드 1.00 / 전압 고정 1.00
1세대: 클록 ×1.41, 전력 밀도 데나드 1.00 / 전압 고정 2.00
2세대: 클록 ×2.00, 전력 밀도 데나드 1.00 / 전압 고정 4.00
3세대: 클록 ×2.83, 전력 밀도 데나드 1.00 / 전압 고정 8.00
p=0.5: 2코어 ×1.3  8코어 ×1.8  64코어 ×2.0
p=0.9: 2코어 ×1.8  8코어 ×4.7  64코어 ×8.8
p=0.99: 2코어 ×2.0  8코어 ×7.5  64코어 ×39.3
```

전압을 못 내리면 클록을 올릴 때마다 전력 밀도가 세대마다 두 배가 되어 열을 감당할 수 없다. 그래서 늘어난 트랜지스터를 클록 대신 코어 수에 쓰기 시작했다. IBM POWER4(2001)가 한 다이에 코어 두 개를 넣었고, 인텔은 2004년 고클록 단일 코어 후속작 Tejas와 4GHz 펜티엄 4 계획을 접고 듀얼 코어로 방향을 틀었으며, 2005년 인텔과 AMD가 데스크톱용 듀얼 코어를 내놓았다.

멀티코어는 하나의 순차 프로그램을 저절로 빠르게 하지 않는다. 소프트웨어가 일을 나눠야 하고, 나눌 수 없는 부분이 상한을 정한다. System/360의 설계자 진 암달이 1967년 발표한 논의에서 이름을 딴 **암달의 법칙**(Amdahl's law)이 그 상한 `1 / ((1 − p) + p/n)`이다. 90%를 병렬화해도 64코어에서 8.8배에 그치고, 아무리 코어를 늘려도 10배를 넘지 못한다.

## SIMD와 GPU
코어를 늘리는 것 말고도, 명령 하나로 데이터 여러 개를 처리하는 방법이 있다. **SIMD**(single instruction, multiple data)는 넓은 레지스터에 값을 여러 개 담아 한 명령으로 함께 계산한다. x86의 SSE는 1999년 펜티엄 III와 함께 128비트 레지스터를 도입해 32비트 실수 4개를 한 번에 더할 수 있게 했다. 6편에서 본 "지우지 않고 더하는" ISA 확장이다. **GPU**는 이 생각을 극단까지 밀어, 단순한 연산 장치를 아주 많이 두고 같은 프로그램을 수많은 데이터에 동시에 돌린다. 엔비디아가 2006년 11월 지포스 8800을 내놓으며 CUDA를 소개한 뒤, GPU는 그래픽이 아닌 일반 계산에도 널리 쓰이게 되었다. 서로 독립인 곱셈-덧셈이 수없이 많은 행렬 곱은 GPU에 딱 맞는 일이고, 오늘날 AI 모델이 GPU 위에서 학습·추론되는 이유다.

## 이 층의 변환
```text
입력: 하나씩 실행하는 순차 의미(ISA)
출력: 겹치고 미리 하고 나눠 하는 실행
보존: 프로그램이 관찰하는 결과
숨김: 파이프라인, 캐시 적중, 예측 실패
```
파이프라인과 캐시는 "하나씩 순서대로 실행한 것과 같은 결과"라는 약속을 지키는 범위에서만 순서를 바꾼다. 해저드 검출과 전달, 예측이 틀렸을 때 결과를 버리는 장치, 캐시와 메모리 내용을 맞추는 장치가 이 약속을 보증하므로 달라지는 것은 시간뿐이다. 반면 멀티코어·GPU의 병렬성은 순차 프로그램 안에 숨길 수 없어서, 소프트웨어가 직접 일을 나누는 새 약속(스레드, CUDA 같은 프로그래밍 모델)이 필요하다.

## 정리
- 실행 시간 = 명령 수 × CPI × 클록 주기이고, 마이크로아키텍처는 기계어를 바꾸지 않고 뒤의 두 인수를 줄인다.
- 기준 프로그램은 파이프라인 없이 170클록, 전달과 2비트 분기 예측을 갖춘 5단계 파이프라인에서 42클록이었다.
- 캐시는 지역성에 기대므로 같은 계산도 접근 순서에 따라 실패율이 6.25%와 100%로 갈린다.
- 데나드 스케일링이 2005~2007년 무렵 끝나면서 성능 향상은 멀티코어·SIMD·GPU의 병렬성으로 옮겨 갔고, 이 병렬성은 소프트웨어가 드러내야 한다.
