# [트랜지스터에서 자연어까지 13/13] AI 에이전트와 자연어 프로그래밍: 명세와 검증의 시대

> **한 줄 요약** — AI 에이전트는 언어 모델의 확률적 코드 생성을 실행·테스트·오류 읽기·수정의 고리로 감싸 성공률을 끌어올리는 시스템이고, 자연어가 추상화 사다리의 맨 위에 올라선 지금 정확성을 지키는 일은 타입 검사기 대신 테스트·명세·리뷰가 맡는다.

## 이 글에서 다루는 것
- 에이전트 루프: 계획 → 작성 → 실행·테스트 → 오류 읽기 → 수정
- 도구 호출(ReAct, Toolformer)과 실제 저장소 과제(SWE-bench)
- 생성-검증 루프가 성공률을 올리는 이유: 파이썬 실험
- 사례: 휴대폰만으로 만든 이 플랫폼
- 자연어가 사다리에서 차지하는 자리와 한계, 시리즈 정리

## 한 번 쓰고 끝내지 않는다
12편의 모델은 명세를 받아 코드를 한 번 내놓았다. 사람 프로그래머는 그렇게 일하지 않는다. 쓰고, 돌리고, 오류 메시지를 읽고, 고친다. **에이전트**(agent)는 이 고리를 언어 모델에게 맡긴 시스템이다. 모델이 다음 행동(파일 읽기, 코드 수정, 명령 실행)을 텍스트로 정하면 바깥 프로그램이 그 행동을 실제로 실행하고, 결과(테스트 출력, 오류 메시지)를 모델의 입력 뒤에 붙인다.
```text
1. 계획: 명세를 읽고 할 일을 나눈다
2. 작성: 코드를 고친다
3. 실행: 테스트와 빌드를 돌린다
4. 관찰: 실패 메시지를 읽는다
5. 수정: 2로 돌아간다 (통과하면 끝)
```
모델은 여전히 다음 토큰을 예측할 뿐이다. 달라진 것은 첫 시도가 틀려도 된다는 점이다. 테스트 결과라는 바깥 세계의 사실이 고리 안으로 들어오기 때문이다.

## 도구 호출: ReAct와 Toolformer
2022년 Yao 등의 ReAct는 모델이 생각(Thought), 행동(Action), 관찰(Observation)을 번갈아 적게 했다. 질의응답 과제 HotpotQA에서 위키백과 API를 검색하게 하자 추론만 이어 가는 방식의 환각과 오류 전파가 줄었고, 가상 가정 환경 ALFWorld와 쇼핑 환경 WebShop에서는 예시 한두 개만으로 모방·강화학습 기반 방법보다 성공률이 각각 34%p, 10%p 높았다. 2023년 메타의 Toolformer는 모델이 도구를 언제 부를지 스스로 배우게 했다. 텍스트 곳곳에 계산기, 질의응답, 검색, 번역, 달력 호출 후보를 넣어 실제로 실행해 보고, 그 결과가 뒤따르는 토큰을 예측하는 데 도움이 된 호출만 남겨 미세 조정한다. 67억 파라미터 GPT-J 기반 모델이 일부 제로샷 과제에서 훨씬 큰 GPT-3를 앞섰다. 코딩 에이전트의 도구는 파일 읽기·검색·편집, 셸 명령, 테스트 실행기다.

## 실제 저장소 과제: SWE-bench
2023년 Jimenez 등의 SWE-bench는 인기 파이썬 저장소 12개의 실제 GitHub 이슈와 그것을 해결한 PR에서 과제 2,294개를 만들었다. 모델은 이슈 설명과 저장소 전체를 받아 패치를 내고, 원래 PR이 고친 테스트가 통과하는지로 채점된다. 논문 당시 가장 좋았던 Claude 2도 1.96%만 풀었다(BM25 검색으로 관련 파일을 골라 준 설정). 2024년의 SWE-agent는 파일 보기·검색·편집 명령을 에이전트용으로 다듬어 GPT-4 Turbo로 12.47%를 풀었고, 같은 해 8월에는 사람이 검토한 500개 부분집합 SWE-bench Verified가 나왔다. 그 뒤 점수는 빠르게 올라 순위표 숫자는 몇 달마다 바뀌므로 여기에는 싣지 않는다. 변하지 않는 점은 채점 방식이다. 12편의 HumanEval처럼 "실행해서 테스트를 통과하는가"다.

## 생성-검증 루프가 성공률을 올리는 이유
명세가 "x를 세 배 하고 1을 더한다"(3x + 1)인 함수를, 아무 생각 없이 무작위 식을 만드는 생성기로 찾아보자. 생성기는 아주 약하지만, 통과할 때까지 만들고 테스트로 거른다. 채점은 x = −10~10의 숨은 테스트 21개로 한다.
```python
import random

def gen(rng, depth=2):                   # 무작위 후보: x, 0~5, (식 연산 식)
    if depth == 0 or rng.random() < 0.3:
        return rng.choice(["x", str(rng.randint(0, 5))])
    op = rng.choice("+-*")
    return f"({gen(rng, depth - 1)} {op} {gen(rng, depth - 1)})"

def passes(expr, tests):
    return all(eval(expr, {"x": x}) == y for x, y in tests)

hidden = [(x, 3 * x + 1) for x in range(-10, 11)]   # 명세: 3x + 1
suites = {"테스트 1개": [(1, 4)], "테스트 2개": [(1, 4), (2, 7)],
          "테스트 4개": [(0, 1), (1, 4), (2, 7), (5, 16)]}

rng = random.Random(0)
cands = [gen(rng) for _ in range(100_000)]
p = sum(passes(c, hidden) for c in cands) / 1e5
print("후보 하나가 정답일 확률:", p, " 1000번 중 하나라도:", f"{1 - (1 - p) ** 1000:.0%}")
print("테스트 2개는 통과, 숨은 테스트는 실패:",
      next(c for c in cands if passes(c, suites["테스트 2개"])
           and not passes(c, hidden)))
print("예산 N별 정답/오답 비율 (N = 1, 10, 100, 1000)")
for name, tests in suites.items():
    row = []
    for budget in (1, 10, 100, 1000):
        rng, ok, wrong = random.Random(1), 0, 0
        for trial in range(300):
            for _ in range(budget):          # 통과할 때까지 생성 → 검증
                cand = gen(rng)
                if passes(cand, tests): break
            else:
                continue                     # 예산 안에 못 찾음
            ok += passes(cand, hidden); wrong += not passes(cand, hidden)
        row.append(f"{ok / 300:.0%}/{wrong / 300:.0%}")
    print(name, "  ".join(row))
```
```text
후보 하나가 정답일 확률: 0.00119  1000번 중 하나라도: 70%
테스트 2개는 통과, 숨은 테스트는 실패: ((x * x) + (3 * 1))
예산 N별 정답/오답 비율 (N = 1, 10, 100, 1000)
테스트 1개 0%/8%  1%/55%  1%/99%  1%/99%
테스트 2개 0%/0%  1%/1%  8%/12%  45%/43%
테스트 4개 0%/0%  1%/0%  8%/0%  68%/0%
```
후보 하나가 맞을 확률은 0.12%뿐이지만, 테스트 4개로 거르며 1000번까지 시도하면 300번 중 68%에서 정답을 찾고 오답은 하나도 통과하지 못한다(이론값 70%). 약한 생성기도 강한 검증기와 묶으면 쓸 만한 시스템이 된다. 12편의 pass@k가 여러 번 뽑을수록 오른 것과 같은 원리다.

반대로 검증기가 약하면 많이 생성할수록 해롭다. 테스트가 `f(1) = 4` 하나뿐이면 통과한 후보의 99%가 오답이고, 두 개여도 `x² + 3`처럼 x = 1, 2에서만 우연히 맞는 식이 절반 가까이 통과한다. 생성기는 명세가 아니라 테스트를 만족시키도록 고르기 때문이다. 2022년 딥마인드의 AlphaCode가 문제마다 아주 많은 후보를 만들고 예제 테스트로 거른 뒤 비슷한 것끼리 묶어 10개만 제출해, 모의 Codeforces 대회에서 평균 상위 54.3%에 든 것도 이 구조다.

## 사례: 휴대폰만으로 만든 이 플랫폼
지금 이 글이 올라가 있는 플랫폼(포스트·좋아요·댓글)은 개발자가 로컬 브라우저나 터미널 없이 휴대폰의 Claude 앱과 클라우드 세션만으로 만들고 있다. 사람은 자연어로 요청하고, Claude가 클라우드 컨테이너에서 코드를 고치고 검사를 돌린다. 사람이 직접 실행해 볼 수 없으므로 "휴대폰에서 볼 수 있는 증거를 만든다"가 규칙이다. 그 규칙과 아키텍처 제약을 적은 저장소의 CLAUDE.md가 에이전트에게 주는 자연어 명세다.
```text
휴대폰의 요청 (자연어)
  ↓
계획 → 코드 수정
  ↓
npm run verify ← 실패하면 다시 수정
  ↓
npm run e2e (실제 Chromium)
  ↓
npm run shots → 스크린샷 전송
  ↓
push → CI 통과 → PR 병합
```
`npm run verify`는 의존 규칙 검사(패키지는 자기보다 낮은 계층에만 의존하고 import에 순환이 없어야 한다), 타입 검사, 단위·통합 테스트, 빌드를 차례로 돌린다. `npm run e2e`는 컨테이너에 미리 설치된 Chromium으로 Playwright를 돌려, 실서버를 데스크톱·모바일 화면으로, 서버 없이 브라우저 안에서 API가 도는 데모를 모바일 화면으로 같은 시나리오에 따라 검사한다. `npm run shots`가 주요 화면을 PNG로 저장하면 Claude가 직접 열어 확인한 뒤 사용자에게 보낸다. push하면 GitHub Actions가 같은 검사를 다시 돌리고, Claude는 결과와 로그를 확인한 뒤에야 PR을 병합한다. 실패를 "가끔 나는 오류"로 넘기지 않고 재현, 원인 수정, 같은 검사 통과까지 확인하는 것도 규칙이다. 실서버의 SQLite 저장소와 데모의 메모리 저장소는 같은 계약 테스트를 통과해야 하므로 두 구현의 동작이 어긋나지 않는다. 이 시리즈의 글도 같은 방식으로 실렸다. 코드 예제는 실제로 실행한 출력을 붙였고, 저장소의 예시 포스트 테스트가 제목 형식과 필수 섹션, 강조 표기 실수를 검사한다.

## 자연어는 사다리의 어디에 서나
```text
자연어 명세 (12·13편)
  ↓ 언어 모델 + 테스트로 거르기
고수준 언어 (11편)
  ↓ 컴파일러 (9편)
어셈블리 (8편)
  ↓ 어셈블러
기계어와 ISA (6편)
  ↓ CPU: 인출·해독·실행 (5·7편)
레지스터·ALU·메모리 (3·4편)
  ↓ 조합·순차 회로
논리 게이트 (2편)
  ↓ CMOS 배치
트랜지스터와 전압 (1편)
```
운영체제(10편)는 이 사다리 옆에서 기계를 여러 프로그램에 나눠 준다. 사다리의 각 단에는 아래 층의 의미를 보존하는 변환기와 그것을 확인하는 수단이 있었다.

| 층 | 변환기 | 정확성을 지키는 것 |
|---|---|---|
| 게이트·회로 | 트랜지스터 배치 | 진리표 전수 검사 |
| 기계어 | CPU | ISA 명세 |
| 고수준 언어 | 컴파일러 | 언어 명세, 타입 검사 |
| 자연어 | 언어 모델 | 테스트, 명세, 리뷰 |

맨 위 칸만 성격이 다르다. 자연어는 모호하고(12편의 중복 제거), 모델의 출력은 같은 요청에도 매번 다르다. 그래서 테스트·명세·리뷰가 이 층의 새 "타입 검사기"가 된다. 다만 타입 검사는 증명이고 테스트는 표본이다. 타입 검사를 통과하면 그 종류의 오류는 어떤 입력에서도 없지만, 테스트는 시험한 입력에서만 맞다는 것을 말해 준다. 위 실험의 `x² + 3`이 그 차이다. 자연어가 아래 층을 없앤 것도 아니다. 에이전트가 쓴 파이썬도 결국 바이트코드와 기계어, 게이트와 트랜지스터 위에서 돈다.

## 이 층의 변환
```text
입력: 자연어 요청, 저장소, 검사 도구
출력: 테스트와 CI를 통과한 코드 변경
보존: 테스트·명세로 적어 둔 만큼의 의도
숨김: 시행착오, 중간 오류, 구현 세부
```
아래 층들의 변환은 규칙이 의미 보존을 보장했지만, 이 층의 생성기는 확률적이라 그런 보장이 없다. 대신 실행이라는 바깥의 사실로 후보를 거르기 때문에 검증기가 강할수록 결과를 믿을 수 있다. 결국 보존되는 의도의 범위는 사람이 테스트와 명세로 얼마나 정확히 적었는가로 정해진다.

## 정리
- 에이전트는 모델이 정한 행동을 실행하고 그 결과를 다시 읽게 하는 고리로, 첫 시도가 틀려도 테스트가 방향을 잡아 준다.
- ReAct와 Toolformer는 도구 호출을, SWE-bench는 실제 저장소에서 테스트로 채점하는 과제를 보여 주었다.
- 약한 생성기도 강한 검증기와 묶으면 성공률이 0.12%에서 68%로 오르지만, 약한 테스트는 오답을 통과시킨다.
- 자연어는 추상화 사다리의 맨 위에 있지만 모호하고 비결정적이어서, 테스트·명세·리뷰가 새 타입 검사기 역할을 한다.
