# [트랜지스터에서 자연어까지 6/13] 명령어 집합: 하드웨어와 소프트웨어의 약속

> **한 줄 요약** — 명령어 집합 구조(ISA)는 "이 비트열을 실행하면 상태가 이렇게 바뀐다"는 하드웨어와 소프트웨어 사이의 계약이고, 계약만 지키면 그 아래 회로는 얼마든지 달라질 수 있어서 같은 기계어가 수십 년 동안 서로 다른 칩에서 돈다.

## 이 글에서 다루는 것
- ISA와 마이크로아키텍처: 무엇을 약속하고 무엇을 숨기나

- 명령어 인코딩: 토이 ISA의 비트 필드와 실제 RISC-V `addi`
- RISC와 CISC, x86·ARM·RISC-V의 역사
- 호환성이 수십 년 유지되는 이유

## ISA는 계약이다
5편의 CPU에 프로그램을 쓰려면 무엇을 알아야 할까? 레지스터가 몇 개이고 몇 비트인지, 어떤 명령이 있고 각각 상태를 어떻게 바꾸는지, 명령이 어떤 비트열로 쓰이는지, 메모리 주소를 어떻게 매기는지다. 이것을 모은 명세가 **명령어 집합 구조**(ISA, instruction set architecture)다. 반대로 명령 하나에 몇 클록이 걸리는지, ALU가 몇 개인지, 캐시가 얼마나 큰지는 몰라도 된다. 이쪽은 **마이크로아키텍처**(microarchitecture), 즉 ISA를 구현한 회로의 몫이다. 실제 ISA는 여기에 예외·인터럽트와 권한 수준 같은 운영체제용 약속도 담는다(10편).

이 구분을 제품 전략의 중심에 둔 것이 1964년 4월 7일 발표된 IBM System/360이다. 작은 기종부터 큰 기종까지 회로는 다르지만 같은 ISA를 구현하는 컴퓨터 가족을 한꺼번에 내놓았고, 고객은 소프트웨어를 다시 쓰지 않고 더 큰 기종으로 옮겨 갈 수 있었다. 진 암달이 수석 설계자, 프레드 브룩스가 프로젝트 관리자였다. 기종마다 다른 회로로 같은 명령을 구현하는 데에는 5편 끝에서 본 마이크로프로그래밍이 큰 역할을 했다. 이 약속은 지금도 이어져서, 오늘날의 IBM Z 메인프레임도 일부 제약은 있지만 응용 프로그램 수준의 호환성을 유지한다.

## 같은 기계어, 다른 구현
토이 ISA를 다시 정의하고, 명령의 의미는 하나로 두되 걸리는 클록 수만 다른 두 구현을 돌려 보자. 단일 사이클 구현은 모든 명령을 1클록에 끝낸다. 다중 사이클 구현은 인출·해독·실행·메모리·쓰기를 단계마다 한 클록씩 쓰는데, 단계 수는 교과서의 다중 사이클 설계에서 흔히 쓰는 값(분기 3, 대부분 4, 메모리 읽기 5)을 빌렸다.
```python
OPS = ["HALT", "LOADI", "ADD", "SUB", "ADDI", "LOAD", "STORE",
       "JMP", "JZ", "JNZ", "OUT"]

def enc(op, rd=0, rs=0, imm=0):          # op 4 · rd 2 · rs 2 · imm 8비트
    return OPS.index(op) << 12 | rd << 10 | rs << 8 | imm & 0xFF

def fields(w):
    return OPS[w >> 12], (w >> 10) & 3, (w >> 8) & 3, w & 0xFF

w = enc("ADDI", rd=1, imm=-1)            # −1은 8비트로 255
b = f"{w:016b}"
print(f"{w:04X} = {b[:4]} {b[4:6]} {b[6:8]} {b[8:]}", fields(w))

def run(prog, cycles_of):               # 명령의 의미(ISA)는 하나, 걸리는 클록은 구현마다
    R, mem, pc, z, out, clk = [0] * 4, [0] * 256, 0, False, [], 0
    while True:
        op, rd, rs, imm = fields(prog[pc])
        pc += 1
        clk += cycles_of(op)
        if op == "HALT": return out, R, clk
        if op == "LOADI": R[rd] = imm
        if op in ("ADD", "SUB", "ADDI"):
            b = imm if op == "ADDI" else R[rs]
            R[rd] = (R[rd] + (-b if op == "SUB" else b)) & 0xFF
            z = R[rd] == 0
        if op == "LOAD": R[rd] = mem[imm]
        if op == "STORE": mem[imm] = R[rd]
        if op == "OUT": out.append(R[rd])
        if (op == "JMP" or (op == "JZ" and z)
                or (op == "JNZ" and not z)): pc = imm

prog = [enc("LOADI", 0, 0, 0), enc("LOADI", 1, 0, 10), enc("ADD", 0, 1),
        enc("ADDI", 1, 0, 255), enc("JNZ", imm=2), enc("OUT", 0), enc("HALT")]
print(" ".join(f"{w:04X}" for w in prog))
single = lambda op: 1                    # 단일 사이클: 모든 명령이 1클록
multi = lambda op: {"JMP": 3, "JZ": 3, "JNZ": 3, "HALT": 3,
                    "LOAD": 5}.get(op, 4)  # 다중 사이클: 단계 수만큼
print("단일 사이클:", run(prog, single))
print("다중 사이클:", run(prog, multi))
```
```text
44FF = 0100 01 00 11111111 ('ADDI', 1, 0, 255)
1000 140A 2100 44FF 9002 A000 0000
단일 사이클: ([55], [55, 0, 0, 0], 34)
다중 사이클: ([55], [55, 0, 0, 0], 125)
```

두 구현은 같은 기계어를 받아 같은 출력과 같은 최종 레지스터를 내지만 클록 수는 34와 125로 다르다. 그렇다고 다중 사이클이 느리다는 뜻은 아니다. 단일 사이클 구현은 가장 느린 명령에 맞춘 긴 클록 주기를 써야 하고, 다중 사이클 구현은 한 단계에 맞춘 짧은 주기를 쓴다. 실행 시간은 클록 수 × 클록 주기라서 어느 쪽이 빠른지는 회로를 봐야 안다. 중요한 것은 프로그램이 이 차이를 전혀 알 필요가 없다는 점이다. 그것이 계약의 뜻이다.

## 명령어 인코딩
ISA는 명령을 비트로 어떻게 쓰는지도 정한다. 토이 ISA와 RISC-V의 I형(즉치 연산) 형식을 나란히 놓으면 이렇다.
```text
toy ISA (16 bit)
┌───────┬─────┬─────┬───────────┐
│   op  │  rd │  rs │    imm8   │
└───────┴─────┴─────┴───────────┘
 15   12 11 10 9   8 7         0

RISC-V I-type (32 bit)
┌─────────┬─────┬─────┬─────┬───────┐
│imm[11:0]│ rs1 │  f3 │  rd │ opcode│
└─────────┴─────┴─────┴─────┴───────┘
 31     20 19 15 14 12 11  7 6     0
```

토이 ISA는 16비트를 네 필드가 나눠 쓴다. opcode 4비트라 명령은 최대 16종(지금 11종을 쓰고 5개가 남는다), 레지스터 필드 2비트라 레지스터는 4개, imm 8비트라 점프 주소와 데이터 주소가 모두 0~255다. 필드끼리 정해진 비트를 나눠 갖기 때문에 레지스터를 늘리면 즉치가 줄어드는 식의 절충이 생긴다. 앞 절 출력의 첫 줄이 `ADDI R1, 255`를 필드별로 끊어 보인 것이다.

RISC-V는 32비트 명령에 5비트 레지스터 필드(레지스터 32개)와 12비트 부호 있는 즉치를 둔다. opcode 7비트와 funct3(f3) 3비트가 함께 연산을 고른다. 레지스터 필드가 형식이 달라도 같은 위치에 있어서, 해독기는 명령 종류를 다 알기 전에 레지스터를 읽기 시작할 수 있다. 함수 앞부분에서 스택을 16바이트 늘리는 `addi sp, sp, -16`을 직접 만들어 보자.
```python
X = {"zero": 0, "ra": 1, "sp": 2, "a0": 10}     # ABI 이름 → 레지스터 번호

def addi(rd, rs1, imm):      # I형: imm[11:0] · rs1 · funct3 · rd · opcode
    assert -2048 <= imm <= 2047                  # 12비트 부호 있는 즉치
    return ((imm & 0xFFF) << 20 | X[rs1] << 15 | 0b000 << 12
            | X[rd] << 7 | 0b0010011)            # OP-IMM, funct3 = ADDI

w = addi("sp", "sp", -16)
b = f"{w:032b}"
print(f"{w:08x}", w == 0xFF010113, addi("sp", "sp", 16) == 0x01010113)
print(b[:12], b[12:17], b[17:20], b[20:25], b[25:])
print("nop =", f"{addi('zero', 'zero', 0):08x}",
      " li a0, 55 =", f"{addi('a0', 'zero', 55):08x}")
print("메모리 바이트:", w.to_bytes(4, "little").hex(" "))
```
```text
ff010113 True True
111111110000 00010 000 00010 0010011
nop = 00000013  li a0, 55 = 03700513
메모리 바이트: 13 01 01 ff
```

비교한 값 `ff010113`과 `01010113`은 GNU binutils의 RISC-V 테스트에 들어 있는 objdump 출력에서 `addi sp,sp,-16`, `addi sp,sp,16`으로 표시되는 워드다. −16은 12비트 2의 보수로 `111111110000`이 되고, sp는 x2라 `00010`이 두 번 나온다. `nop`과 `li`는 별도 명령이 아니라 `addi`에 붙인 별명(의사 명령)이고, objdump도 `addi a0, zero, 55`를 `li a0,55`로 보여 준다. 이런 별명은 8편의 어셈블러가 처리한다. RISC-V는 보통 리틀 엔디언이라 메모리에는 낮은 바이트 `13`부터 놓인다.

x86은 사정이 다르다. 언어 기초 6편에서 본 `mov eax, 55`는 `b8 37 00 00 00` 5바이트, `ret`는 `c3` 1바이트이고, x86 명령은 접두사와 피연산자에 따라 최대 15바이트까지 길어진다. 해독기는 명령의 길이부터 알아내야 다음 명령이 어디서 시작하는지 안다.

## RISC와 CISC
| 항목 | RISC | CISC |
|---|---|---|
| 명령 길이 | 고정(RISC-V 기본 32비트) | 가변(x86 최대 15바이트) |
| 메모리 접근 | load·store 명령만 | 연산 명령이 메모리를 직접 읽고 씀 |
| 해독 | 필드 위치가 고정이라 단순 | 길이와 형식부터 알아내야 함 |
| 예 | ARM, RISC-V, MIPS | x86, VAX |

RISC(reduced instruction set computer)라는 생각은 1970~80년대에 나왔다. IBM에서는 존 코크가 1975년 무렵 801 프로젝트를 시작했고, UC 버클리에서는 데이비드 패터슨 팀이 1980년 RISC 프로젝트를 시작해 이 이름을 붙였으며 첫 칩 RISC-I은 1981~82년에 나왔다. 스탠퍼드에서는 존 헤네시 팀이 1981년 MIPS 프로젝트를 시작했다. 근거는 기계어를 이제 사람보다 컴파일러가 주로 쓰고, 컴파일러는 단순한 명령을 주로 쓰며, 형식이 단순하고 고정되면 7편의 파이프라인을 만들기 쉽다는 것이었다. 지금은 경계가 흐려졌다. 현대 x86 프로세서는 내부에서 명령을 단순한 마이크로 연산(micro-op)으로 쪼개 실행하고, ARM과 RISC-V도 명령 수가 많이 늘었다.

## x86, ARM, RISC-V
- **x86**: 1978년 6월 인텔 8086(16비트)에서 시작했다. 1981년 IBM PC가 그 변형인 8088을 쓰면서 널리 퍼졌다. 1999년 AMD가 64비트 확장 AMD64(x86-64)를 발표했고 첫 제품 옵테론은 2003년 4월에 나왔다. 인텔과 AMD가 따로 설계한 칩이 같은 x86-64 기계어를 실행한다.
- **ARM**: 영국 에이콘 컴퓨터에서 소피 윌슨이 명령어 집합을, 스티브 퍼버가 하드웨어 구조를 맡았고, 첫 칩 ARM1이 1985년 4월 26일 처음 동작했다. 1990년 11월 에이콘·애플·VLSI 테크놀로지의 합작사 Advanced RISC Machines가 세워졌고, ISA와 코어 설계를 다른 회사에 라이선스하는 방식으로 퍼졌다.
- **RISC-V**: 2010년 5월 UC 버클리의 크르스테 아사노비치(Krste Asanović) 교수와 대학원생 Yunsup Lee, Andrew Waterman이 연구용으로 시작했다. 상용 ISA는 마음대로 고치거나 결과를 공유할 수 없었기 때문이다. 2011년 첫 기술 보고서, 2015년 RISC-V 재단(지금의 RISC-V International) 설립을 거쳐, 2019년 12월판 명세에는 기본 정수 ISA RV32I 2.1이 비준(ratified) 상태로 실려 있다. 누구나 명세를 보고 구현할 수 있는 개방형 표준이다.

## 호환성이 수십 년 유지되는 이유
- **소프트웨어가 칩보다 비싸다**: 이미 배포된 기계어 프로그램, 운영체제, 컴파일러, 라이브러리가 모두 ISA에 묶여 있다. 칩을 바꾸는 비용보다 이것들을 다시 만드는 비용이 훨씬 크다.
- **지우지 않고 더한다**: 새 기능은 확장으로 붙인다. AMD64는 64비트 운영체제에서도 32비트 프로그램을 그대로 돌리는 호환 모드를 두었다. RISC-V는 처음부터 작은 기본 ISA에 M(곱셈·나눗셈), A(원자적 연산), F·D(부동소수점), C(16비트 압축 명령) 같은 확장을 고르는 구조로 설계되었다.
- **성능은 계약 아래에서 올린다**: 파이프라인·캐시·멀티코어는 ISA를 그대로 둔 채 같은 기계어를 더 빨리 돌린다(7편).
- **대가도 있다**: 오래된 명령과 복잡한 인코딩을 계속 해독해야 한다. 숨김도 완벽하지 않아서, 실행 시간 차이로 캐시 상태를 엿보는 스펙터(Spectre) 같은 공격은 숨겨 둔 마이크로아키텍처가 새어 나온 예다.

## 이 층의 변환
```text
입력: 서로 다른 회로 구현
출력: 하나의 명령어 목록·의미·인코딩
보존: 같은 기계어 → 같은 결과
숨김: 클록 수, 파이프라인, 캐시
```
ISA는 명령마다 "이전 상태 → 다음 상태"만 정하고 걸리는 시간은 정하지 않는다. 그래서 구현은 그 상태 전이를 지키는 한 무엇이든 해도 되고, 위 실험의 두 구현처럼 클록 수가 네 배 가까이 달라도 프로그램에는 같은 기계로 보인다. 이 약속을 보증하는 것은 명세 문서와, 구현이 명세대로 동작하는지 확인하는 테스트 프로그램이다.

## 어디에 쓰이나
- 언어 기초 8편 「자바와 JVM: 한 번 작성하면 어디서나 실행」: JVM 바이트코드는 소프트웨어로 구현하는 ISA이고, "같은 코드, 다른 구현"이라는 계약을 한 층 위에서 반복한다.
- 언어 기초 5편 「컴파일 언어: 실행 전에 번역하기」: 크로스 컴파일에서 `GOARCH=arm64`처럼 고르는 대상이 바로 ISA다.
- 7편 「빠르게 만드는 기술: 파이프라인, 캐시, 병렬성」: ISA를 그대로 두고 마이크로아키텍처만 바꿔 빨라지는 방법을 다룬다.
- 8편 「어셈블러: 기호를 기계어로 바꾸기」: 이 글의 인코딩 규칙을 기계적으로 적용하는 프로그램을 만든다.

## 정리
- ISA는 레지스터, 명령의 의미, 인코딩을 정한 하드웨어와 소프트웨어의 계약이고, 클록 수나 회로 구조는 숨긴다.
- 같은 기계어를 실행한 두 파이썬 구현은 34클록과 125클록으로 달랐지만 결과는 같았다.
- RISC-V `addi sp, sp, -16`을 비트 필드로 조립하면 `ff010113`이 되고, binutils의 objdump 결과와 일치한다.
- IBM System/360(1964)이 시작한 "한 ISA, 여러 구현"이 x86(1978), ARM(1985), RISC-V(2010)까지 이어지며 수십 년 호환성을 만든다.
