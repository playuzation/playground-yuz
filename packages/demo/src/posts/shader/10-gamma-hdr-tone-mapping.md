## 화면의 숫자는 빛의 양이 아니다
텍스처와 프레임 버퍼의 8비트 값 128은 흰색 빛의 절반이 아니다. 대부분의 모니터와 이미지 파일은 **sRGB** 색 공간(IEC 61966-2-1)을 쓰고, 그 전달 함수는 빛의 양 L을 거듭제곱으로 눌러 화면값 V(0~1)에 담는다. 사람 눈은 어두운 쪽의 차이에 민감하므로 같은 8비트를 어두운 쪽에 촘촘히 쓰려는 것이다. 원점 근처만 직선이고 나머지는 2.4제곱인 구간식이다.
```text
디코드 V → L
  V ≤ 0.04045: L = V/12.92
  그 외: L = ((V+0.055)/1.055)^2.4
인코드 L → V
  L ≤ 0.0031308: V = 12.92·L
  그 외: V = 1.055·L^(1/2.4) − 0.055
```
전체 모양이 2.2제곱과 비슷해 흔히 "감마 2.2"라고 부르지만 같은 함수는 아니다. 두 방향을 구현해 확인한다.
```python
def decode(v):                       # sRGB 화면값(0~1) → 선형 빛의 양
    return v / 12.92 if v <= 0.04045 else ((v + 0.055) / 1.055) ** 2.4

def encode(l):                       # 선형 → sRGB 화면값
    return 12.92 * l if l <= 0.0031308 else 1.055 * l ** (1 / 2.4) - 0.055

ok = all(round(encode(decode(c / 255)) * 255) == c for c in range(256))
print("8비트 코드 256개 왕복:", "모두 일치" if ok else "불일치")
for c in (10, 128):
    print(f"코드 {c}의 빛: sRGB {decode(c / 255):.4f}, "
          f"2.2제곱 근사 {(c / 255) ** 2.2:.4f}")
gap = max((abs(round(255 * encode(l)) - round(255 * l ** (1 / 2.2))), l)
          for l in (i / 10 ** 5 for i in range(10 ** 5 + 1)))
print("같은 빛을 2.2 근사로 인코딩하면 최대 차이: %d코드 (빛 %.4f)" % gap)
dark = lambda f: sum(f(c / 255) < 0.01 for c in range(256))
print("빛 1% 미만에 쓰는 코드 수: 선형 8비트", dark(lambda v: v),
      "/ sRGB", dark(decode))
```
```text
8비트 코드 256개 왕복: 모두 일치
코드 10의 빛: sRGB 0.0030, 2.2제곱 근사 0.0008
코드 128의 빛: sRGB 0.2159, 2.2제곱 근사 0.2195
같은 빛을 2.2 근사로 인코딩하면 최대 차이: 9코드 (빛 0.0035)
빛 1% 미만에 쓰는 코드 수: 선형 8비트 3 / sRGB 26
```
중간톤(128)에서는 2.2제곱 근사와 2% 차이지만 코드 10에서는 거의 4배가 다르고, 같은 빛을 인코딩하면 어두운 쪽에서 9코드까지 어긋난다. 셰이더에서 `pow(c, 2.2)`로 대충 풀면 그림자 쪽이 달라지는 이유다. 마지막 줄은 sRGB를 쓰는 이유다. 빛 1% 미만의 어두운 영역에 선형 8비트는 코드 3개, sRGB는 26개를 쓰므로, 선형 값을 8비트에 그대로 저장하면 어두운 그러데이션에 띠(banding)가 생긴다.

## 계산은 선형 공간에서
빛은 더해지고 곱해지므로, 그 계산은 빛의 양인 선형 값으로 해야 한다. 화면값으로 계산하면 얼마나 틀리는지 센다(앞 코드에 이어서).
```python
to8 = lambda l: round(255 * encode(l))           # 선형 → 8비트 화면 코드
print("검정·흰색 50% 섞기: 화면값 평균", (0 + 255) / 2,
      "/ 선형 평균", to8((decode(0) + decode(1)) / 2))
c = 200                                          # 알베도 텍스처 코드
print("코드 200 × N·L 0.5: 화면값에 곱하면", c // 2,
      "/ 선형에서 곱하면", to8(decode(c / 255) * 0.5))
print("화면값에 곱한 결과의 빛은 원래의",
      f"{decode(100 / 255) / decode(c / 255):.0%}")
```
```text
검정·흰색 50% 섞기: 화면값 평균 127.5 / 선형 평균 188
코드 200 × N·L 0.5: 화면값에 곱하면 100 / 선형에서 곱하면 146
화면값에 곱한 결과의 빛은 원래의 22%
```
흰 픽셀과 검은 픽셀이 반씩 섞인 곳(멀리서 본 체커보드, 반투명 블렌딩, 밉맵 평균)은 빛이 절반이니 화면 코드 188이어야 하는데, 화면값으로 평균하면 128이 되어 어둡다. N·L로 어둡게 할 때도 화면값에 곱하면 빛이 절반이 아니라 22%만 남아 그늘이 지나치게 진해진다. 그래서 파이프라인은 다음처럼 짠다.
- 색 텍스처는 sRGB 형식(OpenGL ES 3.0의 `SRGB8_ALPHA8`, DirectX의 `DXGI_FORMAT_R8G8B8A8_UNORM_SRGB`)으로 만들어 샘플링 때 하드웨어가 선형으로 풀게 한다. 법선·거칠기 맵처럼 빛이 아닌 데이터는 선형 형식으로 둔다.
- 셰이더 안의 조명과 블렌딩은 모두 선형 값으로 한다.
- sRGB 렌더 타깃에 쓰면 하드웨어가 인코딩하고 블렌딩도 선형으로 해 준다. 데스크톱 OpenGL은 `GL_FRAMEBUFFER_SRGB`를 켜야 하고, OpenGL ES 3.0은 sRGB 형식 첨부물이면 늘 변환한다. 이 글의 하네스처럼 RGBA8 캔버스에 그릴 때는 마지막 셰이더가 직접 인코딩한다.

Unity는 Player Settings의 Color Space를 Linear로 두면 이 흐름을 따르고, 텍스처마다 sRGB (Color Texture) 체크로 형식을 정한다.

## HDR: 1보다 밝은 빛 담기
햇빛을 받은 면, 여러 광원의 합, 발광체는 쉽게 1을 넘는다. RGBA8 버퍼는 1에서 잘라 버려 하이라이트의 차이가 사라지고, 뒤에 올 블룸(14편)이나 노출 조절도 할 수 없다. 그래서 조명은 부동소수 렌더 타깃에 담는다. **RGBA16F**는 채널마다 FP16(부호 1, 지수 5, 가수 10비트)이고, **R11G11B10F**는 32비트에 R·G를 11비트(지수 5, 가수 6), B를 10비트(지수 5, 가수 5) 부동소수로 담으며 부호와 알파가 없다. WebGL2(OpenGL ES 3.0)에서는 `EXT_color_buffer_float` 확장이 있어야 이 형식에 렌더링할 수 있다. 비트 구조에서 범위와 정밀도를 계산한다.
```python
import math, random, struct

def fmax(e_bits, m_bits):            # 부호 없는 부분 포함, 최대 유한값
    bias = 2 ** (e_bits - 1) - 1
    return 2.0 ** (2 ** e_bits - 2 - bias) * (2 - 2.0 ** -m_bits)

half = struct.unpack('<e', struct.pack('<H', 0x7BFF))[0]  # FP16 최대 비트
print("FP16 최대:", fmax(5, 10), "struct 해석과 일치:", fmax(5, 10) == half)
print("11비트 float 최대:", fmax(5, 6), "/ 10비트:", fmax(5, 5))

def quant(x, m):                     # 가수 m비트로 반올림(정규 범위)
    step = 2.0 ** (math.floor(math.log2(x)) - m)
    return round(x / step) * step

rng = random.Random(10)
xs = [10 ** rng.uniform(-3, 3) for _ in range(300)]
same = sum(quant(x, 10) == struct.unpack('<e', struct.pack('<e', x))[0]
           for x in xs)
print(f"무작위 300개 FP16 반올림: struct와 일치 {same}/300")
for name, m in (("RGBA16F", 10), ("R11G11B10F의 R·G", 6), ("B", 5)):
    err = max(abs(quant(x, m) / x - 1) for x in xs)
    print(f"{name}: 최대 상대 오차 {err:.3%}, 상한 {2 ** -(m + 1):.3%}")
```
```text
FP16 최대: 65504.0 struct 해석과 일치: True
11비트 float 최대: 65024.0 / 10비트: 64512.0
무작위 300개 FP16 반올림: struct와 일치 300/300
RGBA16F: 최대 상대 오차 0.048%, 상한 0.049%
R11G11B10F의 R·G: 최대 상대 오차 0.755%, 상한 0.781%
B: 최대 상대 오차 1.525%, 상한 1.562%
```
범위는 셋 다 6만 남짓으로 비슷하고 정밀도는 가수 비트가 정한다. 측정한 최대 오차는 모두 반올림 상한 `2^-(m+1)` 아래다. R11G11B10F는 RGBA16F의 절반 크기라 대역폭을 아끼지만 상대 오차가 16~32배 크고 알파가 없어, 알파가 필요 없는 조명 누적 버퍼에 주로 쓴다.

## 노출과 톤 매핑
HDR 값을 화면의 0~1로 접어 넣는 것이 **톤 매핑**(tone mapping)이다. 먼저 카메라처럼 노출을 곱한다. 자동 노출은 프레임의 로그 평균 휘도를 구해 중간 회색 0.18에 맞추는 라인하르트(2002)의 방식이 기본이다. 그다음 곡선을 적용한다. 라인하르트 `x / (1 + x)`는 가장 단순하다. ACES 근사는 영화 업계 표준 ACES의 곡선을 나르코비치(2016)가 유리 함수 하나로 맞춘 것이다. 하블 곡선은 언차티드 2(GDC 2010 발표)에서 쓴 필믹 곡선으로 상수 6개로 어두운 쪽(토)과 밝은 쪽(숄더) 모양을 정하고 흰 점 W = 11.2로 나눈다. 셰이더는 픽셀 열마다 HDR 값 하나를 세 곡선에 넣고, 결과를 sRGB로 인코딩해 R, G, B에 쓴다.
```glsl
#version 300 es
precision highp float;
// render 6x1 rgba
out vec4 fragColor;
const float X[6] = float[6](0.05, 0.18, 0.5, 1.0, 4.0, 16.0);  // HDR 입력

float encodeSRGB(float l) {          // 선형 → sRGB(구간식)
    return l <= 0.0031308 ? 12.92 * l : 1.055 * pow(l, 1.0 / 2.4) - 0.055;
}
float reinhard(float x) { return x / (1.0 + x); }
float aces(float x) {                // 나르코비치의 ACES 근사
    return clamp(x * (2.51 * x + 0.03) / (x * (2.43 * x + 0.59) + 0.14),
                 0.0, 1.0);
}
float hable(float x) {               // 하블(언차티드 2)의 필믹 곡선
    const float A = 0.15, B = 0.50, C = 0.10, D = 0.20, E = 0.02, F = 0.30;
    return (x * (A * x + C * B) + D * E) / (x * (A * x + B) + D * F) - E / F;
}
void main() {
    float x = X[int(gl_FragCoord.x)];          // 픽셀 열마다 값 하나
    vec3 t = vec3(reinhard(x), aces(x), hable(x) / hable(11.2));
    fragColor = vec4(encodeSRGB(t.r), encodeSRGB(t.g), encodeSRGB(t.b), 1.0);
}
```
```text
(0,0) 62 59 38 255
(1,0) 109 141 73 255
(2,0) 156 206 115 255
(3,0) 188 232 150 255
(4,0) 231 252 220 255
(5,0) 248 255 255 255
```
같은 식을 파이썬으로 계산하고, 위 렌더링 값을 옮겨 와 비교한다(앞 코드에 이어서).
```python
def reinhard(x): return x / (1 + x)
def aces(x):
    y = x * (2.51 * x + 0.03) / (x * (2.43 * x + 0.59) + 0.14)
    return min(1.0, max(0.0, y))
def hable(x):
    A, B, C, D, E, F = 0.15, 0.50, 0.10, 0.20, 0.02, 0.30
    f = lambda t: ((t * (A * t + C * B) + D * E)
                   / (t * (A * t + B) + D * F) - E / F)
    return f(x) / f(11.2)

gpu = [(62, 59, 38), (109, 141, 73), (156, 206, 115),
       (188, 232, 150), (231, 252, 220), (248, 255, 255)]  # 위 렌더링 결과
worst = 0
for x, g in zip((0.05, 0.18, 0.5, 1.0, 4.0, 16.0), gpu):
    py = [min(255, to8(op(x))) for op in (reinhard, aces, hable)]
    worst = max(worst, max(abs(p - q) for p, q in zip(py, g)))
    print(f"x={x}: 잘라내기 {to8(min(x, 1.0))}, 라인하르트 {py[0]}, "
          f"ACES {py[1]}, 하블 {py[2]}")
print("GPU 렌더링과의 최대 차이(코드):", worst)
```
```text
x=0.05: 잘라내기 63, 라인하르트 62, ACES 59, 하블 38
x=0.18: 잘라내기 118, 라인하르트 109, ACES 141, 하블 73
x=0.5: 잘라내기 188, 라인하르트 156, ACES 206, 하블 115
x=1.0: 잘라내기 255, 라인하르트 188, ACES 232, 하블 150
x=4.0: 잘라내기 255, 라인하르트 231, ACES 252, 하블 220
x=16.0: 잘라내기 255, 라인하르트 248, ACES 255, 하블 255
GPU 렌더링과의 최대 차이(코드): 0
```
GPU와 파이썬은 코드 하나까지 같다. 잘라내기는 1, 4, 16이 모두 255라 밝은 부분의 차이가 사라진다. 라인하르트는 16에서도 흰색에 닿지 않고 중간 회색도 118에서 109로 어두워진다. ACES 근사는 0.05를 59로 누르고 0.18을 141로 올려 대비가 크며, 분자와 분모가 같아지는 x ≈ 7.24에서 흰색에 닿는다. 하블 곡선은 그대로면 어두워서 노출을 2배쯤 올려 쓰고, W보다 밝은 값은 1을 넘어 잘린다. Unity URP의 Tonemapping은 None·Neutral·ACES 중에서 고르고, 언리얼 엔진은 4.15부터 ACES를 따르는 필믹 톤 매퍼가 기본이다.

## 어디에 쓰이나
- 양자화 2편 「수 형식의 지도: FP32에서 FP4까지」: FP16의 지수·가수 구조가 그대로 RGBA16F이고, R11G11B10F는 부호를 버리고 가수를 줄인 변형이다.
- 5편 「텍스처 샘플링: 필터링, 밉맵, 이방성 필터링」: 밉맵 평균과 쌍선형 필터링도 빛의 평균이어야 하므로 색 텍스처는 sRGB 형식으로 두어 선형으로 풀어 읽는다.
- 14편 「포스트 프로세싱: 분리 가능한 블러, 블룸, 외곽선」: 블룸은 1을 넘는 밝은 부분을 뽑아야 하므로 톤 매핑 전의 HDR 버퍼에서 한다.
- 미적분 4편 「지수 함수와 로그 함수」: 자동 노출의 로그 평균 휘도는 밝기 차이가 몇 자릿수인 장면에서 극단값에 끌리지 않는 기하 평균이다.

## 정리
- sRGB 화면값은 빛의 양을 눌러 담은 값이고, 구간식은 2.2제곱과 어두운 쪽에서 크게 다르다.
- 조명과 블렌딩은 선형 값으로 해야 하며, sRGB 텍스처와 렌더 타깃이 변환을 하드웨어로 처리한다.
- HDR 버퍼는 RGBA16F(8바이트)나 R11G11B10F(4바이트)로 6만 남짓까지 담고, 정밀도는 가수 비트가 정한다.
- 톤 매핑 곡선은 하이라이트를 1 안으로 접어 넣으며, GLSL 결과와 파이썬 계산이 코드 단위까지 일치했다.
