# [게임 셰이더 16/16] 셰이더 성능: 분기, 정밀도, 오버드로, 셰이더 변형

## 픽셀은 묶여서 실행된다
프래그먼트 셰이더는 픽셀 하나씩 도는 것처럼 쓰지만, GPU는 3편의 2×2 쿼드 여러 개를 모아 한 명령을 32개(NVIDIA의 워프, AMD RDNA의 wave32) 또는 64개(AMD GCN의 웨이브프런트) 레인에 동시에 내린다(GPU와 CUDA 3편 「SIMT와 워프: 32개 스레드가 함께 걷는 법」). 그래서 비용은 묶음이 실행한 명령 수로 봐야 한다. if 문의 조건이 유니폼처럼 모든 레인에서 같으면 **균일한 분기**(uniform branch)라 묶음이 한쪽만 실행한다. 조건이 픽셀마다 다르면 **갈라지는 분기**(divergent branch)가 되어, 레인 하나라도 가는 갈래는 묶음 전체가 실행하고 나머지 레인은 결과를 버린다. 아래 셰이더는 원 안이면 비싼 갈래로 가는 조건을 두고, 8×4 픽셀을 32레인 묶음 하나로 가정해 묶음마다 참인 레인을 센다(실제 배치는 하드웨어마다 다르다). 묶음 전체가 참이면 `@`, 전체가 거짓이면 빈칸, 갈라진 묶음은 참인 픽셀 `+`, 거짓인 픽셀 `-`다.
```glsl
#version 300 es
precision highp float;
// render 32x12
in vec2 vUV;
out vec4 fragColor;
bool inside(vec2 p) { return length(p - vec2(13, 6)) < 7.5; }  // 분기 조건
void main() {
    vec2 p = floor(vUV * vec2(32, 12));          // 픽셀 좌표(정수)
    vec2 b = floor(p / vec2(8, 4)) * vec2(8, 4); // 이 픽셀이 속한 8×4 묶음
    int n = 0;                                   // 묶음 32레인 중 참인 수
    for (int y = 0; y < 4; y++)
        for (int x = 0; x < 8; x++) n += inside(b + vec2(x, y) + 0.5) ? 1 : 0;
    float c = n == 0 ? 0.0 : n == 32 ? 1.0 : inside(p + 0.5) ? 0.55 : 0.33;
    fragColor = vec4(vec3(c), 1);
}
```
```text
--------@@@@@@@@++------
-------+@@@@@@@@+++-----
------++@@@@@@@@++++----
------++@@@@@@@@++++----
------++@@@@@@@@++++----
------++@@@@@@@@++++----
------++@@@@@@@@++++----
------++@@@@@@@@++++----
------++@@@@@@@@++++----
------++@@@@@@@@++++----
-------+@@@@@@@@+++-----
--------@@@@@@@@++------
```
참 갈래 100명령, 거짓 갈래 20명령이라 가정하고 같은 조건으로 묶음별 비용을 센다. 지도의 한 글자가 묶음 하나다.
```python
import math, random, struct
inside = lambda x, y: math.hypot(x - 13, y - 6) < 7.5   # 셰이더와 같은 조건
A, B = 100, 20                     # 참 갈래·거짓 갈래의 명령 수(가정)
warp = ideal = 0
for by in (8, 4, 0):               # 위쪽 묶음부터, 한 글자 = 8×4 묶음
    row = ""
    for bx in (0, 8, 16, 24):
        t = sum(inside(bx + x + .5, by + y + .5) for y in range(4) for x in range(8))
        ideal += t * A + (32 - t) * B              # 레인마다 제 갈래만 실행
        warp += 32 * (A * (t > 0) + B * (t < 32))  # 한 레인이라도 가면 전체 실행
        row += "@" if t == 32 else "." if t == 0 else "+"
    print(row)
print(f"실행한 레인·명령 {warp:,}, 이상적 {ideal:,} → {warp/ideal:.2f}배")
```
```text
+@+.
+@+.
+@+.
실행한 레인·명령 34,560, 이상적 20,160 → 1.71배
```

지도가 GPU 출력의 묶음 배치와 같고, 12개 묶음 중 6개가 두 갈래를 모두 실행해 이상적인 경우의 1.71배를 썼다. 경계가 지나는 묶음만 손해를 보므로 갈래가 짧거나 경계가 드물면 괜찮고, 짧은 분기는 컴파일러가 양쪽을 다 계산해 고르는 코드로 바꾸기도 한다. 또 하나의 축은 레지스터다. 텍스처 읽기는 수백 사이클이 걸리고 GPU는 그동안 다른 워프를 돌려 지연을 숨기는데, 셰이더가 레지스터를 많이 쓰면 동시에 올릴 워프가 줄어 숨길 거리가 사라진다(GPU와 CUDA 8편 「점유율과 지연 숨기기: 레지스터와 공유 메모리가 동시 워프 수를 정한다」).

## 정밀도: mediump와 half
GLSL ES 3.00의 mediump는 최소 범위 ±2¹⁴, 상대 정밀도 2⁻¹⁰만 보장해 FP16(양자화 2편)으로 구현될 수 있다. 모바일 GPU에서 FP16은 대개 더 빠르고 전력과 레지스터를 덜 써서 0~1 범위의 색 계산에는 이득이다. 문제는 큰 값이다. 파이썬 `struct`의 FP16 변환으로 간격을 재고 공식과 대조한다(앞 코드에 이어서).
```python
def step(x):                       # x 근처에서 FP16이 표현하는 간격
    h = struct.unpack("<H", struct.pack("<e", x))[0]
    nxt, cur = (struct.unpack("<e", struct.pack("<H", v))[0] for v in (h + 1, h))
    return nxt - cur

rng = random.Random(2)
ok = sum(step(x) == 2.0 ** (math.floor(math.log2(x)) - 10)
         for x in (rng.uniform(1, 60000) for _ in range(300)))
print(f"무작위 300개: FP16 간격 = 2^(⌊log₂x⌋ − 10) 일치 {ok}/300")
for t in (1.0, 60.0, 3600.0):      # 초 단위 시간을 FP16에 담으면
    print(f"시간 {t:g}초: 간격 {step(t):g}초")
print(f"UV 0.9 근처: 간격 {step(0.9):.6f} = 4096 텍스처의 {step(0.9)*4096:g}텍셀")
```
```text
무작위 300개: FP16 간격 = 2^(⌊log₂x⌋ − 10) 일치 300/300
시간 1초: 간격 0.000976562초
시간 60초: 간격 0.03125초
시간 3600초: 간격 2초
UV 0.9 근처: 간격 0.000488 = 4096 텍스처의 2텍셀
```

초 단위 시간을 mediump로 넘기면 1분 만에 간격이 0.031초로 60fps의 프레임 시간(0.0167초)보다 커지고, 한 시간이면 2초 간격이라 `sin(uTime)` 애니메이션이 멈췄다 튄다. 4096 텍스처의 UV도 2텍셀 간격으로 뭉개진다. 데스크톱 드라이버는 정밀도 한정자를 무시하고 32비트로 계산하는 경우가 많아 이런 버그는 모바일 기기에서만 드러난다. 시간은 CPU에서 주기로 감아 넘기고 위치·UV는 highp로 둔다. HLSL에서는 `min16float`나 셰이더 모델 6.2의 16비트 타입으로 요청한다.

## 오버드로와 이른 깊이 테스트
같은 픽셀을 여러 번 셰이딩하는 것을 **오버드로**(overdraw)라 한다. GPU는 셰이더 전에 깊이를 비교하는 **이른 깊이 테스트**(early-Z)로 이미 더 가까운 것이 그려진 픽셀을 건너뛰므로, 불투명 물체는 앞에서 뒤로 그려야 이득이다. 셰이더가 `discard`나 `gl_FragDepth`를 쓰면 실행 전에 깊이를 확정할 수 없어 이른 테스트가 꺼질 수 있다. 64×64 화면에 불투명 사각형 40개를 순서별로 그린다(앞 코드에 이어서).
```python
rects = []                         # 불투명 사각형 40개: (x0, y0, x1, y1, 깊이)
for _ in range(40):
    x, y = rng.randrange(64), rng.randrange(64)
    rects.append((x, y, min(x + rng.randint(8, 32), 64),
                  min(y + rng.randint(8, 32), 64), rng.random()))
pix = lambda r: ((x, y) for y in range(r[1], r[3]) for x in range(r[0], r[2]))

def shaded(order):                 # 이른 깊이 테스트를 통과해 셰이딩된 수
    zbuf, n = {}, 0
    for r in order:
        for p in pix(r):
            if r[4] < zbuf.get(p, 2.0): zbuf[p] = r[4]; n += 1
    return n

area = sum(1 for r in rects for _ in pix(r))
cover = len({p for r in rects for p in pix(r)})
far = sorted(rects, key=lambda r: -r[4])
print(f"뒤→앞 {shaded(far):,} (넓이 합 {area:,}), 무작위 순서 {shaded(rects):,}")
print(f"앞→뒤 {shaded(far[::-1]):,} (덮인 픽셀 {cover:,})")
```
```text
뒤→앞 10,284 (넓이 합 10,284), 무작위 순서 5,463
앞→뒤 3,013 (덮인 픽셀 3,013)
```

뒤에서 앞으로 그리면 매번 더 가까운 것이 와서 넓이 합만큼, 앞에서 뒤로 그리면 덮인 픽셀 수만큼 셰이딩한다. 두 값 모두 정의대로 센 값과 같고 차이는 3.4배다. 물체 단위 정렬은 완벽하지 않으므로 엔진은 깊이만 먼저 그리는 **깊이 프리패스**(depth prepass)로 정점 처리를 한 번 더 하는 대신 셰이딩을 픽셀당 한 번으로 만든다(15편의 포워드+). 반투명 물체는 뒤에서 앞으로 그려야 해서(12편) 오버드로를 피할 수 없다.

## 작은 삼각형과 쿼드 효율
미분(dFdx·dFdy)을 위해 픽셀은 2×2 쿼드로 셰이딩되고, 삼각형이 쿼드 일부만 덮어도 4레인이 모두 돈다(덮지 않은 레인은 도우미 레인으로 결과를 버린다). 무작위 삼각형을 크기별로 래스터화해 쿼드 효율(덮인 픽셀 ÷ 실행 레인)을 재고, 쿼드 수 세기는 직사각형 공식으로 먼저 확인한다(앞 코드에 이어서).
```python
lanes = lambda px: 4 * len({(x // 2, y // 2) for x, y in px})  # 쿼드마다 4레인

def tri(a, b, c):                  # 중심이 삼각형 안인 픽셀(3편의 에지 함수)
    e = lambda p, q, x, y: (q[0]-p[0]) * (y-p[1]) - (q[1]-p[1]) * (x-p[0])
    out = []
    for y in range(int(min(a[1], b[1], c[1])), int(max(a[1], b[1], c[1])) + 1):
        for x in range(int(min(a[0], b[0], c[0])), int(max(a[0], b[0], c[0])) + 1):
            w = (e(a, b, x+.5, y+.5), e(b, c, x+.5, y+.5), e(c, a, x+.5, y+.5))
            if min(w) >= 0 or max(w) <= 0: out.append((x, y))
    return out

ok = 0                             # 정렬된 직사각형: 쿼드 수 공식과 대조
for _ in range(300):
    x0, y0, w, h = (rng.randint(0, 9) for _ in range(4))
    q = ((x0 + w) // 2 - x0 // 2 + 1) * ((y0 + h) // 2 - y0 // 2 + 1)
    ok += lanes([(x, y) for x in range(x0, x0+w+1) for y in range(y0, y0+h+1)]) == 4*q
print(f"직사각형 300개: 쿼드 수 = 공식 {ok}/300")
for s in (1, 4, 16, 32):           # 꼭짓점이 ±s 픽셀 안인 무작위 삼각형 300개
    px = ln = 0
    for _ in range(300):
        ox, oy = rng.uniform(0, 64), rng.uniform(0, 64)
        p = tri(*[(ox + rng.uniform(-s, s), oy + rng.uniform(-s, s)) for _ in "abc"])
        px += len(p); ln += lanes(p)
    print(f"±{s:2d}픽셀: 평균 {px/300:5.1f}픽셀, 쿼드 효율 {px/max(ln, 1):.0%}")
```
```text
직사각형 300개: 쿼드 수 = 공식 300/300
± 1픽셀: 평균   0.3픽셀, 쿼드 효율 25%
± 4픽셀: 평균   5.1픽셀, 쿼드 효율 45%
±16픽셀: 평균  82.7픽셀, 쿼드 효율 74%
±32픽셀: 평균 313.9픽셀, 쿼드 효율 84%
```

픽셀 몇 개짜리 삼각형은 레인의 절반도 일하지 않는다. 먼 물체에 LOD(게임 자원 관리 9편)를 쓰는 이유는 정점 수만이 아니라 화면에서 삼각형이 너무 작아지지 않게 하는 데에도 있다.

## 셰이더 변형과 컴파일 끊김
엔진은 기능마다 키워드(안개, 그림자, 법선 맵…)를 두고 조합마다 따로 컴파일한 **셰이더 변형**(shader variant)을 만든다. 분기와 달리 안 쓰는 코드가 레지스터를 차지하지 않지만, 켜고 끄는 키워드가 n개면 변형은 2ⁿ개다. 10개면 1,024개, 20개면 1,048,576개다. 선택지가 여럿인 그룹(안개 끔·선형·지수…)이면 그룹 크기의 곱이고, 패스 수와 그래픽 API 수만큼 다시 곱해진다(앞 코드에 이어서).
```python
import itertools
count = lambda g: len(list(itertools.product(*map(range, g))))  # 직접 열거
g = [2] * 10                       # 켜고 끄는 키워드 10개
print(f"on/off 10개: 2^10 = {2**10}, 열거 {count(g)}")
g = [4, 3, 2, 2, 3]                # 안개 4가지, 그림자 3가지 … 같은 그룹들
n = math.prod(g)
print(f"그룹 {g}: 곱 {n} = 열거 {count(g)}, 패스 3 × API 2면 컴파일 {n * 6}번")
```
```text
on/off 10개: 2^10 = 1024, 열거 1024
그룹 [4, 3, 2, 2, 3]: 곱 144 = 열거 144, 패스 3 × API 2면 컴파일 864번
```

Unity의 `multi_compile`은 모든 조합을 만들고 `shader_feature`는 빌드에 든 머티리얼이 쓰는 조합만 만든다. DirectX 12·Vulkan·Metal에서는 셰이더와 블렌딩·깊이·정점 형식 상태를 묶은 파이프라인 상태 객체(PSO)를 만들 때 드라이버가 최종 GPU 코드를 컴파일하므로, 처음 보는 조합을 게임 도중에 만나면 그 프레임이 멈칫한다(셰이더 컴파일 스터터). 대책은 로딩 중에 미리 만드는 것이다. Unity의 `ShaderVariantCollection.WarmUp`, 언리얼 엔진의 번들 PSO 캐시와 5.1부터의 PSO 사전 캐싱, Vulkan의 `VkPipelineCache`가 그 도구다.

## 어디에 쓰이나
- GPU와 CUDA 3편 「SIMT와 워프: 32개 스레드가 함께 걷는 법」: 갈라지는 분기의 비용은 CUDA 커널의 워프 분기와 같고, 픽셀 셰이더에서는 묶음이 화면의 이웃 픽셀이라는 점만 다르다.
- 게임 자원 관리 1편 「프레임 예산: 16.67ms 안에 모든 일을 끝내기」: 오버드로, 쿼드 효율, 변형 컴파일 끊김은 프레임 예산을 넘기는 대표 원인이다.
- 이산수학 6편 「경우의 수: 순열과 조합」: 키워드 그룹마다 선택지 수를 곱한 것이 셰이더 변형 수다.

## 정리
- 픽셀은 쿼드와 워프로 묶여 실행되므로 갈라지는 분기는 두 갈래를 다 치르고(실험에서 1.71배), 작은 삼각형은 쿼드 효율이 25~45%로 떨어진다.
- mediump는 FP16일 수 있어 큰 값에서 간격이 커지고, 한 시간 지난 시간 값은 2초 간격이 된다.
- 불투명 물체는 앞에서 뒤로 그리거나 깊이 프리패스를 쓰면 셰이딩이 덮인 픽셀 수로 줄어든다(실험에서 3.4배 차이).
- 키워드 n개는 변형 2ⁿ개를 만들고, PSO를 미리 만들어 두지 않으면 첫 사용 때 끊긴다.
