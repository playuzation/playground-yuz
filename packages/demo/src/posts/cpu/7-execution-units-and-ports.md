# [CPU 마이크로아키텍처 7/12] 실행 유닛과 포트: 지연 시간과 처리량은 다르다

> **한 줄 요약** — 백엔드는 포트마다 다른 실행 유닛을 달아 사이클마다 μop 여러 개를 동시에 시작하지만, 결과가 나오기까지의 지연이 시작 간격보다 길어서, 의존 사슬 하나뿐인 루프는 유닛을 놀리고 독립 누산기를 "지연 × 처리량"개만큼 두어야 포트가 꽉 찬다.

## 이 글에서 다루는 것
- 실행 포트와 실행 유닛: 스케줄러가 μop를 어디로 보내는가(Skylake 예)
- 지연(latency)과 처리량(throughput)의 차이, 리틀의 법칙
- 누산기 1·2·4·8·16개의 사이클을 스케줄링 모델로 세고 닫힌 식과 대조
- 포트 압력: 내적은 FMA보다 적재 포트가 먼저 찬다
- 컴파일러가 누산기를 마음대로 늘리지 못하는 이유(gcc 출력과 C 실행)

## 넓은 백엔드, 좁은 사슬
6편에서 해독된 μop는 4편의 이름 바꾸기를 거쳐 스케줄러(예약 스테이션)에 들어가고, 5편의 ROB가 순서를 지킨다. 스케줄러는 입력이 준비된 μop를 골라 **실행 포트**(execution port)로 내보내고, 포트 뒤에 달린 **실행 유닛**(execution unit)이 계산한다. 인텔 Skylake(클라이언트, 2015)는 포트가 8개다.
```text
μop → scheduler → port → unit

p0: ALU  FMA/FP  div  branch
p1: ALU  FMA/FP  imul
p5: ALU  shuffle
p6: ALU  branch
p2: load + address
p3: load + address
p4: store data
p7: store address
```
정수 덧셈은 네 포트(p0·p1·p5·p6) 어디로든 갈 수 있어 사이클당 4개, 부동소수 덧셈·곱셈·FMA는 p0·p1의 두 유닛이 맡아 사이클당 2개, 적재는 p2·p3로 사이클당 2개를 시작한다. 같은 일을 하는 유닛을 여러 개 두고 포트를 나눈 것이 슈퍼스칼라 백엔드다.

## 지연과 처리량
명령어마다 숫자가 두 개 있다. **지연**은 입력이 들어가서 결과가 나올 때까지의 사이클이고, **처리량**은 사이클마다 새로 시작할 수 있는 개수다(그 역수를 역처리량이라 부른다). Skylake의 FP 덧셈은 지연 4, 처리량 2다. 유닛 자체가 4단 파이프라인이라 한 덧셈이 끝나기 전에 다음 덧셈을 매 사이클 받는다.

문제는 다음 덧셈이 앞 결과를 입력으로 쓸 때다. `s += a[i]`는 매번 직전 `s`가 필요하므로 4사이클에 하나밖에 시작하지 못한다. 유닛 두 개, 각 4단, 즉 동시에 8개를 처리할 수 있는 자리 중 1개만 쓴다. 이 자리를 채우려면 서로 독립인 일이 8개 있어야 한다. 대기열 이론의 **리틀의 법칙**(동시에 진행 중인 일 = 처리량 × 지연)이 말하는 그대로다. 그래서 합을 누산기 k개로 나눠, 원소 i를 `s[i % k]`에 더하고 마지막에 합친다.

이것을 사이클 단위 모델로 세어 보자. 덧셈 μop는 같은 누산기의 바로 앞 덧셈이 끝나야 시작할 수 있고, 매 사이클 준비된 것 중 오래된 순서로 최대 2개를 시작한다(지연 4).
```python
import math, random

def simulate(n, k, lat=4, ports=2):
    """덧셈 n개를 누산기 k개에 돌려 가며(원소 i → 누산기 i % k)
    실행. 매 사이클 준비된 μop 중 오래된 것부터 ports개 시작."""
    finish = [None] * n               # 결과가 나오는 사이클
    waiting, cycle = list(range(n)), 0
    while waiting:
        slots, rest = ports, []
        for i in waiting:
            d = i - k                 # 같은 누산기의 바로 앞 덧셈
            ready = d < 0 or (finish[d] is not None
                              and finish[d] <= cycle)
            if ready and slots:
                finish[i], slots = cycle + lat, slots - 1
            else:
                rest.append(i)
        waiting, cycle = rest, cycle + 1
    return max(finish)

n = 1024
for k in (1, 2, 4, 8, 16):
    c = simulate(n, k)
    print(f"누산기 {k:2}개: {c:4}사이클, 원소당 {c / n:.2f}")
```
```text
누산기  1개: 4096사이클, 원소당 4.00
누산기  2개: 2048사이클, 원소당 2.00
누산기  4개: 1025사이클, 원소당 1.00
누산기  8개:  515사이클, 원소당 0.50
누산기 16개:  515사이클, 원소당 0.50
```

누산기를 두 배로 늘릴 때마다 시간이 절반이 되다가 8개에서 멈춘다. 8개부터는 사슬이 아니라 포트 두 개가 한계라서 16개로 늘려도 그대로다. 원소당 사이클은 `max(지연/k, 1/처리량)`이다.

시뮬레이터가 맞는지 닫힌 식으로 확인한다. 사슬이 충분하면(k ≥ 지연 × 포트) μop i는 사이클 `i // p`에 시작한다. 모자라면 사슬 c는 포트가 빌 때(`c // p`) 시작해 지연마다 한 걸음씩 간다. 앞 코드에 이어서 실행한다.
```python
def closed_form(n, k, lat, p):
    if k >= lat * p:                  # 사슬이 충분: 포트가 한계
        return (n - 1) // p + lat
    # 사슬 c는 c // p 사이클에 시작해 lat마다 한 걸음
    return max(c // p + math.ceil((n - c) / k) * lat
               for c in range(min(k, n)))

rng = random.Random(7)
ok = 0
for _ in range(300):
    n, k = rng.randint(1, 300), rng.randint(1, 24)
    lat, p = rng.randint(1, 6), rng.randint(1, 4)
    ok += simulate(n, k, lat, p) == closed_form(n, k, lat, p)
print(f"닫힌 식과 무작위 300개 비교: {ok}개 일치")
print("필요한 누산기 수 = 지연 × 처리량 =", 4 * 2)
```
```text
닫힌 식과 무작위 300개 비교: 300개 일치
필요한 누산기 수 = 지연 × 처리량 = 8
```

## 포트 압력: 어느 포트가 먼저 차나
누산기를 넉넉히 둬도 다른 포트가 먼저 찰 수 있다. 내적 `s += a[i]*b[i]`는 원소마다 적재가 2개, FMA가 1개다. 한 바퀴에 원소 4개를 처리하도록 펼친 루프의 μop를 포트에 배정해 본다. 포트 집합 S마다 "S 안에서만 실행할 수 있는 μop 수 ÷ ∣S∣"의 최댓값이 하한이고, 유량 문제의 성질상 이 하한은 실제로 달성된다. 모든 배정을 다 해 보는 느린 계산과 대조한다.
```python
from itertools import combinations, product

loop = ["0156", "06"]                 # 인덱스 증가, 비교+분기
kernels = {"내적": ["23"] * 8 + ["01"] * 4 + loop,
           "합": ["23"] * 4 + ["01"] * 4 + loop}

def bound(uops):                      # 포트 집합별 하한의 최댓값
    ports, best = sorted(set("".join(uops))), 0
    for r in range(1, len(ports) + 1):
        for S in combinations(ports, r):
            cnt = sum(set(u) <= set(S) for u in uops)
            best = max(best, -(-cnt // r))       # 올림
    return best

def brute(uops):                      # 모든 배정에서 최대 부하의 최소
    return min(max(p.count(q) for q in set(p))
               for p in product(*uops))

for name, u in kernels.items():
    print(f"{name}: 하한 {bound(u)}, 전수 탐색 {brute(u)} 사이클/4원소")
```
```text
내적: 하한 4, 전수 탐색 4 사이클/4원소
합: 하한 2, 전수 탐색 2 사이클/4원소
```

합은 FMA 포트와 적재 포트가 똑같이 바빠 원소당 0.5사이클이지만, 내적은 적재 8개가 p2·p3 두 포트에 몰려 원소당 1사이클이다. FMA 유닛은 절반을 논다. 내적·행렬-벡터 곱이 "계산이 아니라 적재가 한계"인 이유가 여기 있다. 행렬 곱은 적재한 값을 여러 번 재사용할 수 있어 FMA 포트까지 채울 수 있다.

## 컴파일러는 왜 대신 해 주지 않나
gcc 13.3, `-O2`, x86-64에서 `float` 배열의 합을 컴파일하면 안쪽 루프가 이렇다.
```text
.L3:
	addss	(%rdi), %xmm0
	addq	$8, %rdi
	addss	-4(%rdi), %xmm0
	cmpq	%rax, %rdi
	jne	.L3
```
두 번 펼쳤지만 두 `addss`가 모두 `%xmm0` 하나에 더한다. 누산기가 1개라 원소당 4사이클이다. 컴파일러가 누산기를 늘리지 않는 이유는 부동소수 덧셈에 결합 법칙이 성립하지 않아서다. 더하는 순서를 바꾸면 결과가 달라지므로, C 표준이 정한 왼쪽부터의 순서를 지켜야 한다.
```c
#include <stdio.h>

#define N 1000000
static float a[N];

int main(void) {
    for (int i = 0; i < N; i++)
        a[i] = 1.0f / (float)(i + 1);

    float s = 0.0f;                        /* 누산기 1개 */
    for (int i = 0; i < N; i++)
        s += a[i];

    float s0 = 0, s1 = 0, s2 = 0, s3 = 0;  /* 누산기 4개 */
    for (int i = 0; i < N; i += 4) {
        s0 += a[i];
        s1 += a[i + 1];
        s2 += a[i + 2];
        s3 += a[i + 3];
    }
    float s4 = (s0 + s1) + (s2 + s3);

    double d = 0.0;                        /* 기준: double */
    for (int i = 0; i < N; i++)
        d += a[i];

    printf("acc 1 : %.7f\n", s);
    printf("acc 4 : %.7f\n", s4);
    printf("double: %.7f\n", d);
    return 0;
}
```
```text
acc 1 : 14.3573580
acc 4 : 14.3898878
double: 14.3927268
```

같은 100만 개를 더했는데 셋째 자리부터 다르다. 이 예에서는 누산기 4개 쪽이 double 기준에 더 가깝지만(부분합이 작아 반올림 손실이 덜하다), 어느 쪽이든 "다른 답"이므로 컴파일러는 허락 없이 바꾸지 않는다. `-O3 -ffast-math`를 주면 gcc는 순서 재배치를 허락받아 `addps` 하나로 4레인 부분합을 만든다. 그래도 벡터 누산기가 1개라 사슬은 남는다. 정수 덧셈은 결합 법칙이 성립해 컴파일러가 자유롭게 바꾼다.

정리하면 코드에서 할 일은 세 가지다. 뜨거운 루프의 의존 사슬을 찾아 누산기를 지연 × 처리량만큼 나누고, 부동소수라면 결과가 조금 바뀌는 것을 받아들이거나 그 루프에만 재결합을 허락하며, 포트 압력을 계산해 적재·저장이 한계라면 계산이 아니라 데이터 재사용을 늘린다.

## 숫자로 보기
인텔 Skylake 기준(Agner Fog의 명령어 표, 인텔 최적화 매뉴얼). 처리량은 사이클당 시작 개수다.

| 연산 | 지연 | 처리량 |
|---|---|---|
| 정수 덧셈 | 1 | 4 |
| 정수 곱셈(64비트) | 3 | 1 |
| FP 덧셈·곱셈·FMA | 4 | 2 |
| L1 적재 | 4~5 | 2 |

- 바로 앞 세대 Haswell(2013)은 FP 덧셈 지연 3(포트 하나), 곱셈·FMA 지연 5였고, Skylake에서 두 유닛 모두 덧셈·곱셈·FMA를 지연 4로 처리하게 바뀌었다. 같은 x86-64 코드라도 필요한 누산기 수가 세대마다 다르다.
- 나눗셈과 제곱근은 지연이 10사이클을 넘고 파이프라인이 일부만 겹친다. 반복문 안의 나눗셈을 역수 곱셈으로 바꾸는 최적화가 흔한 이유다.

## 어디에 쓰이나
- GPU와 CUDA 8편 「점유율과 지연 숨기기: 레지스터와 공유 메모리가 동시 워프 수를 정한다」: GPU가 동시 워프 수로 지연을 숨기는 계산도 같은 리틀의 법칙이다. CPU는 누산기(명령어 수준 병렬성)로, GPU는 워프 수로 채운다.
- 선형대수 2편 「내적과 코사인 유사도」: 내적 커널이 FMA보다 적재 포트에 막힌다는 포트 압력 계산이 벡터 검색·임베딩 유사도 계산의 실제 한계다.
- 트랜지스터에서 자연어까지 9편 「컴파일러: 식과 문장을 명령어로 바꾸기」: 컴파일러의 명령어 스케줄링과 루프 펼치기는 이 글의 지연·포트 정보를 쓰지만, 부동소수 의미를 바꾸는 재결합은 옵션 없이는 하지 않는다.
- BLAS의 행렬 곱 마이크로커널은 FMA의 지연 × 처리량을 덮을 만큼 독립 누산 레지스터를 두도록 블록 크기를 정한다.

## 정리
- 백엔드는 포트마다 유닛을 달아 사이클당 여러 μop를 시작하지만, 결과는 지연만큼 늦게 나온다.
- 의존 사슬 하나는 처리량이 아니라 지연에 묶인다. 누산기를 지연 × 처리량(Skylake FP 덧셈은 4 × 2 = 8)개 두면 포트가 꽉 찬다.
- 누산기가 충분해도 특정 포트가 먼저 찰 수 있다. 내적은 적재 포트가 한계라 원소당 1사이클이다.
- 부동소수 합의 순서를 바꾸면 답이 달라지므로 컴파일러는 허락(`-ffast-math` 등) 없이는 누산기를 나누지 않는다.
