# [CPU 마이크로아키텍처 6/12] 명령어 해독과 마이크로 연산: 가변 길이 x86을 고정 폭 내부 연산으로

> **한 줄 요약** — x86 명령어는 1~15바이트로 길이가 제각각이라 앞 명령어를 해독해야 다음 명령어의 시작을 아는데, 현대 x86 코어는 이를 고정 폭 마이크로 연산(μop)으로 바꿔 백엔드에 넘기고, 한 번 해독한 결과를 μop 캐시에 담아 다시 해독하지 않으며, 비교와 분기를 한 μop로 묶어 폭을 아낀다.

## 이 글에서 다루는 것
- x86 명령어 형식과 길이를 알아내기 어려운 이유
- 마이크로 연산(μop), 마이크로코드, 매크로 퓨전
- μop 캐시: 해독을 건너뛰는 지름길
- gcc가 만든 실제 기계어로 길이 분포 보기와 해독 폭 모델
- 고정 길이 ARM·RISC-V와의 비교

## 길이부터 알아내야 하는 명령어
트랜지스터에서 자연어까지 6편 「명령어 집합: 하드웨어와 소프트웨어의 약속」에서 RISC-V `addi`는 32비트 안의 정해진 자리에 필드가 있었다. x86 명령어는 앞에서부터 읽어 나가야 형식이 드러난다.
```text
┌───┬───┬──────┬─────┬───┬────┬───┐
│pfx│REX│opcode│ModRM│SIB│disp│imm│
└───┴───┴──────┴─────┴───┴────┴───┘
 0-4 0-1  1-3   0-1  0-1 0-4  0-8
```
접두사(prefix)가 몇 개 붙었는지, 64비트 피연산자를 뜻하는 REX가 있는지, opcode가 1바이트인지 `0F`로 시작하는 2바이트 이상인지를 봐야 하고, opcode에 따라 ModRM 바이트가 있는지, ModRM의 값에 따라 SIB와 변위(disp)가 몇 바이트인지, 즉치(imm)가 몇 바이트인지가 정해진다. AVX 명령어는 REX와 일부 opcode 바이트를 VEX·EVEX 접두사로 대신한다. 인텔 매뉴얼은 명령어 길이의 상한을 15바이트로 정한다.

아래는 이 글의 C 파일(뒤에 나온다)에서 실수 내적 반복문을 gcc 13.3 `-O2`로 컴파일하고 `objdump -d`로 본 실제 기계어다(칸 맞춤만 바꿨다).
```asm
  10:  f2 0f 10 04 c7     movsd  (%rdi,%rax,8),%xmm0
  15:  f2 0f 59 04 c6     mulsd  (%rsi,%rax,8),%xmm0
  1a:  48 83 c0 01        add    $0x1,%rax
  1e:  f2 0f 58 c8        addsd  %xmm0,%xmm1
  22:  48 39 c2           cmp    %rax,%rdx
  25:  75 e9              jne    10 <dot+0x10>
```
`f2 0f 10 04 c7`은 접두사 `f2`(스칼라 double), 2바이트 opcode `0f 10`, ModRM `04`(뒤에 SIB가 온다는 뜻), SIB `c7`(rdi + rax×8)로 5바이트다. `48 83 c0 01`은 REX.W `48`, opcode `83`, ModRM `c0`(레지스터 rax, 연산은 ADD), 즉치 `01`로 4바이트, `75 e9`는 2바이트다. 해독기는 첫 바이트만 보고는 길이를 모르므로, 16바이트를 가져와도 그 안의 명령어 경계를 찾는 일 자체가 직렬이다. 실제 코어는 길이만 먼저 알아내 경계를 표시하는 예비 해독(predecode) 단계를 따로 두고, 여러 바이트 위치를 한꺼번에 살펴 이 직렬성을 줄인다.

## 마이크로 연산으로 쪼개기
x86 명령어 하나는 메모리를 읽고 계산하고 쓰는 일까지 할 수 있다. 4편 「비순차 실행: 레지스터 이름 바꾸기와 토마술로 알고리즘」의 백엔드는 단순하고 폭이 고정된 연산을 다루기 쉬우므로, 해독기는 x86 명령어를 내부의 **마이크로 연산**(μop, micro-operation)으로 바꾼다. 인텔은 Pentium Pro(1995)에서 이 방식을 썼다. 해독기 3개 중 하나만 아무 명령어나 해독해 사이클당 μop를 최대 4개 내고, 나머지 둘은 μop 하나짜리 단순한 명령어만 맡는 4-1-1 구성이었다. 그보다 긴 명령어는 마이크로코드 롬이 μop 열을 내보낸다(트랜지스터에서 자연어까지 5편의 마이크로프로그래밍).

위의 `mulsd (%rsi,%rax,8),%xmm0`은 메모리 적재와 곱셈 두 일을 한다. 백엔드에서는 적재 μop와 곱셈 μop로 따로 실행되지만, 인텔 코어는 이런 쌍을 프런트엔드와 ROB에서 한 칸으로 묶어 폭을 아끼기도 한다(마이크로 퓨전, 주소 형식과 세대에 따라 다르다). 반대 방향의 묶음도 있다. **매크로 퓨전**(macro-fusion)은 `cmp %rax,%rdx` 바로 뒤의 `jne`처럼 비교·검사와 조건 분기가 붙어 있으면 두 명령어를 μop 하나로 해독한다. 인텔은 Core 마이크로아키텍처(2006)부터 이를 썼다. 아래 표본 86개 명령어에도 `cmp`·`test` 바로 뒤에 조건 분기가 오는 쌍이 10개 있다. 컴파일러가 비교를 분기 바로 앞에 붙여 두는 이유다.

## μop 캐시
해독은 전력도 많이 쓴다. 반복문은 같은 명령어를 수없이 다시 해독하므로, 한 번 만든 μop를 저장해 두면 다음에는 해독기를 거치지 않아도 된다. 인텔은 Sandy Bridge(2011)에 약 1.5K μop를 담는 **μop 캐시**(decoded ICache)를 넣었고, 적중하면 해독 단계를 끄고 μop를 바로 공급한다. 1편 「CPU 마이크로아키텍처 지도: 명령어 집합 아래에서 일어나는 일」의 표처럼 Golden Cove는 4K개를 사이클당 8개, Zen 4는 6.75K개를 사이클당 9개 공급한다.

## gcc가 만든 기계어의 길이
이 C 파일을 gcc 13.3 `-O2 -c`로 컴파일했다(x86-64).
```c
#include <stddef.h>
double dot(const double *a, const double *b, size_t n) {
    double s = 0;
    for (size_t i = 0; i < n; i++) s += a[i] * b[i];
    return s;
}
size_t count_char(const char *s, char c) {
    size_t k = 0;
    for (; *s; s++) k += (*s == c);
    return k;
}
void isort(int *a, size_t n) {
    for (size_t i = 1; i < n; i++) {
        int x = a[i];
        size_t j = i;
        for (; j > 0 && a[j - 1] > x; j--) a[j] = a[j - 1];
        a[j] = x;
    }
}
unsigned fnv1a(const unsigned char *p, size_t n) {
    unsigned h = 2166136261u;
    while (n--) h = (h ^ *p++) * 16777619u;
    return h;
}
```
`objdump -d`가 보여 준 `.text`의 86개 명령어 길이를 16진 한 자리씩 옮겨 적고 분포를 센다. `objdump -h`가 보고한 `.text` 크기는 0x116바이트다.
```python
import math
from collections import Counter

# gcc 13.3 -O2로 만든 dec.o의 .text, 명령어 86개의 길이(16진 한 자리씩)
L = ("43224155443241444174322233343332231544642433325244"
     "233324343213443321b14323573426321351")
lens = [int(c, 16) for c in L]
print(f"명령어 {len(lens)}개, 합계 {sum(lens)}바이트,",
      ".text 크기와 일치:", sum(lens) == 0x116)
print("길이별:", dict(sorted(Counter(lens).items())))
print(f"평균 {sum(lens) / len(lens):.2f}바이트")
```
```text
명령어 86개, 합계 278바이트, .text 크기와 일치: True
길이별: {1: 9, 2: 18, 3: 26, 4: 22, 5: 6, 6: 2, 7: 2, 11: 1}
평균 3.23바이트
```

3~4바이트가 가장 많고 1바이트(`ret`, `nop`)부터 11바이트까지 퍼져 있다. 11바이트짜리와 1·3·4·5·7바이트 일부는 반복문 시작·분기 목적지·다음 함수를 정렬하려고 넣은 `nop` 계열로, 86개 중 11개다.

## 해독 폭 모델
해독기 수와 사이클당 가져오는 바이트 수가 해독 속도를 어떻게 제한하는지 단순한 모델로 본다. 사이클마다 다음 명령어부터 window바이트 안에 완전히 들어오는 명령어를 해독기 수만큼 해독한다고 하자. 해독기 4개·16바이트는 Golden Cove 직전 세대(Sunny Cove 계열)까지의 인텔 큰 코어, 6개·32바이트는 Golden Cove의 공개 수치를 빌렸다. 경계는 이미 안다고 치고, 해독기마다 맡는 명령어 종류의 제약이나 정렬된 블록 단위 인출은 무시했다. 앞 코드에 이어서 실행한다.
```python
def cycles(lens, width, window):   # 단순화한 해독 모델: 사이클마다
    i = cyc = 0                    # 다음 명령어부터 window바이트 안에
    while i < len(lens):           # 완전히 든 명령어를 width개까지
        cyc += 1
        used = k = 0
        while (i < len(lens) and k < width
               and used + lens[i] <= window):
            used, i, k = used + lens[i], i + 1, k + 1
    return cyc

for w, win in ((4, 16), (6, 32)):
    c = cycles(lens, w, win)
    print(f"해독기 {w}개·{win}B: {c}사이클, 사이클당 {len(lens) / c:.2f}개")
print(f"μop 캐시(사이클당 8개): {math.ceil(len(lens) / 8)}사이클")
ok = all(cycles([n] * 1000, w, win) == math.ceil(1000 / min(w, win // n))
         for n in range(1, 16) for w, win in ((4, 16), (6, 32), (8, 32)))
print("고정 길이 1~15바이트, 모델 = 공식:", ok)
for n in (4, 7, 10):                # 길이 n바이트 명령어 60개
    print(f"길이 {n}: {cycles([n] * 60, 4, 16)}사이클",
          f"/ {cycles([n] * 60, 6, 32)}사이클")
```
```text
해독기 4개·16B: 23사이클, 사이클당 3.74개
해독기 6개·32B: 15사이클, 사이클당 5.73개
μop 캐시(사이클당 8개): 11사이클
고정 길이 1~15바이트, 모델 = 공식: True
길이 4: 15사이클 / 10사이클
길이 7: 30사이클 / 15사이클
길이 10: 60사이클 / 20사이클
```

길이를 고정한 열에서는 사이클당 `min(해독기 수, ⌊window ÷ 길이⌋)`개라는 공식이 나와야 하고, 모델이 1~15바이트 모두에서 공식과 맞았다. gcc 표본은 평균 3.23바이트라 16바이트 창에 4개가 대체로 들어가 사이클당 3.74개를 해독한다. 마지막 세 줄은 같은 길이의 명령어 60개를 두 구성(4개·16B / 6개·32B)으로 해독한 사이클이다. 길이가 7바이트면 16바이트 창에 두 개밖에 안 들어가, 해독기가 4개여도 2개씩만 해독한다. Golden Cove가 해독기와 함께 바이트 폭을 두 배로 늘린 이유다. μop 캐시에 적중하면 바이트 길이와 상관없이 사이클당 8개를 공급하므로 11사이클이면 된다.

## 고정 길이 ISA와 비교
AArch64 명령어는 모두 4바이트다. 명령어 경계가 4의 배수로 정해져 있으니 32바이트를 가져오면 8개의 시작점을 바로 알고 해독기 8개가 동시에 일할 수 있다. RISC-V는 기본 명령어가 32비트이고, C 확장의 16비트 압축 명령어를 섞을 수 있다. 그래도 길이는 첫 16비트의 하위 두 비트만 보면 안다(`11`이면 32비트 이상, 아니면 16비트). 대신 가변 길이는 자주 쓰는 명령어를 짧게 만들 수 있다. 위 표본은 평균 3.23바이트로 4바이트 고정보다 짧았다(같은 일에 드는 명령어 수는 ISA마다 다르다). 코드가 작으면 L1 명령어 캐시에 더 많이 든다. x86은 해독의 어려움을 예비 해독·μop 캐시·퓨전으로 메우고, 고정 길이 ISA는 해독을 단순하게 두는 대신 명령어 수와 코드 크기를 다른 방법으로 다룬다.

## 코드에 주는 의미
- 뜨거운 반복문이 μop 캐시에 들어가면 해독 병목이 사라진다. 지나친 루프 펼치기나 인라이닝은 코드를 키워 μop 캐시와 L1i에서 밀려날 수 있다.
- 매크로 퓨전은 비교와 분기가 붙어 있어야 일어난다. 컴파일러가 알아서 하지만, 손으로 쓴 어셈블리에서는 사이에 다른 명령어를 넣지 않는다.
- 위 표본의 `nop`처럼 gcc는 반복문과 함수 시작을 정렬한다(`-falign-loops`, `-falign-functions`). 코드 크기와 인출 효율을 맞바꾸는 선택이다.

## 정리
- x86 명령어는 1~15바이트이고 접두사·opcode·ModRM을 차례로 읽어야 길이를 알아서, 경계 찾기가 해독의 핵심 난제다.
- 해독기는 x86 명령어를 μop로 바꾸고, 마이크로 퓨전과 매크로 퓨전으로 폭을 아끼며, μop 캐시는 해독 자체를 건너뛴다.
- gcc 13.3 `-O2` 표본 86개 명령어는 1~11바이트, 평균 3.23바이트였고, 해독 폭 모델은 고정 길이 열에서 공식과 일치했다.
- 고정 길이 ARM·RISC-V는 경계를 바로 알아 해독이 단순하고, x86은 코드가 작은 대신 해독에 하드웨어를 더 쓴다.
