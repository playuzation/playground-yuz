# [CPU 마이크로아키텍처 1/12] CPU 마이크로아키텍처 지도: 명령어 집합 아래에서 일어나는 일

> **한 줄 요약** — 같은 x86-64 기계어라도 칩마다 그 아래의 회로(마이크로아키텍처)가 달라 걸리는 시간이 다르고, 실행 시간을 명령어 수 × CPI × 클록 주기로 나눈 뒤 CPI를 병목별로 쪼개면 어디를 고쳐야 빨라지는지 숫자로 보인다.

## 이 글에서 다루는 것
- ISA와 마이크로아키텍처: 같은 x86-64, 다른 칩
- 코어의 지도: 프런트엔드(예측·인출·해독)와 백엔드(이름 바꾸기·실행·은퇴)
- 실행 시간의 세 인수와 CPI 스택을 파이썬으로 계산하기
- 성능 카운터가 세는 것과 톱다운 분석

## 같은 기계어, 다른 칩
트랜지스터에서 자연어까지 6편 「명령어 집합: 하드웨어와 소프트웨어의 약속」에서 본 것처럼 ISA는 "이 비트열을 실행하면 상태가 이렇게 바뀐다"는 계약이고, 시간은 약속하지 않는다. 그 계약을 지키는 실제 회로가 **마이크로아키텍처**(microarchitecture)다. 인텔 12세대 코어의 P코어인 Golden Cove와 AMD의 Zen 4는 똑같은 x86-64 실행 파일을 돌리지만, 해독해 둔 연산을 담는 캐시의 크기와 공급 폭, 동시에 처리 중인 명령어 수가 모두 다르다(아래 숫자로 보기). 그래서 같은 프로그램이 칩마다 다른 속도로 돈다.

트랜지스터에서 자연어까지 7편 「빠르게 만드는 기술: 파이프라인, 캐시, 병렬성」이 파이프라인·캐시·SIMD를 개요로 보여 줬다면, 이 시리즈는 그것이 실제 코어 안에서 어떤 표와 버퍼와 카운터로 만들어지는지 사이클 단위로 센다.

## 코어의 지도
현대 고성능 코어는 크게 둘로 나뉜다. **프런트엔드**(front-end)는 다음에 실행할 명령어를 예측해 가져오고 내부 연산으로 바꾸며, 프로그램 순서대로 움직인다. **백엔드**(back-end)는 그 연산을 피연산자가 준비되는 대로 순서와 상관없이 실행하고, 결과는 다시 프로그램 순서대로 확정(은퇴)한다.
```text
 front-end (in order)
┌─────────────────────────────┐
│ branch predictor            │
│ → fetch (L1i) → decode      │
│ → uop cache → uop queue     │
└──────────────┬──────────────┘
               ↓ rename, allocate
 back-end (out of order)
┌─────────────────────────────┐
│ scheduler → ports → ALU,LSU │
│ ROB → retire (in order)     │
└─────────────────────────────┘
```
- **분기 예측기**(branch predictor): 분기 결과가 나오기 전에 다음 인출 주소를 정한다. 3편 「분기 예측: 2비트 카운터에서 gshare와 TAGE까지」.
- **해독기**(decoder)와 **μop 캐시**: 가변 길이 x86 명령어를 고정 폭 마이크로 연산(μop)으로 바꾼다. 6편 「명령어 해독과 마이크로 연산: 가변 길이 x86을 고정 폭 내부 연산으로」.
- **이름 바꾸기**(rename)와 **스케줄러**: 가짜 의존을 지우고 준비된 μop부터 실행 포트로 보낸다. 4편 「비순차 실행: 레지스터 이름 바꾸기와 토마술로 알고리즘」, 7편 「실행 유닛과 포트: 지연 시간과 처리량은 다르다」.
- **재정렬 버퍼**(ROB, reorder buffer): 순서 없이 끝난 결과를 순서대로 은퇴시키고, 예측이 틀리면 되돌린다. 5편 「재정렬 버퍼와 추측 실행: 틀린 미래를 되돌리는 법」.

이 장치들 밑에는 2편 「파이프라인 해저드: 포워딩과 스톨을 사이클 단위로」의 파이프라인이 깔려 있고, 데이터는 메모리 시스템 1편 「메모리 계층 지도: 레지스터에서 SSD까지 지연과 대역폭」의 캐시 계층에서 온다.

## 세 인수와 CPI 스택
```text
시간 = 명령어 수 × CPI × 클록 주기
CPI = 기본 CPI
    + Σ 명령어당 사건 수 × 벌점
```
명령어 수는 알고리즘·컴파일러·ISA가, CPI(cycles per instruction)는 마이크로아키텍처와 프로그램의 궁합이, 클록은 회로와 공정·전력이 정한다. 역수인 IPC(instructions per cycle)도 자주 쓴다. 한 사이클에 μop 4개를 은퇴시키는 4폭 코어의 이상적인 CPI는 0.25지만, 실제 프로그램은 분기 예측 실패와 캐시 미스로 사이클을 잃어 훨씬 높다. 그래서 CPI를 "막힘이 없을 때의 기본값 + 사건별로 잃은 사이클"로 쪼개 보는 **CPI 스택**(CPI stack)이 쓸모 있다.

가상의 프로그램을 성능 카운터로 쟀다고 하고 계산해 보자(숫자는 설명용이다). 벌점은 비순차 실행이 일부를 겹쳐 숨긴 뒤 남는 "실효" 사이클로 가정한다.
```python
import random

# 가상의 프로그램을 성능 카운터로 쟀다고 하자(설명용 숫자)
cnt = {"instructions": 2_000_000_000, "br-miss": 10_000_000,
       "L2 hit": 30_000_000, "DRAM": 4_000_000}
pen = {"br-miss": 17, "L2 hit": 12, "DRAM": 250}  # 실효 벌점(사이클)
base, ghz = 0.30, 3.0              # 막힘 없을 때의 CPI, 클록(GHz)

def cpi_stack(cnt, pen):
    n = cnt["instructions"]
    st = {"base": base}
    for k, p in pen.items():
        st[k] = cnt[k] / n * p      # 명령어당 사건 수 × 벌점
    return st

st = cpi_stack(cnt, pen)
cpi = sum(st.values())
for k, v in st.items():
    print(f"{k:8} {v:.3f} ({v / cpi:5.1%})")
t = cnt["instructions"] * cpi / (ghz * 1e9)
print(f"CPI {cpi:.3f}, IPC {1 / cpi:.2f}, 시간 {t:.3f}초")
for k in pen:                      # 사건 하나를 절반으로 줄이면?
    new = sum(cpi_stack(dict(cnt, **{k: cnt[k] // 2}), pen).values())
    print(f"{k} 절반 → ×{cpi / new:.2f}")
```
```text
base     0.300 (28.2%)
br-miss  0.085 ( 8.0%)
L2 hit   0.180 (16.9%)
DRAM     0.500 (46.9%)
CPI 1.065, IPC 0.94, 시간 0.710초
br-miss 절반 → ×1.04
L2 hit 절반 → ×1.09
DRAM 절반 → ×1.31
```

DRAM까지 간 적재는 명령어 500개에 하나(0.2%)뿐인데 CPI의 47%를 차지한다. 분기 예측 실패를 절반으로 줄이는 최적화는 4%, DRAM 미스를 절반으로 줄이는 최적화는 31%를 번다. 고칠 곳은 "자주 일어나는 사건"이 아니라 "사건 수 × 벌점"이 큰 곳이다.

클록을 올리면 어떨까? DRAM 지연은 나노초로 거의 고정이라, 클록이 빨라지면 사이클로 센 벌점이 커진다. 앞 코드에 이어서 실행한다.
```python
def run(g, dram_ns=250 / 3.0):     # DRAM 지연은 나노초로 고정
    c = sum(cpi_stack(cnt, dict(pen, DRAM=dram_ns * g)).values())
    return c, cnt["instructions"] * c / (g * 1e9)

t3 = run(3.0)[1]
for g in (3.0, 4.0, 5.0):
    c, t = run(g)
    print(f"{g}GHz: CPI {c:.3f}, {t:.3f}초, ×{t3 / t:.2f}")
```
```text
3.0GHz: CPI 1.065, 0.710초, ×1.00
4.0GHz: CPI 1.232, 0.616초, ×1.15
5.0GHz: CPI 1.398, 0.559초, ×1.27
```

클록을 1.33배로 올려도 1.15배, 1.67배로 올려도 1.27배만 빨라진다. GHz만으로 칩을 비교하면 안 되는 이유이고, 12편 「전력과 클록: 동적 전력, DVFS, 터보, 이종 코어」에서 터보 클록의 효과가 프로그램마다 다른 이유다.

## 모델을 확인하기
CPI 스택은 "사건이 명령어마다 정해진 확률로 독립적으로 일어나고 벌점이 더해진다"는 모델의 기댓값이다. 명령어 100만 개를 하나씩 흉내 내며 사건을 뽑아 사이클을 직접 더한 값과 비교해 보자. 앞 코드에 이어서 실행한다.
```python
rng = random.Random(1)
N = 1_000_000
rate = {k: cnt[k] / cnt["instructions"] for k in pen}
cycles, seen = 0.0, dict.fromkeys(pen, 0)
for _ in range(N):                 # 명령어 하나씩 사건을 뽑는다
    cycles += base
    for k, r in rate.items():
        if rng.random() < r:
            cycles += pen[k]
            seen[k] += 1
sim = cycles / N
print(f"시뮬레이션 CPI {sim:.3f}, 공식 {cpi:.3f}",
      f"(차이 {abs(sim - cpi) / cpi:.1%})")
print("사건 수:", seen)
print("기댓값:", {k: round(N * r) for k, r in rate.items()})
```
```text
시뮬레이션 CPI 1.069, 공식 1.065 (차이 0.4%)
사건 수: {'br-miss': 5006, 'L2 hit': 15033, 'DRAM': 2016}
기댓값: {'br-miss': 5000, 'L2 hit': 15000, 'DRAM': 2000}
```

사건 수가 기댓값 근처에서 흔들린 만큼만 CPI가 0.4% 다르다. 실제 코어에서는 이 모델의 가정이 깨진다. 비순차 코어는 서로 독립인 미스 여러 개를 겹쳐 기다리므로(메모리 수준 병렬성) 벌점이 단순히 더해지지 않고, 이 시리즈 4·5편이 그 겹침을 만드는 장치를 다룬다. 그래도 "어느 사건이 사이클을 먹는가"를 가늠하는 첫 도구로는 충분하다.

## 성능 카운터로 무엇을 재나
현대 CPU에는 사건을 세는 하드웨어 카운터(PMU, performance monitoring unit)가 있다. 리눅스에서는 `perf`가 이를 읽는다.
```sh
perf stat -e cycles,instructions,branches,branch-misses ./app
```
- `cycles`와 `instructions`로 IPC를 얻는다. IPC가 높아도 쓸데없는 명령어가 많으면 느리므로 시간 전체를 같이 본다.
- `branch-misses ÷ instructions × 1000`은 천 명령어당 예측 실패(MPKI)로, 예측기 비교에 쓰는 단위다.
- 캐시 계층별 미스 사건으로 위의 L2·DRAM 항목을 채운다. 사건 이름과 개수는 제조사·세대마다 다르다.

인텔의 아마드 야신이 2014년 ISPASS에서 발표한 **톱다운 분석**(top-down method)은 사이클마다 코어 폭만큼의 "슬롯"을 네 가지로 나눈다. 유용한 μop로 채워져 은퇴한 슬롯(Retiring), 버려진 추측에 쓴 슬롯(Bad Speculation), 프런트엔드가 μop를 못 대 준 슬롯(Frontend Bound), 실행 자원이나 메모리를 기다린 슬롯(Backend Bound)이다. 위 CPI 스택과 같은 질문을 슬롯 단위로 묻는 셈이고, 리눅스 `perf`와 인텔 VTune이 이 분류를 보여 준다.

## 숫자로 보기
같은 x86-64를 구현한 두 코어의 프런트엔드·백엔드 크기(제조사 발표 기준)다.

| 구조 | Golden Cove | Zen 4 |
|---|---|---|
| μop 캐시 | 4K개 | 6.75K개 |
| μop 캐시 공급 | 사이클당 8개 | 사이클당 9개 |
| ROB | 512개 | 320개 |

Golden Cove는 해독기를 4개에서 6개로, 사이클당 인출 폭을 16바이트에서 32바이트로 늘렸고, ROB는 직전 세대 Sunny Cove의 352개에서 512개가 되었다. 인텔은 이 과정에서 분기 예측 실패의 최소 벌점이 16사이클에서 17사이클로 한 단계 늘었다고 밝혔다. Zen 4는 Zen 3보다 μop 캐시를 4K개에서 6.75K개로, ROB를 256개에서 320개로 키웠다.

## 어디에 쓰이나
- 트랜지스터에서 자연어까지 7편 「빠르게 만드는 기술: 파이프라인, 캐시, 병렬성」: 세 인수와 파이프라인·캐시 개요를 이 시리즈가 부품 단위로 연다.
- 양자화 15편 「CPU 오프로드: GPU 메모리보다 큰 모델 돌리기」: CPU에서 도는 큰 행렬 곱이 메모리를 기다리는지 계산을 기다리는지 묻는 것은 CPI 스택의 DRAM 몫을 묻는 것과 같다.
- 컴파일러: gcc의 `-march`는 쓸 수 있는 명령어(ISA 확장)를, `-mtune`은 같은 ISA 안에서 어느 마이크로아키텍처의 비용 모델로 명령어를 배치할지를 고른다.
- 프로파일러: 리눅스 `perf`와 VTune의 톱다운 보기가 이 글의 CPI 스택을 실제 카운터로 채운다.

## 정리
- ISA는 결과를, 마이크로아키텍처는 시간을 정한다. 같은 x86-64라도 Golden Cove와 Zen 4는 μop 캐시의 크기와 공급 폭, ROB 크기가 다르다.
- 코어는 순서대로 움직이는 프런트엔드(예측·인출·해독)와 순서 없이 실행하고 순서대로 은퇴하는 백엔드로 나뉜다.
- CPI를 사건별 "명령어당 사건 수 × 벌점"으로 쪼개면, 예시에서는 0.2%의 DRAM 미스가 CPI의 47%였고 시뮬레이션이 공식과 0.4% 안에서 맞았다.
- 메모리 지연은 나노초로 고정이라 클록을 1.67배로 올려도 1.27배만 빨라졌다. 카운터와 톱다운 분석으로 병목부터 찾는다.
