# [어텐션 9/9] 서빙을 위한 어텐션: 페이지드 어텐션과 플래시 디코딩

> **한 줄 요약** — LLM 서빙의 디코드 단계는 메모리 바운드라 KV 캐시를 얼마나 알뜰하게 담고 빨리 읽느냐가 처리량을 정하며, 페이지드 어텐션은 KV 캐시를 고정 크기 블록으로 나눠 단편화를 없애고 플래시 디코딩은 긴 KV를 조각내 병렬로 읽은 뒤 온라인 소프트맥스 식으로 정확히 합친다.

## 이 글에서 다루는 것
- 프리필(연산 바운드)과 디코드(메모리 바운드), 산술 강도
- KV 캐시 단편화와 고정 크기 블록 페이지(vLLM)
- 접두사 공유
- 플래시 디코딩: KV 길이 방향으로 나눠 계산한 뒤 합치기

## 프리필과 디코드
요청 하나를 처리하는 과정은 두 단계다.
- **프리필**(prefill): 프롬프트 토큰 수천 개를 한꺼번에 넣어 KV 캐시를 채우고 첫 토큰을 낸다. 행렬 곱의 행이 많아 연산이 많다.
- **디코드**(decode): 토큰을 하나씩 만든다. 스텝마다 행이 하나뿐인 행렬 곱을 하면서도 가중치 전체와 그 요청의 KV 캐시 전체를 읽어야 한다.

둘의 차이는 **산술 강도**(arithmetic intensity), 즉 메모리에서 읽은 1바이트당 연산 수로 잴 수 있다. GPU의 연산 능력을 대역폭으로 나눈 값(능선, ridge point)보다 낮으면 메모리 바운드, 높으면 연산 바운드다.
```python
import numpy as np

ridge = 989e12 / 3.35e12                  # H100 SXM: BF16 FLOP/s ÷ 바이트/s
print(f"능선 {ridge:.0f} FLOP/바이트")

def linear_intensity(tokens, din=4096, dout=4096, b=2):
    flops = 2 * tokens * din * dout       # 토큰 수만큼 행렬 곱
    data = (din * dout + tokens * (din + dout)) * b   # 가중치 + 입출력
    return flops / data

for name, t in [("프리필 2048토큰", 2048), ("디코드 배치 1", 1),
                ("디코드 배치 64", 64)]:
    print(f"{name}: {linear_intensity(t):.1f}")

t, dh, g = 8192, 128, 4                   # 문맥, 헤드 차원, GQA 그룹
flops = g * 4 * t * dh                    # 쿼리 g개 × (q·K + p·V)
data = 2 * t * dh * 2                     # 공유하는 K, V 읽기 (BF16)
print(f"디코드 어텐션: {flops / data:.1f}")
```
```text
능선 295 FLOP/바이트
프리필 2048토큰: 1024.0
디코드 배치 1: 1.0
디코드 배치 64: 62.1
디코드 어텐션: 4.0
```

H100 SXM의 BF16 연산 989TFLOPS와 대역폭 3.35TB/s로 계산한 능선은 약 295다. 4096 × 4096 선형 층을 2048토큰 프리필로 계산하면 강도가 1024로 연산 바운드지만, 디코드 배치 1은 1이라 연산 능력의 1%도 쓰지 못한다. 여러 요청을 묶으면(배치 64) 가중치 읽기가 공유되어 강도가 62로 오른다. 반면 디코드 어텐션은 요청마다 자기 KV 캐시를 읽어야 해서 배치를 키워도 강도가 오르지 않고, 라마 3 8B처럼 GQA 그룹이 4면 4에 머문다. 그래서 디코드 처리량은 KV 캐시를 얼마나 많이 담고(배치 크기) 얼마나 빨리 읽느냐에 달려 있다. 이 글의 두 기법이 각각 이 두 가지를 다룬다.

## KV 캐시 단편화
초기 서빙 시스템은 요청마다 최대 생성 길이만큼의 KV 캐시를 연속된 메모리로 미리 잡았다. 실제 길이는 생성이 끝나 봐야 알기 때문이다. 그러면 세 가지 낭비가 생긴다.
- 예약 낭비: 아직 만들지 않은 토큰의 자리를 미리 잡아 둔다.
- 내부 단편화: 일찍 끝난 요청은 남은 자리를 끝까지 쓰지 못한다.
- 외부 단편화: 크기가 제각각인 연속 구간이 생겼다 사라지며 사이사이에 쓸 수 없는 틈이 남는다.
```python
rng = np.random.default_rng(0)
lengths = rng.integers(50, 2048, size=100)    # 요청 100개의 실제 길이
max_len, blk = 2048, 16
contig = 100 * max_len                        # 최대 길이만큼 미리 예약
paged = sum(-(-L // blk) * blk for L in lengths)   # 16토큰 블록 올림
print(f"실제 {lengths.sum():,}  연속 예약 {contig:,}"
      f" ({lengths.sum() / contig:.0%})  페이지 {paged:,}"
      f" ({lengths.sum() / paged:.1%})")
```
```text
실제 106,704  연속 예약 204,800 (52%)  페이지 107,424 (99.3%)
```

길이가 50~2047 사이로 고르게 퍼진 요청 100개에 2048토큰씩 연속 예약하면 잡아 둔 칸의 52%만 실제로 쓰인다. 16토큰 블록 단위로 필요할 때마다 받으면 99.3%가 쓰이고, 낭비는 요청마다 마지막 블록의 빈칸뿐이다.

## 페이지드 어텐션: KV 캐시의 가상 메모리
**페이지드 어텐션**(PagedAttention)은 vLLM(Kwon 등, 2023)이 제안했다. 운영체제의 가상 메모리처럼 KV 캐시를 고정 크기 **블록**(페이지, 예: 16토큰)으로 나누고, 요청마다 **블록 테이블**에 "논리 블록 i번 → 물리 블록 몇 번"을 기록한다. 물리 블록은 메모리 어디에 흩어져 있어도 되고, 어텐션 커널은 블록 테이블을 따라 블록들을 모아 읽는다.
```python
def softmax(x):
    e = np.exp(x - x.max())
    return e / e.sum()

d, blk = 8, 4
pool_k = np.zeros((32, blk, d))               # 물리 블록 32개짜리 풀
pool_v = np.zeros((32, blk, d))
free = rng.permutation(32).tolist()           # 빈 블록을 아무 순서로

K, V = rng.normal(size=(2, 10, d))            # 시퀀스 하나, 10토큰
table = []                                    # 블록 테이블: 논리 → 물리
for t in range(10):
    if t % blk == 0:
        table.append(free.pop())              # 블록이 차면 새로 받는다
    pool_k[table[-1], t % blk] = K[t]
    pool_v[table[-1], t % blk] = V[t]
print("블록 테이블", table)

q = rng.normal(size=d)
Kp = pool_k[table].reshape(-1, d)[:10]        # 테이블로 모아 읽기
Vp = pool_v[table].reshape(-1, d)[:10]
paged_out = softmax(Kp @ q / np.sqrt(d)) @ Vp
contig_out = softmax(K @ q / np.sqrt(d)) @ V
print(np.abs(paged_out - contig_out).max())
```
```text
블록 테이블 [15, 17, 0]
0.0
```

10토큰짜리 시퀀스가 흩어진 물리 블록 15, 17, 0번에 저장되었지만, 블록 테이블로 모아 읽은 어텐션 결과는 연속 메모리에서 계산한 것과 정확히 같다(0.0). 블록이 모두 같은 크기라 외부 단편화가 없고, 내부 낭비는 마지막 블록 하나로 제한된다. 논문은 같은 지연 수준에서 FasterTransformer, Orca 같은 기존 시스템보다 처리량을 2~4배 높였다고 보고했다.

## 접두사 공유
블록 테이블을 쓰면 여러 요청이 같은 물리 블록을 가리킬 수 있다. 같은 시스템 프롬프트로 시작하는 요청들, 한 프롬프트에서 답을 여러 개 뽑는 병렬 샘플링, 빔 서치는 앞부분의 KV가 같으므로 블록을 한 번만 저장하고 참조 횟수를 센다. 누군가 공유 블록에 새 토큰을 쓰려 할 때만 복사한다(copy-on-write, 운영체제의 fork와 같은 방식). 요청이 끝난 뒤에도 접두사 블록을 남겨 두었다가 재사용하면 같은 접두사의 프리필 자체를 건너뛸 수 있다(접두사 캐싱).

## 플래시 디코딩: KV 길이 방향으로 나누기
플래시 어텐션(7편)은 배치, 헤드, 쿼리 블록 방향으로 일을 나눠 GPU의 SM들에 뿌린다. 그런데 디코드에서는 쿼리가 토큰 하나뿐이라, 배치가 작으면 일감이 SM 수보다 적어 대부분의 SM이 논다. 문맥이 길수록 한 SM이 긴 KV 전체를 혼자 읽느라 더 느려진다.

**플래시 디코딩**(Flash-Decoding, Dao 등, 2023)은 KV를 길이 방향으로 여러 조각으로 나눠 각 조각을 서로 다른 SM이 동시에 계산한다. 조각마다 7편의 (최댓값 m, 지수 합 ℓ, 정규화 전 출력 o)를 내고, 마지막에 전체 최댓값 M으로 기준을 맞춰 합친다.
```text
M = max(mᵢ)
ℓ = Σ ℓᵢ·exp(mᵢ − M)
출력 = Σ oᵢ·exp(mᵢ − M) / ℓ
```
```python
d, T, chunks = 128, 8192, 8
q = rng.normal(size=d)
K, V = rng.normal(size=(2, T, d))
full = softmax(K @ q / np.sqrt(d)) @ V

parts = []                                    # 조각마다 (m, l, o)
for Kc, Vc in zip(np.split(K, chunks), np.split(V, chunks)):
    s = Kc @ q / np.sqrt(d)                   # 각 조각은 따로 계산된다
    m = s.max()
    p = np.exp(s - m)
    parts.append((m, p.sum(), p @ Vc))

M = max(m for m, _, _ in parts)               # 전체 최댓값으로 맞춘다
L = sum(l * np.exp(m - M) for m, l, _ in parts)
O = sum(o * np.exp(m - M) for m, _, o in parts) / L
print(np.abs(O - full).max())
```
```text
1.0408340855860843e-16
```

8,192개 KV를 8조각으로 나눠 따로 계산한 뒤 합친 결과가 전체를 한 번에 계산한 결과와 10⁻¹⁶ 수준으로 같다. 조각들은 서로 기다리지 않으므로 모두 병렬로 실행되고, 합치는 단계는 조각 수만큼의 작은 계산이다. 2023년 발표 글은 CodeLlama-34B로 아주 긴 시퀀스를 생성할 때 최대 8배 빨라졌다고 보고했다.

## 정리
- 프리필은 연산 바운드, 디코드는 메모리 바운드이며, 디코드 어텐션은 배치를 키워도 산술 강도가 오르지 않는다.
- 연속 예약은 예약·내부·외부 단편화로 메모리를 낭비하고, 페이지드 어텐션은 고정 크기 블록과 블록 테이블로 낭비를 마지막 블록 하나로 줄인다.
- 블록 테이블 덕분에 접두사가 같은 요청들은 KV 블록을 공유하고, 쓸 때만 복사한다.
- 플래시 디코딩은 KV를 길이 방향으로 나눠 병렬로 계산한 뒤 (m, ℓ, o)를 온라인 소프트맥스 식으로 합치며, 결과는 정확히 같다.
