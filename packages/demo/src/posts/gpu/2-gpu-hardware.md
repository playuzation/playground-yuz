# [GPU와 CUDA 2/14] GPU 하드웨어 구조: GPC, SM, 워프 스케줄러, 텐서 코어

> **한 줄 요약** — 엔비디아 GPU는 GPC → TPC → SM의 계층으로 같은 블록을 수십~수백 개 복제한 칩이고, SM 하나는 워프 스케줄러를 하나씩 가진 네 분할과 공유 L1으로 이루어지며, 이론 FLOPS는 SM 수 × 클록당 FMA 수 × 2 × 클록으로 계산되어 A100의 공개 수치와 부스트 클록에 정확히 맞는다.

## 이 글에서 다루는 것
- 칩 전체의 계층: GPC, TPC, SM, 그리고 L2와 HBM
- SM 안: 네 분할, 워프 스케줄러, FP32·INT32·FP64 유닛, 텐서 코어, 로드·스토어, SFU
- 레지스터 파일에서 HBM까지 저장 계층
- A100과 H100 SXM5의 실제 수치와 이론 FLOPS 계산(공개 수치에서 클록 역산)

## 같은 블록을 복제한 칩
1편에서 GPU는 지연을 수많은 워프로 가린다고 했다. 그러려면 같은 계산 블록을 최대한 많이 깔아야 하고, 설계도 그렇게 되어 있다. 엔비디아 데이터센터 GPU의 계층은 다음과 같다(Hopper 세대 GH100 다이 기준).
```text
GPU (GH100 full die)
├─ 8 GPC
│  └─ 9 TPC per GPC
│     └─ 2 SM per TPC = 144 SM
├─ L2 cache, shared by all SMs
└─ HBM3 memory controllers
```
**GPC**(graphics processing cluster)는 TPC 여러 개를 묶은 가장 큰 단위로 이름은 그래픽 시절에서 왔고, **TPC**(texture processing cluster)는 SM 두 개를 묶은 단위다. 계산의 실제 단위는 **SM**(streaming multiprocessor)이다. CUDA 블록은 SM 하나에 통째로 배정되고(4편), 공유 메모리와 레지스터도 SM 단위로 나뉜다.

제품은 다이 전체를 켜지 않는다. 다이가 크면 어딘가에 결함이 있을 확률이 높으므로, 결함 있는 SM을 끄고 파는 것이 수율을 올린다. GH100 다이는 SM이 144개지만 H100 SXM5는 132개, H100 PCIe는 114개만 켠다. A100은 GA100 다이(SM 128개) 중 108개를 켠다.

## SM 안: 네 분할과 공유 L1
SM은 다시 네 개의 **분할**(processing block, 서브 파티션)로 나뉜다. 분할마다 워프 스케줄러와 디스패치 유닛, 64KB 레지스터 파일(32비트 레지스터 16,384개), 계산 유닛이 있고, 네 분할이 L1 데이터 캐시·공유 메모리를 함께 쓴다.
```text
SM (Hopper, H100)
┌─────────────────────────┐
│ L1 instruction cache    │
│ [part 0]     [part 1]   │
│ [part 2]     [part 3]   │
│ 256KB L1 / shared mem   │
│ texture units           │
└─────────────────────────┘
one partition
┌─────────────────────────┐
│ warp scheduler+dispatch │
│ 64KB register file      │
│ FP32 x32   FP64 x16     │
│ INT32 units             │
│ 1 tensor core           │
│ LD/ST units, SFU        │
└─────────────────────────┘
```
- **워프 스케줄러**(warp scheduler): 매 사이클 자기 분할에 배정된 워프 중 다음 명령이 준비된 것 하나를 골라 명령 하나를 낸다. SM 하나가 사이클마다 최대 네 워프의 명령을 내는 셈이다.
- **FP32·INT32·FP64 유닛**: 흔히 "CUDA 코어"라 부르는 것이 FP32 레인이다. 볼타(2017) 이후 INT32를 별도 유닛으로 두어, 주소 계산 같은 정수 명령과 실수 명령을 동시에 흘릴 수 있다.
- **텐서 코어**(tensor core): 작은 행렬 곱-누적을 한 명령으로 처리하는 유닛이다. 분할마다 하나, SM당 넷이다(11편).
- **로드·스토어 유닛**(LD/ST): 메모리 명령의 주소를 계산해 L1·공유 메모리로 보낸다.
- **SFU**(special function unit): sin, cos, 역제곱근 같은 초월 함수를 근사 계산한다.

레인이 32개가 아니라는 점이 중요하다. A100 분할의 FP32 레인은 16개라서 32스레드 워프의 FP32 명령 하나가 유닛을 2사이클 점유한다. 그동안 스케줄러는 다른 워프의 정수 명령이나 메모리 명령을 낼 수 있다. H100은 분할당 FP32 레인을 32개로 늘렸다.

먼저 백서의 구성으로 유닛 수를 세어 백서가 밝힌 합계와 맞춰 보자.
```python
# 백서의 구성으로 유닛 수를 세고 백서의 합계와 대조한다
cfg = {  # 이름: (켜진 SM, SM당 FP32 레인, SM당 텐서 코어, 백서 FP32 합계)
    "A100": (108, 64, 4, 6912),
    "H100 SXM5": (132, 128, 4, 16896),
}
print("GH100 다이 전체 SM:", 8 * 9 * 2)       # GPC 8 × TPC 9 × SM 2
for name, (sm, fp32, tc, total) in cfg.items():
    lanes = fp32 // 4                          # 분할 하나의 FP32 레인
    print(f"{name}: FP32 {sm * fp32}개(백서와 같음 {sm * fp32 == total}),",
          f"텐서 코어 {sm * tc}개")
    print(f"  분할당 FP32 {lanes}개 → 워프 명령 하나에 {32 // lanes}사이클")
```
```text
GH100 다이 전체 SM: 144
A100: FP32 6912개(백서와 같음 True), 텐서 코어 432개
  분할당 FP32 16개 → 워프 명령 하나에 2사이클
H100 SXM5: FP32 16896개(백서와 같음 True), 텐서 코어 528개
  분할당 FP32 32개 → 워프 명령 하나에 1사이클
```

## 저장 계층: 레지스터에서 HBM까지
- **레지스터 파일**: SM당 256KB(32비트 65,536개)를 상주 스레드가 나눠 가진다. 스레드당 레지스터를 많이 쓰면 동시에 올릴 수 있는 워프가 줄어든다(8편).
- **L1 데이터 캐시·공유 메모리**: 같은 SRAM을 나눠 쓴다. A100은 SM당 192KB 중 공유 메모리를 최대 164KB, H100은 256KB 중 최대 228KB까지 설정할 수 있다. 마이크로벤치마크로 잰 L1 적중 지연은 약 33사이클이다.
- **L2 캐시**: 모든 SM이 공유한다. A100 40MB, H100 SXM5 50MB이며, 두 칩 모두 L2가 둘로 나뉘어 있어 먼 쪽 절반은 더 느리다(A100 측정값 약 200~400사이클).
- **HBM**: 다이 옆에 적층 메모리를 붙인다. A100 40GB는 약 1.6TB/s, H100 SXM5는 80GB HBM3에 3.35TB/s다. 구조는 메모리 시스템 8편 「HBM과 GDDR: 넓게 쌓은 메모리와 빠르게 달리는 메모리」에서 다룬다.

## 이론 FLOPS 계산하기
이론 최대 FLOPS는 `SM 수 × SM당 클록당 FMA 수 × 2 × 클록`이다. FMA(곱셈-누적) 하나를 곱셈과 덧셈 두 연산으로 센다. 클록을 넣는 대신 공개 수치에서 클록을 거꾸로 풀어 보면 계산이 맞는지 확인할 수 있다. A100 텐서 코어는 클록당 FP16 FMA 256개, H100은 512개(밀집 행렬 기준)로 놓았다.
```python
# 이론 FLOPS = SM 수 × 클록당 FMA 수 × 2(곱셈 + 덧셈) × 클록
# 공개 수치에서 클록을 거꾸로 풀어 본다
spec = [  # (이름, SM 수, SM당 클록당 FMA, 공개 TFLOPS)
    ("A100 FP32", 108, 64, 19.5),
    ("A100 FP16 텐서", 108, 4 * 256, 312),
    ("H100 FP32", 132, 128, 67),
    ("H100 FP16 텐서", 132, 4 * 512, 989.4),
]
for name, sm, fma, pub in spec:
    ghz = pub * 1e3 / (sm * fma * 2)
    print(f"{name}: {pub} TFLOPS → 클록 {ghz:.2f}GHz")
print("H100 텐서를 1.98GHz로 계산:", round(132 * 4 * 512 * 2 * 1.98 / 1e3),
      "TFLOPS")
```
```text
A100 FP32: 19.5 TFLOPS → 클록 1.41GHz
A100 FP16 텐서: 312 TFLOPS → 클록 1.41GHz
H100 FP32: 67 TFLOPS → 클록 1.98GHz
H100 FP16 텐서: 989.4 TFLOPS → 클록 1.83GHz
H100 텐서를 1.98GHz로 계산: 1071 TFLOPS
```

A100은 두 수치 모두 공개 부스트 클록 1,410MHz와 정확히 맞는다. 유닛 수와 공식이 옳다는 대조다. H100 SXM5는 FP32 수치가 1.98GHz, 텐서 수치가 1.83GHz에 해당한다. 두 공개 수치가 같은 클록으로 계산되지 않았다는 뜻으로, 1.98GHz를 그대로 넣으면 1,071TFLOPS가 되어 공개값보다 8% 크다. 텐서 코어를 가득 돌리면 전력 한계 때문에 클록이 내려간다는 점을 반영한 것으로 보인다. 어느 쪽이든 실제 커널은 클록 변동과 메모리 대기 때문에 이론치보다 낮게 나온다.

이 수치를 메모리 대역폭과 나란히 놓으면 GPU가 무엇에 굶주렸는지 보인다(앞 코드에 이어서).
```python
# 대역폭 1바이트당 몇 FLOP을 해야 계산 유닛이 쉬지 않나, 칩 안 저장 공간
for name, tbs, f32, f16 in [("A100 40GB", 1.555, 19.5, 312),
                            ("H100 SXM5", 3.35, 67, 989.4)]:
    print(f"{name}: FP32 {f32 / tbs:.0f}, FP16 텐서 {f16 / tbs:.0f} FLOP/B")
for name, sm, l2 in [("A100", 108, 40), ("H100 SXM5", 132, 50)]:
    print(f"{name}: 레지스터 합 {sm * 256 / 1024:.1f}MB, L2 {l2}MB")
```
```text
A100 40GB: FP32 13, FP16 텐서 201 FLOP/B
H100 SXM5: FP32 20, FP16 텐서 295 FLOP/B
A100: 레지스터 합 27.0MB, L2 40MB
H100 SXM5: 레지스터 합 33.0MB, L2 50MB
```

H100 SXM5에서 텐서 코어를 쉬지 않게 하려면 HBM에서 읽은 1바이트마다 약 300번 연산해야 한다. 세대가 바뀔 때 FLOPS가 대역폭보다 빨리 늘어서 이 비율은 커지는 추세다. 데이터를 칩 안에 붙잡아 두고 재사용하는 타일링(10편)과 루프라인 분석(13편)이 필요한 이유다. 레지스터 파일을 다 합치면 33MB로 L2(50MB)의 3분의 2에 이른다. CPU에서는 상상하기 어려운 비율이고, 1편에서 본 "모든 워프의 상태를 칩 위에 올려 두는" 설계의 비용이다.

## 코드에 주는 의미
- 블록 수는 SM 수보다 훨씬 많게 잡는다. 132개 SM에 블록 100개를 보내면 32개 SM이 논다(블록 배정은 4편, 점유율은 8편).
- 정수 주소 계산은 별도 유닛에서 실수 연산과 겹친다. 반대로 FP64를 많이 쓰면 FP64 유닛(A100은 SM당 32개)이 병목이 된다.
- 행렬 곱이라면 텐서 코어를 써야 한다. H100 SXM5에서 FP16 텐서는 FP32 레인의 약 15배다(989.4 ÷ 67).
- "CUDA 코어 수 × 클록"만 보고 GPU를 비교하지 않는다. 메모리 대역폭과 L2, 텐서 코어 세대가 실제 성능을 더 자주 가른다.

| 항목 | A100 | H100 SXM5 |
|---|---|---|
| SM(다이 전체) | 108(128) | 132(144) |
| SM당 FP32 레인 | 64 | 128 |
| SM당 텐서 코어 | 4(3세대) | 4(4세대) |
| SM당 L1·공유 | 192KB | 256KB |

모두 엔비디아 백서·제품 사양의 값이다. A100의 HBM 수치는 40GB 모델 기준이고, 80GB 모델은 약 2TB/s다. 희소 행렬(2:4 희소성) 수치는 밀집의 두 배로 공개되지만 여기서는 쓰지 않았다.

## 어디에 쓰이나
- 어텐션 7편 「플래시 어텐션: 메모리 계층을 아는 정확한 어텐션」: SM당 L1·공유 메모리 크기가 플래시 어텐션의 블록 크기를 정하고, FlashAttention-3가 쓰는 H100의 TMA와 워프 특화도 이 SM 구조 위에서 돈다.
- 양자화 12편 「KV 캐시·활성값·FP8: 추론과 학습의 저정밀화」: H100의 4세대 텐서 코어가 FP8을 지원하면서 FP8 학습·추론이 실용화되었다.
- 트랜지스터에서 자연어까지 4편 「순차 회로: 클록, 플립플롭, 메모리」: 레지스터 파일과 L1을 이루는 SRAM이 그 글의 래치·메모리 회로다.
- CUDA 런타임의 `cudaGetDeviceProperties`가 돌려주는 SM 수(`multiProcessorCount`)와 Nsight Compute가 보여 주는 클록·대역폭 지표가 이 글의 숫자들이다.

## 정리
- GPU는 GPC → TPC → SM으로 같은 블록을 복제한 칩이고, 결함 있는 SM을 꺼서 수율을 맞춘다(GH100 144개 중 H100 SXM5는 132개).
- SM은 워프 스케줄러를 하나씩 가진 네 분할과 공유 L1·공유 메모리로 이루어지며, 분할마다 FP32·INT32·FP64 유닛, 텐서 코어, 로드·스토어, SFU가 있다.
- 이론 FLOPS = SM 수 × 클록당 FMA × 2 × 클록. A100은 1.41GHz로 FP32와 텐서 수치가 모두 맞고, H100 SXM5의 공개 수치는 FP32와 텐서가 서로 다른 클록(1.98GHz, 1.83GHz)에 해당한다.
- 대역폭 1바이트당 필요한 연산이 FP16 텐서 기준 200~300번이라, 데이터 재사용 없이는 계산 유닛을 채울 수 없다.
