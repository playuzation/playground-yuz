# [GPU와 CUDA 7/14] 공유 메모리와 뱅크 충돌: 32개 뱅크를 동시에 쓰기

> **한 줄 요약** — 공유 메모리는 4바이트 워드를 차례로 32개 뱅크에 나눠 담아 워프의 32개 접근을 한 번에 처리하지만, 같은 뱅크의 서로 다른 워드를 읽는 스레드가 있으면 그 수만큼 나뉘어 처리되고(보폭 s면 gcd(s, 32)배), 행렬 전치에서는 타일에 열 하나를 덧대는 것만으로 32배 충돌이 사라진다.

## 이 글에서 다루는 것
- 공유 메모리의 32개 뱅크와 주소 → 뱅크 규칙
- 뱅크 충돌과 방송, 파이썬 충돌 계산기와 `gcd(보폭, 32)` 대조
- 행렬 전치: 타일로 병합을 살리고 +1 패딩으로 충돌 없애기
- `__syncthreads()`가 왜 필요한가(빠뜨렸을 때 틀리는 원소 세기)

## 32개 뱅크
5편에서 공유 메모리는 SM 안의 SRAM이라 L1처럼 빠르다고 했다. 워프 32개 스레드가 한 사이클에 각자 다른 주소를 읽으려면 포트가 32개인 메모리가 필요한데, 그런 SRAM은 크고 비싸다. 그래서 공유 메모리는 독립적으로 읽고 쓸 수 있는 **뱅크**(bank) 32개로 나뉜다. 연속된 4바이트 워드가 차례로 다음 뱅크에 놓이므로 `뱅크 = (바이트 주소 ÷ 4) mod 32`이고, 뱅크마다 사이클당 4바이트를 내보낸다. SM 하나에서 사이클당 128바이트다.
```text
word : 0  1  2 ... 31 32 33 ...
bank : 0  1  2 ... 31  0  1 ...
float s[64]: s[0] and s[32]
             share bank 0
```
워프의 32개 주소가 모두 다른 뱅크에 있으면 한 번에 끝난다. 같은 뱅크의 **서로 다른 워드**를 원하는 스레드가 k개면 그 뱅크는 k번에 나눠 처리해야 하고, 워프 전체가 가장 붐비는 뱅크를 기다린다. 이것이 **k-way 뱅크 충돌**(bank conflict)이다. 반대로 여러 스레드가 **같은 워드**를 읽으면 값을 한 번 읽어 나눠 주는 **방송**(broadcast)이라 충돌이 아니다. 같은 워드 안의 다른 바이트를 읽는 것도 마찬가지다.

## 충돌 계산기
```python
def ways(addrs):
    """워프의 공유 메모리 바이트 주소들 → 처리 단계 수(충돌 차수).
    뱅크 = (주소 // 4) % 32. 같은 4바이트 워드는 방송되어 한 번에 끝난다."""
    banks = {}
    for a in addrs:
        word = a // 4
        banks.setdefault(word % 32, set()).add(word)  # 뱅크별 서로 다른 워드
    return max(len(w) for w in banks.values())

lane = range(32)
pat = {
    "s[lane]": [4 * l for l in lane],
    "s[2*lane]": [8 * l for l in lane],
    "s[3*lane]": [12 * l for l in lane],
    "s[32*lane]": [128 * l for l in lane],
    "s[0] (모두 같은 주소)": [0] * 32,
    "s[lane/4] (4개씩 공유)": [4 * (l // 4) for l in lane],
    "char c[lane]": [l for l in lane],
}
for name, addrs in pat.items():
    print(f"{name}: {ways(addrs)}-way")
```
```text
s[lane]: 1-way
s[2*lane]: 2-way
s[3*lane]: 1-way
s[32*lane]: 32-way
s[0] (모두 같은 주소): 1-way
s[lane/4] (4개씩 공유): 1-way
char c[lane]: 1-way
```

보폭 2는 짝수 뱅크만 쓰므로 뱅크마다 워드 둘이 몰려 2-way, 보폭 32는 모두 뱅크 0에 몰려 32-way다. 보폭 3은 3과 32가 서로소라 32개 뱅크를 한 번씩 돈다. 일반적으로 워드 단위 보폭 s의 충돌 차수는 `gcd(s, 32)`다. 스레드 l의 뱅크 `(o + s·l) mod 32`가 같은 값으로 돌아오는 주기가 `32 / gcd(s, 32)`이기 때문이다. 무작위 보폭과 시작 위치로 대조한다(앞 코드에 이어서).
```python
import math, random
rng = random.Random(9)
ok = 0
for _ in range(300):
    s, o = rng.randint(1, 96), rng.randint(0, 1000)    # 워드 단위 보폭, 시작
    ok += ways([4 * (o + s * l) for l in lane]) == math.gcd(s, 32)
print(f"무작위 300개 비교: 충돌 차수 = gcd(보폭, 32) 일치 {ok}/300")
```
```text
무작위 300개 비교: 충돌 차수 = gcd(보폭, 32) 일치 300/300
```

6편의 전역 메모리 병합과 비교하면 규칙이 다르다는 점이 중요하다. 전역 메모리는 주소가 **가까워야** 섹터가 줄고, 공유 메모리는 주소가 **뱅크에 고르게 퍼져야** 한다. 보폭 3은 전역 메모리에서 섹터 12개(효율 33%)지만 공유 메모리에서는 충돌이 없다. 8바이트·16바이트 접근은 요청이 여러 단계로 나뉘어 처리되며 세부 규칙은 세대마다 다르므로, 여기서는 4바이트 접근만 다룬다.

## 행렬 전치: 타일과 +1 패딩
n×n 행렬 전치 `out[x][y] = in[y][x]`는 두 규칙이 부딪치는 대표 문제다. 행 방향으로 읽으면 쓰기가 열 방향이 되어, 6편의 기준으로 워프마다 섹터 32개를 쓴다. 해법은 32×32 타일을 공유 메모리에 행으로 읽어 들인 뒤 열로 꺼내, 전역 메모리 읽기와 쓰기를 모두 행 방향(병합)으로 만드는 것이다. 그런데 타일을 `float tile[32][32]`로 잡으면 열로 꺼낼 때 보폭이 32워드라 32-way 충돌이 난다. 행 폭을 33으로 늘리면 보폭이 33이 되고 `gcd(33, 32) = 1`이라 충돌이 사라진다(직접 실행하지 않은 읽기용 코드다).
```cuda
#define TILE 32
// n×n 행렬, n은 32의 배수. 실행: dim3 block(TILE, TILE), grid(n/TILE, n/TILE)
__global__ void transpose(float* out, const float* in, int n)
{
    __shared__ float tile[TILE][TILE + 1];   // +1: 열 읽기의 충돌 제거
    int x = blockIdx.x * TILE + threadIdx.x;
    int y = blockIdx.y * TILE + threadIdx.y;
    tile[threadIdx.y][threadIdx.x] = in[y * n + x];   // 병합된 읽기
    __syncthreads();                                   // 타일이 다 찰 때까지
    x = blockIdx.y * TILE + threadIdx.x;               // 블록 위치를 맞바꿔
    y = blockIdx.x * TILE + threadIdx.y;
    out[y * n + x] = tile[threadIdx.x][threadIdx.y];   // 병합된 쓰기
}
```
타일 하나(워프 32개)를 처리하는 비용을 세 가지 방식으로 센다. 전역 메모리는 6편의 섹터 수, 공유 메모리는 충돌 차수를 더한 처리 단계 수다(앞 코드에 이어서).
```python
def sectors(addrs):                       # 6편: 32바이트 섹터 수
    return len({a // 32 for a in addrs})

def transpose_cost(n, shared, pad=0):
    """n×n 행렬 전치에서 32×32 타일 하나(워프 32개)의 비용.
    워프 = threadIdx.y가 같은 32개 스레드, tx = 0..31."""
    W = 32 + pad                          # 공유 타일의 행 폭(워드)
    g = sm = 0
    for ty in range(32):
        g += sectors([4 * (ty * n + tx) for tx in range(32)])     # in 읽기
        if shared:
            sm += ways([4 * (ty * W + tx) for tx in range(32)])   # 타일 쓰기
            sm += ways([4 * (tx * W + ty) for tx in range(32)])   # 타일 읽기
            g += sectors([4 * (ty * n + tx) for tx in range(32)]) # out 쓰기
        else:
            g += sectors([4 * (tx * n + ty) for tx in range(32)]) # 열로 쓰기
    return g, sm

for name, args in [("공유 메모리 없이", (False,)), ("타일[32][32]", (True, 0)),
                   ("타일[32][33]", (True, 1))]:
    g, sm = transpose_cost(1024, *args)
    print(f"{name}: 전역 섹터 {g}, 공유 메모리 단계 {sm}")
```
```text
공유 메모리 없이: 전역 섹터 1152, 공유 메모리 단계 0
타일[32][32]: 전역 섹터 256, 공유 메모리 단계 1056
타일[32][33]: 전역 섹터 256, 공유 메모리 단계 64
```

공유 메모리 없이 전치하면 읽기 128섹터에 쓰기 1,024섹터가 든다. 타일을 쓰면 전역 섹터가 256개로 4.5배 줄지만, 패딩이 없으면 열 읽기 32번이 각각 32단계라 공유 메모리에서 1,056단계를 쓴다. 패딩 한 열(타일당 128바이트)로 64단계, 즉 워프 명령마다 한 단계가 된다. 패딩 대신 열 번호를 행 번호와 XOR해 섞는 **스위즐**(swizzle) 배치도 같은 목적을 이루며, CUTLASS 같은 라이브러리와 H100의 TMA가 이 방식을 쓴다.

## `__syncthreads()`: 다 쓴 뒤에 읽는다
전치 커널에서 스레드 (tx, ty)가 꺼내는 `tile[tx][ty]`는 다른 워프(threadIdx.y = tx)가 써 넣은 값이다. 워프들은 서로 다른 속도로 진행하므로, 모든 워프가 쓰기를 마칠 때까지 기다리는 장벽이 필요하다. `__syncthreads()`는 블록의 모든 스레드가 그 지점에 도착할 때까지 기다리게 하고, 그 전의 공유 메모리 쓰기가 블록 전체에 보이게 한다. 장벽이 없을 때 가능한 실행 순서 하나(워프마다 쓰기와 읽기를 연달아 하는 순서)를 흉내 내어, 정의 그대로의 전치와 비교한다(앞 코드에 이어서).
```python
def tiled_transpose(A, barrier, pad=1):
    """블록 하나(32×32 스레드)의 전치를 워프 순서대로 흉내 낸다.
    barrier=False면 워프마다 쓰기와 읽기를 연달아 해 버린다."""
    tile = [[None] * (32 + pad) for _ in range(32)]
    out = [[None] * 32 for _ in range(32)]
    def write(ty):
        for tx in range(32):
            tile[ty][tx] = A[ty][tx]
    def read(ty):
        for tx in range(32):
            out[ty][tx] = tile[tx][ty]
    if barrier:                            # __syncthreads(): 모두 쓴 뒤 읽기
        for ty in range(32): write(ty)
        for ty in range(32): read(ty)
    else:
        for ty in range(32): write(ty); read(ty)
    return out

A = [[rng.random() for _ in range(32)] for _ in range(32)]
T = [list(r) for r in zip(*A)]             # 정의 그대로의 전치
for b in (True, False):
    out = tiled_transpose(A, barrier=b)
    bad = sum(out[i][j] != T[i][j] for i in range(32) for j in range(32))
    print(f"__syncthreads {'있음' if b else '없음'}: 틀린 원소 {bad}/1024")
```
```text
__syncthreads 있음: 틀린 원소 0/1024
__syncthreads 없음: 틀린 원소 496/1024
```

장벽이 있으면 정의 그대로의 전치와 완전히 같다. 장벽이 없으면 워프 ty가 읽을 때 아직 아무도 쓰지 않은 행이 31 − ty개라 합쳐서 496개가 틀린다. 실제 GPU에서 워프 순서는 매번 달라서 틀리는 개수도 실행마다 다를 수 있고, 그래서 이런 버그는 재현이 어렵다. `__syncthreads()`는 블록의 모든 스레드가 도달해야 하므로, 스레드마다 결과가 다른 조건문 안에 두면 커널이 멈출 수 있다.

## 코드에 주는 의미
- 공유 메모리 배열의 접근 보폭이 2의 거듭제곱이면 의심한다. 행 폭을 홀수로 만드는 패딩 한 열이 가장 싼 해법이다.
- 워프의 여러 스레드가 같은 값을 읽는 것은 방송이라 괜찮다. 충돌은 같은 뱅크의 **다른 워드**만이다.
- 전역 메모리는 가까이, 공유 메모리는 고르게 퍼지게. 둘이 부딪치면 공유 메모리 타일로 순서를 바꾼다.
- 공유 메모리를 채운 뒤와 다시 덮어쓰기 전에는 `__syncthreads()`를 둔다. Nsight Compute는 공유 메모리 뱅크 충돌 수를 지표로 보여 준다(13편).

## 정리
- 공유 메모리는 연속된 4바이트 워드를 32개 뱅크에 차례로 담고, 같은 뱅크의 서로 다른 워드를 원하는 스레드 수만큼 나뉘어 처리된다. 같은 워드는 방송이다.
- 워드 단위 보폭 s의 충돌 차수는 `gcd(s, 32)`이며, 무작위 300개 대조에서 계산기와 일치했다.
- 행렬 전치는 공유 메모리 타일로 전역 섹터를 1,152개에서 256개로 줄이고, `[32][33]` 패딩으로 공유 메모리 단계를 1,056에서 64로 줄인다.
- `__syncthreads()`가 없으면 다른 워프가 아직 쓰지 않은 값을 읽어, 흉내 낸 순서에서 1,024개 중 496개가 틀렸다.
