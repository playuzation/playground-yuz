# [GPU와 CUDA 8/14] 점유율과 지연 숨기기: 레지스터와 공유 메모리가 동시 워프 수를 정한다

> **한 줄 요약** — SM은 기다리는 워프 대신 준비된 워프의 명령을 발행해 지연을 숨기는데, 함께 올라갈 워프 수(점유율)는 워프·블록 슬롯과 레지스터·공유 메모리 중 먼저 바닥나는 자원이 정하고, 지연을 실제로 숨기는 것은 점유율이 아니라 기다리는 동안 발행할 독립 명령의 총량이다.

## 이 글에서 다루는 것
- 워프 교체가 공짜인 이유와 그 대가: 모든 워프의 상태가 SM 안에 상주한다
- 네 가지 한도로 점유율 계산하기(파이썬 계산기, 블록을 하나씩 넣는 방식과 대조)
- 지연 숨기기 시뮬레이션: 워프 수와 명령어 수준 병렬성(ILP)의 맞바꿈
- `__launch_bounds__`와 점유율 API

## 워프 교체는 공짜, 대신 자리가 한정된다
1편 「GPU는 왜 다르게 생겼나: 지연을 숨기는 처리량 기계」의 리틀의 법칙대로, 지연이 L 사이클인 메모리를 기다리는 동안 연산 장치를 놀리지 않으려면 L 사이클어치 다른 일이 있어야 한다. GPU의 답은 워프 교체다. 2편 「GPU 하드웨어 구조: GPC, SM, 워프 스케줄러, 텐서 코어」에서 본 SM의 네 분할마다 워프 스케줄러가 있고, 스케줄러는 매 사이클 자기 워프들 가운데 다음 명령의 피연산자가 준비된 워프 하나를 골라 발행한다. 적재 결과를 기다리는 워프는 그냥 건너뛴다.

CPU의 문맥 교환은 레지스터를 메모리에 저장하고 다시 불러와야 하지만, GPU의 워프 교체는 저장할 것이 없어 사이클 단위로 공짜다. SM에 올라간 모든 워프의 레지스터는 처음부터 끝까지 레지스터 파일에 자리를 차지하고, 블록의 공유 메모리도 블록이 끝날 때까지 SM 안에 머문다. 그래서 동시에 올라갈 수 있는 워프 수는 칩 안 저장 공간이 정한다.
```text
SM 하나 (H100, 계산 능력 9.0)
┌───────────────────────────┐
│ warp slots   64           │
│ block slots  32           │
│ registers    65536 x 32b  │
│ shared mem   228 KB       │
└───────────────────────────┘
blocks/SM = min(4 limits)
```

**점유율**(occupancy)은 SM에 상주하는 워프 수를 최대 워프 수로 나눈 값이다. 블록은 통째로만 들어가므로 네 자원 각각으로 들어갈 블록 수를 구해 가장 작은 값을 고른다.
- 워프 슬롯: SM당 최대 워프 ÷ 블록당 워프
- 블록 슬롯: SM당 최대 블록 수(계산 능력 9.0은 32)
- 레지스터: 워프당 `스레드당 레지스터 × 32`를 256개 단위로 올려 잡고, 네 분할이 16K개씩 나눠 가진다
- 공유 메모리: 블록당 요청량을 128바이트 단위로 올리고 블록마다 시스템 예약 1KB를 더한다

할당 단위는 엔비디아 점유율 계산기가 쓰는 값이고, 아래 계산기는 그 규칙을 단순화한 모델이다(공유 메모리는 L1과 나눠 쓰는 몫을 최대로 잡는다고 가정).
```python
# 계산 능력별 한도: (워프, 블록, SM당 공유 메모리 KB, 블록당 최대 KB)
LIMITS = {"8.0": (64, 32, 164, 163), "8.6": (48, 16, 100, 99),
          "9.0": (64, 32, 228, 227)}
REGS, SUBS = 65536, 4          # SM당 32비트 레지스터, 분할 4개

def up(x, g):                  # x를 g의 배수로 올림
    return -(-x // g) * g

def occupancy(cc, threads, regs, smem):
    warps, blocks, sm_kb, blk_kb = LIMITS[cc]
    w = up(threads, 32) // 32                  # 블록당 워프 수
    if threads > 1024 or regs > 255 or smem > blk_kb * 1024:
        return 0, "실행 불가"
    per_warp = up(regs * 32, 256)              # 워프당 256개 단위
    lim = {"워프": warps // w, "블록": blocks,
           "레지스터": SUBS * (REGS // SUBS // per_warp) // w,
           "공유 메모리": sm_kb * 1024 // (up(smem, 128) + 1024)}
    b = min(lim.values())
    return b * w / warps, (min(lim, key=lim.get) if b else "실행 불가")

for t, r, s in [(256, 32, 0), (256, 40, 0), (256, 64, 0),
                (128, 32, 48 * 1024), (32, 32, 0), (1024, 128, 0)]:
    res = [occupancy(cc, t, r, s) for cc in ("9.0", "8.6")]
    print(f"{t}스레드 R{r} {s // 1024}KB →",
          ", ".join(f"{o:.0%} {why}" for o, why in res))
```
```text
256스레드 R32 0KB → 100% 워프, 100% 워프
256스레드 R40 0KB → 75% 레지스터, 100% 워프
256스레드 R64 0KB → 50% 레지스터, 67% 레지스터
128스레드 R32 48KB → 25% 공유 메모리, 17% 공유 메모리
32스레드 R32 0KB → 50% 블록, 33% 블록
1024스레드 R128 0KB → 0% 실행 불가, 0% 실행 불가
```

R은 스레드당 레지스터 수이고, 화살표 뒤 앞쪽이 H100(9.0), 뒤쪽이 계산 능력 8.6이다. 256스레드 블록에서 레지스터를 32개 쓰면 H100에서 100%지만 40개면 75%, 64개면 50%로 레지스터가 먼저 바닥난다. 할당 단위 때문에 점유율은 계단식으로 변하고, SM당 워프가 48개인 8.6에서는 같은 커널의 비율이 다르다. 32스레드짜리 작은 블록은 다른 자원이 남아도 블록 슬롯에 걸리고, 1024스레드 × 레지스터 128개는 블록 하나에 레지스터 131,072개가 필요해 SM 전체(65,536개)를 넘으므로 아예 실행되지 않는다("too many resources requested for launch" 오류).

앞 코드에 이어서, 같은 규칙을 나눗셈 공식 대신 블록을 하나씩 SM에 넣어 보며 세는 방식으로 다시 구현하고 무작위 설정 300개를 비교한다.
```python
import random

def greedy(cc, threads, regs, smem):          # 블록을 하나씩 넣어 본다
    warps, blocks, sm_kb, blk_kb = LIMITS[cc]
    if threads > 1024 or regs > 255 or smem > blk_kb * 1024:
        return 0.0
    w, need_r = up(threads, 32) // 32, up(regs * 32, 256)
    need_s, sub = up(smem, 128) + 1024, [REGS // SUBS] * SUBS
    n = 0
    while (n + 1) * w <= warps and n < blocks and \
            (n + 1) * need_s <= sm_kb * 1024:
        for j in range(w):                     # 워프를 분할에 돌아가며
            sub[(n * w + j) % SUBS] -= need_r
        if min(sub) < 0:                       # 레지스터가 모자라다
            break
        n += 1
    return n * w / warps

rng, same = random.Random(8), 0
for _ in range(300):
    cfg = (rng.choice(list(LIMITS)), rng.randrange(1, 33) * 32,
           rng.randrange(16, 256), rng.randrange(0, 120) * 1024)
    same += occupancy(*cfg)[0] == greedy(*cfg)
print(f"무작위 300개 설정, 공식과 하나씩 넣기 비교: {same}개 일치")
```
```text
무작위 300개 설정, 공식과 하나씩 넣기 비교: 300개 일치
```

## 지연 숨기기: 워프 수 × 독립 명령
점유율은 수단이지 목표가 아니다. 스케줄러 하나를 모델로 세어 보자. 워프는 서로 독립인 적재 ILP개를 연달아 발행하고, 적재 하나당 계산 명령 C개를 실행한 뒤, 다음 적재 결과를 L 사이클 기다린다. 대기 한 번 사이에 발행하는 명령은 `work = ILP × (1 + C)`개다. 한 워프가 기다리는 동안 다른 워프들이 그 자리를 채워야 하므로 발행 슬롯 이용률은 `min(1, 워프 수 × work / (work + L))`이 된다. H100은 SM당 워프 64개를 스케줄러 4개가 나누므로 스케줄러당 16개가 점유율 100%다. 앞 코드에 이어서 실행한다.
```python
def simulate(warps, work, lat, periods=40):
    """스케줄러 하나: 매 사이클 준비된 워프 하나가 명령 하나를 발행"""
    ready, left = [0] * warps, [work] * warps
    T = periods * (work + lat)
    busy = 0
    for t in range(2 * T):                     # 앞 절반은 예열
        for w in range(warps):                 # 준비된 워프 중 번호 순
            if ready[w] <= t:
                busy += t >= T
                left[w] -= 1
                if left[w] == 0:               # 적재 결과를 기다린다
                    left[w], ready[w] = work, t + 1 + lat
                break
    return busy / T

LAT, C = 400, 4        # 가정: 메모리 지연 400사이클, 적재 1개당 계산 4개
match = True
for warps, ilp in [(16, 1), (16, 4), (8, 4), (8, 8), (16, 8)]:
    work = ilp * (1 + C)                       # 대기 한 번 사이의 명령 수
    sim = simulate(warps, work, LAT)
    formula = min(1, warps * work / (work + LAT))
    match &= abs(sim - formula) < 0.005
    print(f"워프 {warps} (점유율 {warps / 16:.0%}), ILP {ilp}:",
          f"이용률 {sim:.3f}, 공식 {formula:.3f}")
print("공식과 일치:", match)
```
```text
워프 16 (점유율 100%), ILP 1: 이용률 0.198, 공식 0.198
워프 16 (점유율 100%), ILP 4: 이용률 0.762, 공식 0.762
워프 8 (점유율 50%), ILP 4: 이용률 0.381, 공식 0.381
워프 8 (점유율 50%), ILP 8: 이용률 0.727, 공식 0.727
워프 16 (점유율 100%), ILP 8: 이용률 1.000, 공식 1.000
공식과 일치: True
```

ILP가 1이면 점유율 100%로도 이용률이 20%에 그친다. 400사이클을 이 방식으로 숨기려면 스케줄러당 워프가 81개 필요한데 자리는 16개뿐이다. 같은 100%에서 스레드마다 독립 적재를 4개씩 내면 76%가 되고, 점유율을 50%로 낮추더라도 ILP를 8로 올리면 73%로 100%·ILP 1보다 3.7배 높다. 2010년 GTC에서 바실리 볼코프(Vasily Volkov)가 「Better Performance at Lower Occupancy」로 보인 요점이 이것이다. 스레드 하나가 원소 여러 개를 맡으면 레지스터를 더 써서 점유율은 떨어지지만, 레지스터에 든 독립 연산들이 지연을 대신 숨긴다.

모델이 생략한 것도 있다. 실제 지연은 세대와 부하에 따라 다르고(400은 설명용 가정), 메모리 대역폭이 포화되면 워프나 ILP를 더 늘려도 빨라지지 않는다. `__syncthreads()`가 잦은 커널은 한 블록이 장벽에서 멈춘 동안 다른 블록이 있어야 하므로 블록 수도 중요하다.

## `__launch_bounds__`와 점유율 API
컴파일러는 기본적으로 레지스터를 넉넉히 쓴다. 블록 크기와 원하는 블록 수를 알려 주면 그에 맞춰 레지스터 수를 제한한다. 아래 CUDA 코드는 컨테이너에 GPU와 nvcc가 없어 직접 실행하지 않은 읽기용이다.
```cuda
#include <cstdio>

__global__ void __launch_bounds__(256, 4)   // 블록 ≤ 256스레드, SM당 4블록 이상
saxpy(int n, float a, const float* x, float* y) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) y[i] = a * x[i] + y[i];
}

int main() {
    int blocks = 0, minGrid = 0, best = 0;
    // 컴파일된 커널의 실제 레지스터·공유 메모리 사용량으로 계산
    cudaOccupancyMaxActiveBlocksPerMultiprocessor(&blocks, saxpy, 256, 0);
    cudaOccupancyMaxPotentialBlockSize(&minGrid, &best, saxpy, 0, 0);
    printf("SM당 블록 %d, 추천 블록 크기 %d\n", blocks, best);
    return 0;
}
```

`__launch_bounds__(256, 4)`는 "블록은 256스레드 이하이고, SM 하나에 이런 블록이 4개 이상 들어가게 하라"는 약속이다. SM의 레지스터가 65,536개이므로 컴파일러는 스레드당 레지스터를 65,536 ÷ (256 × 4) = 64개 이하로 맞추고, 모자라면 값을 로컬 메모리로 내보낸다(5편 「CUDA 메모리 계층: 레지스터, 공유, 전역, 상수, 로컬」의 스필). 스필이 L1에 걸리면 싸지만 넘치면 전역 메모리 트래픽이 되므로, 제한을 건 뒤에는 `nvcc -Xptxas -v`가 출력하는 레지스터 수와 스필 바이트를 확인한다. 파일 전체에 거는 `-maxrregcount` 옵션도 있다. Nsight Compute는 이론 점유율과 실행 중 측정한 달성 점유율(achieved occupancy)을 함께 보여 준다.

## 흔한 오해와 세대별 변화
- "점유율 100%가 목표다": 대역폭을 다 쓰거나 발행 슬롯이 차면 점유율을 더 올려도 소용없다.
- "블록을 키우면 점유율이 오른다": 블록이 크면 자원이 큰 덩어리로 잡힌다. 1024스레드 블록은 스레드당 레지스터가 64개를 넘는 순간 SM에 하나도 들어가지 못한다.
- 한도는 계산 능력마다 다르다. SM당 공유 메모리만 해도 V100 96KB, A100 164KB, H100 228KB로 늘었다. 블록·타일 크기를 세대마다 다시 고르는 이유다.

## 숫자로 보기
| 계산 능력(제품) | SM당 워프·블록 | 공유 메모리/SM |
|---|---|---|
| 8.0 (A100) | 워프 64, 블록 32 | 164KB |
| 8.6 (RTX 30 등) | 워프 48, 블록 16 | 100KB |
| 9.0 (H100) | 워프 64, 블록 32 | 228KB |

- 세 세대 공통: SM당 32비트 레지스터 65,536개, 스레드당 최대 255개, 블록당 최대 1,024스레드. 블록당 공유 메모리 최대는 SM당 값보다 1KB 작다(163·99·227KB). 출처는 엔비디아 Ampere·Hopper 튜닝 가이드다.

## 어디에 쓰이나
- 어텐션 7편 「플래시 어텐션: 메모리 계층을 아는 정확한 어텐션」: 타일을 키우면 HBM 왕복은 줄지만 블록당 공유 메모리와 레지스터가 늘어 SM에 들어가는 블록 수가 준다.
- CPU 마이크로아키텍처 11편 「멀티코어와 SMT: 하이퍼스레딩, 코어 연결망, NUMA」: SMT는 코어 하나에 스레드 상태를 두 벌 두고 번갈아 발행하는 같은 생각이고, GPU는 이를 SM당 수십 벌로 늘렸다.
- 10편 「행렬 곱셈 커널 최적화: 타일링에서 레지스터 블로킹까지」: 스레드당 출력을 늘려 점유율을 낮추는 대신 ILP와 재사용을 얻는 대표 사례다.

## 정리
- 워프 교체가 공짜인 대가로 모든 워프의 레지스터와 블록의 공유 메모리가 SM에 상주하고, 그 용량이 동시 워프 수를 정한다.
- SM당 블록 수는 워프 슬롯·블록 슬롯·레지스터·공유 메모리 한도의 최솟값이고, 할당 단위 반올림 때문에 레지스터 몇 개 차이로 점유율이 계단식으로 바뀐다.
- 지연을 숨기는 것은 워프 수 × 워프당 독립 명령이다. 모델에서 점유율 50%·ILP 8이 100%·ILP 1보다 3.7배 높았다.
- `__launch_bounds__`로 레지스터 상한을 정하고, 스필과 실제 점유율은 컴파일러 출력과 점유율 API, 프로파일러로 확인한다.
