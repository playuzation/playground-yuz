# [GPU와 CUDA 6/14] 메모리 병합: 전역 메모리를 32바이트 섹터로 읽기

> **한 줄 요약** — 워프가 전역 메모리를 읽으면 하드웨어는 32개 스레드의 주소를 모아 필요한 32바이트 섹터 수만큼만 트랜잭션을 만들므로, 이웃 스레드가 이웃 주소를 읽으면 섹터 4개로 끝나고 보폭이 커지거나 주소가 흩어지면 같은 데이터에 섹터 32개, 대역폭 효율 12.5%까지 떨어진다.

## 이 글에서 다루는 것
- 병합(coalescing): 워프의 32개 주소가 섹터와 라인으로 묶이는 규칙
- 연속·어긋남·보폭·무작위 접근의 섹터 수를 파이썬으로 세고 닫힌 식과 대조
- 구조체의 배열(AoS)과 배열의 구조체(SoA)
- 정렬과 벡터 적재(`float4`)

## 워프 단위로 메모리를 읽는다
5편에서 전역 메모리는 HBM에 있고 수백 사이클이 걸린다고 했다. 대역폭도 귀하다. H100 SXM5의 3.35TB/s를 132개 SM이 나누면 사이클당 SM 하나에 약 12.8바이트다(1편). 그런데 메모리 시스템은 바이트 하나씩 오가지 않는다. 계산 능력 6.0 이후 GPU에서 워프의 전역 메모리 접근은 32개 스레드의 주소를 모은 뒤, 그 주소들을 덮는 데 필요한 **32바이트 섹터**(sector) 수만큼의 트랜잭션으로 처리된다. L1 캐시의 라인은 128바이트(섹터 4개)이고, 섹터 단위로 채워진다.

이렇게 여러 스레드의 접근을 몇 개의 트랜잭션으로 합치는 것을 **병합**(coalescing)이라 한다. 스레드 t가 `in[t]`를 읽으면 32 × 4 = 128바이트가 연속이라 섹터 4개면 된다. 스레드 t가 `in[32·t]`를 읽으면 주소가 128바이트씩 떨어져 섹터 32개가 필요하고, 섹터마다 4바이트만 쓰고 28바이트는 버린다.
```text
warp loads in[t], t = 0..31
bytes 0     32    64    96   128
      |sec 0|sec 1|sec 2|sec 3|
      └──── one 128B line ────┘
warp loads in[32*t]
      t0 → sector 0   (4B used)
      t1 → sector 4   (4B used)
      ...  32 sectors, 12.5%
```

## 섹터 수 세기
워프의 바이트 주소 목록을 받아 건드리는 섹터와 라인을 센다. **효율**은 실제로 필요한 바이트를 옮긴 바이트(섹터 수 × 32)로 나눈 값이다. 배열 시작은 `cudaMalloc`처럼 256바이트에 정렬되어 있다고 둔다.
```python
import random

def sectors(addrs, size=4):
    """워프의 바이트 주소들 → 건드리는 32바이트 섹터 수, 128바이트 라인 수"""
    sec, line = set(), set()
    for a in addrs:
        for byte in (a, a + size - 1):       # 접근의 첫 바이트와 끝 바이트
            sec.add(byte // 32)
            line.add(byte // 128)
    return len(sec), len(line)

base = 4096                                  # cudaMalloc은 256바이트 정렬
rng = random.Random(8)
pat = {                                      # 이름: (스레드별 주소, 크기)
    "연속 float": ([base + 4 * t for t in range(32)], 4),
    "1칸 어긋남": ([base + 4 * (t + 1) for t in range(32)], 4),
    "보폭 2": ([base + 8 * t for t in range(32)], 4),
    "보폭 32": ([base + 128 * t for t in range(32)], 4),
    "무작위": ([base + 4 * rng.randrange(1 << 20) for t in range(32)], 4),
    "AoS의 x(12B 보폭)": ([base + 12 * t for t in range(32)], 4),
    "연속 float4": ([base + 16 * t for t in range(32)], 16),
}
for name, (addrs, size) in pat.items():
    s, l = sectors(addrs, size)
    eff = len(set(addrs)) * size / (32 * s)  # 필요한 바이트 ÷ 옮긴 바이트
    print(f"{name}: 섹터 {s}, 라인 {l}, 효율 {eff:.1%}")
```
```text
연속 float: 섹터 4, 라인 1, 효율 100.0%
1칸 어긋남: 섹터 5, 라인 2, 효율 80.0%
보폭 2: 섹터 8, 라인 2, 효율 50.0%
보폭 32: 섹터 32, 라인 32, 효율 12.5%
무작위: 섹터 32, 라인 32, 효율 12.5%
AoS의 x(12B 보폭): 섹터 12, 라인 3, 효율 33.3%
연속 float4: 섹터 16, 라인 4, 효율 100.0%
```

한 칸만 어긋나도 128바이트가 섹터 경계 다섯 곳에 걸쳐 80%가 된다. 보폭 2는 섹터마다 절반만 쓰고, 보폭이 float 8개(32바이트) 이상이면 스레드마다 섹터 하나씩이라 무작위 접근과 같아진다. 효율은 곧 유효 대역폭이다. 보폭 32로 읽는 커널은 H100 SXM5에서 3.35TB/s가 아니라 약 0.42TB/s 분량의 쓸모 있는 데이터만 받는다. 모든 스레드가 같은 주소를 읽는 경우는 섹터 하나로 방송된다.

닫힌 식으로도 셀 수 있다. 보폭 s와 어긋남 o(둘 다 float 단위)에서 s ≤ 8이면 이웃 스레드 사이가 32바이트 이내라 건너뛰는 섹터가 없으므로, 첫 섹터부터 마지막 섹터까지 연속 구간 `⌊(o + 31s)/8⌋ − ⌊o/8⌋ + 1`개다. s > 8이면 32개다. 시뮬레이터와 대조하고, `float`과 `float4`로 1MiB를 읽을 때의 명령 수도 세어 보자(앞 코드에 이어서).
```python
def formula(s, o):     # s: 보폭, o: 어긋남(둘 다 float 단위), 섹터 = float 8개
    if s <= 8:         # 이웃 스레드가 32바이트 이내라 건너뛰는 섹터가 없다
        return (o + 31 * s) // 8 - o // 8 + 1
    return 32          # 스레드마다 다른 섹터
ok = 0
for _ in range(300):
    s, o = rng.randint(0, 40), rng.randint(0, 63)
    got, _ = sectors([base + 4 * (o + s * t) for t in range(32)])
    ok += got == formula(s, o)
print(f"무작위 300개 비교: 공식과 일치 {ok}/300")
for size in (4, 16):   # 1MiB를 float과 float4로 읽을 때
    warps = (1 << 20) // (32 * size)
    s, _ = sectors([base + size * t for t in range(32)], size)
    print(f"{size}바이트씩: 워프 적재 명령 {warps}개, 섹터 {warps * s}개")
```
```text
무작위 300개 비교: 공식과 일치 300/300
4바이트씩: 워프 적재 명령 8192개, 섹터 32768개
16바이트씩: 워프 적재 명령 2048개, 섹터 32768개
```

## 커널에서는 이렇게 보인다
아래는 어긋남과 보폭을 바꿔 가며 복사하는 커널이다(직접 실행하지 않은 읽기용 코드다). `copyOffset`은 o가 8의 배수가 아니면 워프마다 섹터 5개, `copyStride`는 보폭이 커질수록 섹터가 32개까지 는다. 저장도 같은 규칙으로 섹터 단위로 처리된다.
```cuda
__global__ void copyOffset(float* out, const float* in, int o)
{
    int i = blockIdx.x * blockDim.x + threadIdx.x + o;
    out[i] = in[i];                       // 어긋난 연속 접근
}

__global__ void copyStride(float* out, const float* in, int s)
{
    int i = (blockIdx.x * blockDim.x + threadIdx.x) * s;
    out[i] = in[i];                       // 보폭 s 접근
}
```
2차원 배열에서 가장 흔한 실수는 `threadIdx.x`를 행 번호에 쓰는 것이다. 폭이 1,024인 행 우선 행렬에서 이웃 스레드가 이웃 행을 읽으면 보폭이 1,024라 섹터 32개다. `threadIdx.x`가 열(연속 주소) 방향을 맡게 해야 한다. 행 폭이 32의 배수가 아니면 행 시작이 섹터 경계에서 어긋나므로, `cudaMallocPitch`로 행마다 여백을 넣어 정렬을 맞추기도 한다.

## AoS와 SoA
입자마다 `x, y, z`를 묶은 구조체 배열(AoS, array of structures)은 객체 지향 코드에서 자연스럽지만, `x`만 갱신하는 커널에서는 12바이트 보폭이 되어 섹터 12개 중 3분의 1만 쓴다. 필드마다 배열을 따로 두는 배열의 구조체(SoA, structure of arrays)는 같은 일을 섹터 4개로 한다.
```cuda
struct Particle { float x, y, z; };       // AoS: 12바이트 구조체

__global__ void shiftAoS(Particle* p, int n, float dx)
{
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) p[i].x += dx;              // 12바이트 보폭
}

__global__ void shiftSoA(float* x, int n, float dx)
{
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) x[i] += dx;                // 4바이트 연속
}
```
세 필드를 모두 읽는 커널이라면 AoS도 결국 모든 섹터를 쓰므로 차이가 줄어든다. 무엇을 함께 읽는지에 따라 배치를 고른다는 원리는 CPU 캐시와 같다(메모리 시스템 4편 「캐시를 아는 코드: 접근 순서, 블로킹, 프리페치」). GPU에서는 워프 32개 스레드가 한꺼번에 읽기 때문에 차이가 더 크게 드러날 뿐이다.

## 정렬과 벡터 적재
`float4`(16바이트)로 읽으면 스레드 하나가 한 명령에 16바이트를 가져온다. 위 결과처럼 옮기는 섹터 수는 같지만 워프 적재 명령이 4분의 1로 줄어, 명령 발행과 주소 계산, 진행 중인 요청을 추적하는 자원이 덜 든다. 1편의 리틀의 법칙에서 `float4`면 SM당 워프 15개로 대역폭을 채울 수 있었던 이유다.
```cuda
__global__ void copyVec4(float4* out, const float4* in, int n4)
{
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n4) out[i] = in[i];           // 16바이트 적재·저장 한 번씩
}
```
조건은 정렬이다. 16바이트 적재는 주소가 16의 배수여야 한다. `cudaMalloc`이 돌려주는 주소는 256바이트 이상으로 정렬되어 있지만, 포인터에 1을 더해 넘기면 정렬이 깨진다. 원소 수가 4의 배수가 아니면 꼬리 원소는 따로 처리한다.

## 코드에 주는 의미
- 워프의 이웃 스레드가 이웃 주소를 읽게 인덱스를 배치한다. 2차원이면 `threadIdx.x`를 연속 방향에 쓴다.
- 일부 필드만 읽는 커널이 많으면 SoA로 바꾼다.
- 배열 시작과 행 시작을 32바이트(가능하면 128바이트) 경계에 맞춘다.
- 정렬이 보장되면 `float4` 같은 벡터 적재로 명령 수를 줄인다.
- 흩어진 접근이 피할 수 없다면(그래프, 해시 테이블) 공유 메모리에 모아 재배치하거나(7편) 정렬로 지역성을 만든다.

## 숫자로 보기
| 항목 | 값 | 근거 |
|---|---|---|
| 트랜잭션 단위 | 32바이트 섹터 | CUDA 가이드(CC 6.0~) |
| L1 라인 | 128바이트(섹터 4개) | 엔비디아 문서 |
| 워프의 float 적재 | 128바이트 = 섹터 4개 | 계산 |
| 최악(흩어진 float) | 섹터 32개, 효율 12.5% | 계산 |
| 할당 정렬 | 256바이트 이상 | CUDA 가이드 |
| H100 SXM5 대역폭 | 3.35TB/s | 제품 사양 |

규칙은 세대마다 조금씩 달랐다. 일부 예전 세대(계산 능력 3.x 등)는 L1에 캐시되는 적재를 128바이트 단위로 처리해 흩어진 접근의 낭비가 더 컸다. 6.0 이후의 32바이트 규칙에서도 연속 접근이 최선이라는 원칙은 그대로다.

## 어디에 쓰이나
- 메모리 시스템 5편 「DRAM의 구조: 1T1C 셀, 뱅크, 행 버퍼, 리프레시」: DRAM도 행 버퍼와 버스트 단위로 읽으므로, 연속 접근이 유리한 이유가 칩 안의 섹터에서 DRAM 셀까지 이어진다.
- 선형대수 12편 「텐서와 브로드캐스팅: 코드 속의 선형대수」: 텐서의 보폭(stride)과 연속(contiguous) 여부가 GPU 커널에서 병합 여부를 정하므로, PyTorch에서 전치 뒤 `.contiguous()`를 부르는 이유가 여기 있다.
- 어텐션 4편 「KV 캐시와 MQA·GQA·MLA」: KV 캐시의 메모리 배치(헤드·토큰 순서)를 정할 때 디코딩 커널이 연속으로 읽도록 맞추는 것이 이 글의 원리다.

## 정리
- 워프의 전역 메모리 접근은 필요한 32바이트 섹터 수만큼 트랜잭션이 되며, 연속 `float` 접근이 섹터 4개로 최선이다.
- 한 칸 어긋나면 섹터 5개(80%), 보폭 2면 8개(50%), 보폭 8 이상이나 무작위면 32개(12.5%)이고, s ≤ 8에서 `⌊(o + 31s)/8⌋ − ⌊o/8⌋ + 1`이라는 식과 300개 대조가 일치했다.
- 일부 필드만 읽는다면 AoS보다 SoA가 섹터를 덜 쓴다(12개 → 4개).
- `float4` 적재는 섹터 수는 같고 명령 수를 4분의 1로 줄이며, 16바이트 정렬이 필요하다.
