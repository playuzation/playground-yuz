# [GPU와 CUDA 1/14] GPU는 왜 다르게 생겼나: 지연을 숨기는 처리량 기계

> **한 줄 요약** — CPU는 스레드 하나가 기다리는 시간을 캐시·예측·비순차 실행으로 줄이는 데 트랜지스터를 쓰고, GPU는 그 시간을 그대로 둔 채 수많은 워프를 번갈아 실행해 기다림을 가리는 데 쓰며, 몇 개가 동시에 날아다녀야 하는지는 리틀의 법칙이 알려 준다.

## 같은 수백 사이클을 대하는 두 방법
DRAM에서 값 하나를 가져오는 데는 수백 사이클이 걸린다. 마이크로벤치마크 논문들은 A100의 DRAM 지연을 약 390~550사이클, H100은 약 550~730사이클로 측정했다(L2 슬라이스가 가까운지 먼지에 따라 두 갈래). 그동안 계산 유닛이 놀면 칩은 비싼 난로가 된다.

**CPU**는 이 지연을 줄이는 쪽으로 진화했다. 큰 캐시로 대부분의 접근을 수 사이클 안에 끝내고(메모리 시스템 1편 「메모리 계층 지도: 레지스터에서 SSD까지 지연과 대역폭」), 분기를 미리 맞히고(CPU 마이크로아키텍처 3편 「분기 예측: 2비트 카운터에서 gshare와 TAGE까지」), 기다리는 명령 뒤의 독립 명령을 먼저 실행한다(CPU 마이크로아키텍처 4편 「비순차 실행: 레지스터 이름 바꾸기와 토마술로 알고리즘」). 모두 스레드 하나를 빨리 끝내려는 장치다.

**GPU**는 지연을 줄이지 않고 숨긴다. 어떤 스레드 묶음이 메모리를 기다리면 다른 묶음의 명령을 낸다. 이 묶음이 32개 스레드로 된 **워프**(warp)다(3편). 모든 워프의 레지스터가 처음부터 거대한 레지스터 파일에 올라가 있어서, 워프를 바꾸는 데 저장·복원이 필요 없고 매 사이클 다른 워프를 골라도 된다. 운영체제의 문맥 교환과 달리 공짜다.
```text
CPU core (latency first)
┌─────────────────────────┐
│ branch predictor        │
│ out-of-order window     │
│ a few wide ALUs         │
│ large L1 / L2 / L3      │
└─────────────────────────┘
GPU SM (throughput first)
┌─────────────────────────┐
│ 4 warp schedulers       │
│ 128 FP32 lanes          │
│ 256KB register file     │
│ up to 64 warps resident │
│ 256KB L1 / shared       │
└─────────────────────────┘
```
아래 상자는 H100의 SM(streaming multiprocessor) 하나다. 예측기와 비순차 창 대신 계산 레인과 레지스터에 면적을 썼다. 내부 구조는 2편에서 자세히 본다.

## 리틀의 법칙: 몇 개가 날아다녀야 하나
줄 서는 시스템에서 안정 상태라면 `L = λ × W`가 성립한다. 시스템 안에 있는 평균 개수 L은 도착률 λ와 머무는 시간 W의 곱이다(리틀이 1961년 증명했다). 메모리에 대입하면 "대역폭을 다 쓰려면 지연 동안 날아다니는 바이트 = 대역폭 × 지연"이다. CPU는 W를 줄이고, GPU는 L을 키운다.
```python
# H100 SXM5 기준 어림: HBM을 쉬지 않게 하려면 몇 바이트가 날아다녀야 하나
bw = 3.35e12        # HBM3 대역폭(바이트/초)
clock = 1.98e9      # 공개 FP32 수치에서 역산한 클록(Hz), 2편 참조
lat = 600           # DRAM 왕복 지연 가정(사이클)
sms = 132
inflight = bw * lat / clock          # 리틀의 법칙 L = λ × W
per_sm = inflight / sms
print(f"전체 {inflight / 1e6:.2f}MB, SM당 {per_sm / 1e3:.1f}KB")
for name, b in [("float", 4), ("float4", 16)]:
    req = 32 * b                     # 워프 하나가 한 번에 읽는 바이트
    print(f"{name}: 워프당 {req}B → SM당 워프 {per_sm / req:.0f}개")
```
```text
전체 1.02MB, SM당 7.7KB
float: 워프당 128B → SM당 워프 60개
float4: 워프당 512B → SM당 워프 15개
```

칩 전체에서 1MB가 늘 이동 중이어야 한다. 워프마다 `float` 하나씩(32 × 4바이트) 읽고 기다린다면 SM 하나에 워프 60개가 필요하다. H100(CUDA의 계산 능력 9.0)의 SM 하나에는 워프를 최대 64개(2,048 스레드)까지 올려 둘 수 있으니, 이 한도가 우연히 정해진 값이 아님을 알 수 있다. 스레드마다 16바이트(`float4`)를 읽으면 15개로 충분하다. 지연 600사이클은 위 측정값 범위에서 고른 가정이다.

## 워프 스케줄러 시뮬레이션
이번에는 명령을 내는 쪽에서 보자. 스케줄러는 매 사이클 준비된 워프 하나를 골라 명령 하나를 낸다. 워프는 명령 k개를 내는데 마지막이 메모리 적재이고, 결과가 올 때까지 L 사이클 쉰다. 정책은 막힐 때까지 같은 워프를 고르고, 막히면 가장 오래 기다린 워프로 바꾸는 단순한 방식이다(연구 문헌의 GTO와 비슷하며, 실제 엔비디아 정책은 공개되지 않았다).
```python
def run(n_warps, k, lat, cycles):
    """워프 스케줄러 하나. 매 사이클 준비된 워프 하나가 명령 하나를 낸다.
    워프는 명령 k개를 내는데 k번째가 메모리 적재이고, 그 뒤 lat 사이클 쉰다.
    정책: 막힐 때까지 같은 워프, 막히면 가장 오래 기다린 워프(GTO)."""
    ready = [0] * n_warps            # 이 사이클부터 명령을 낼 수 있다
    left = [k] * n_warps             # 적재까지 남은 명령 수
    cur, line = 0, []
    for t in range(cycles):
        if ready[cur] > t:           # 현재 워프가 막히면 갈아탄다
            cur = min(range(n_warps), key=lambda w: ready[w])
        if ready[cur] > t:
            line.append(".")         # 준비된 워프가 없다: 빈 사이클
            continue
        line.append(str(cur))
        left[cur] -= 1
        if left[cur] == 0:           # 적재를 냈다: lat 사이클 뒤에 돌아온다
            left[cur], ready[cur] = k, t + 1 + lat
    return "".join(line)

for n in (2, 3, 4):
    s = run(n, k=4, lat=12, cycles=32)
    busy = 1 - s.count(".") / len(s)
    print(f"N={n} {busy:4.0%} {s}")
```
```text
N=2  50% 00001111........00001111........
N=3  75% 000011112222....000011112222....
N=4 100% 00001111222233330000111122223333
```

숫자는 그 사이클에 명령을 낸 워프 번호, 점은 빈 사이클이다. 워프 하나는 16사이클(일 4 + 대기 12)마다 4사이클만 일하므로 워프 4개가 있어야 빈틈이 메워진다. 일반식은 `N = ⌈(k + L) / k⌉`이다. 무작위 매개변수에서 시뮬레이터가 찾은 최소 워프 수가 이 식과 같은지 확인하고, 지연 600사이클에 대입해 보자(앞 코드에 이어서).
```python
import math, random
rng = random.Random(1)
same = 0
for _ in range(300):
    k, lat = rng.randint(1, 10), rng.randint(20, 400)
    need = math.ceil((k + lat) / k)      # 공식: 워프 한 주기 ÷ 일하는 몫
    T = 3 * (k + lat)
    full = "." not in run(need, k, lat, T)
    short = "." in run(need - 1, k, lat, T)
    same += full and short
print(f"무작위 300개: 최소 워프 수가 공식과 일치 {same}/300")
for k in (4, 16, 40):                    # 지연 600사이클일 때
    print(f"적재 1개당 명령 {k}개 → 스케줄러당 워프",
          math.ceil((k + 600) / k))
print(f"SM당 HBM 몫 {bw / sms / clock:.1f}B/사이클,",
      f"k=40의 요구 {4 * 128 / 40:.1f}B/사이클")
```
```text
무작위 300개: 최소 워프 수가 공식과 일치 300/300
적재 1개당 명령 4개 → 스케줄러당 워프 151
적재 1개당 명령 16개 → 스케줄러당 워프 39
적재 1개당 명령 40개 → 스케줄러당 워프 16
SM당 HBM 몫 12.8B/사이클, k=40의 요구 12.8B/사이클
```

SM에는 스케줄러가 4개이므로 워프 64개는 스케줄러당 16개다. 명령 4개마다 적재가 하나인 커널은 스케줄러당 151개가 있어야 하는데 그만큼 올릴 수 없고, 올릴 수 있다 해도 SM당 대역폭 몫(12.8바이트/사이클)이 먼저 바닥난다. 적재 하나에 명령이 40개쯤 따라붙어야 16개 워프로 지연이 가려지고, 공교롭게 그때 요구 대역폭도 HBM 몫과 같아진다. 적재당 계산량, 즉 **산술 강도**(arithmetic intensity)가 GPU 성능을 가르는 이유이며 13편의 루프라인 모델이 이를 정식으로 다룬다.

## 그래픽에서 범용 계산으로
이 구조는 그래픽에서 왔다. 화면의 픽셀 수백만 개는 서로 독립이라 같은 셰이더 프로그램을 동시에 돌리면 된다. 초기 GPU에는 정점용·픽셀용 셰이더 유닛이 따로 있었고, 그래픽 밖의 계산을 하려면 데이터를 텍스처로, 계산을 픽셀 셰이더로 위장해야 했다.

2006년 11월 엔비디아는 지포스 8800 GTX(G80)를 내놓았다. 정점·픽셀 처리를 같은 프로세서 128개가 나눠 맡는, 엔비디아의 첫 **통합 셰이더**(unified shader) 구조였고, 이 구조를 **테슬라 아키텍처**(Tesla)라 부른다. 같은 프로세서가 그래픽이 아닌 일도 할 수 있게 되자 엔비디아는 C를 확장한 **CUDA**를 함께 발표했고 2007년에 공개했다. 그 뒤 GPU는 과학 계산과 딥러닝의 주력 계산기가 되었다.

## 코드에 주는 의미
- 스레드를 충분히 만든다. H100 SXM5에는 132 × 2,048 = 270,336개 스레드가 동시에 상주할 수 있다. 원소가 수천 개뿐인 일은 GPU를 채우지 못한다.
- 적재 하나당 계산을 늘린다. 데이터를 공유 메모리나 레지스터에 올려 여러 번 쓰는 타일링(10편)이 대표적이다.
- 워프 수가 모자라면 워프 하나가 독립 적재를 여러 개 동시에 내게 한다(명령 수준 병렬성, 8편).
- CPU 최적화 습관 대신 워프 단위로 생각한다. 분기 갈림(3편), 메모리 병합(6편), 뱅크 충돌(7편)이 GPU 판의 캐시 미스다.
- 작은 일을 자주 보내지 않는다. 커널 실행과 복사에도 고정 비용이 든다(12편).

## 어디에 쓰이나
- 트랜지스터에서 자연어까지 7편 「빠르게 만드는 기술: 파이프라인, 캐시, 병렬성」: 그 글이 한 단락으로 소개한 SIMD와 GPU를 이 시리즈가 이어받아, 지연을 숨기는 방식부터 칩 안으로 내려간다.
- AI 기초 4편 「컴퓨터 사이언스로 보는 AI 모델: 텐서, 연산, 메모리」: 토큰 생성 속도가 메모리 대역폭에 묶인다는 어림은, 적재당 명령이 적으면 대역폭이 먼저 바닥난다는 이 글의 계산과 같은 이야기다.
- 어텐션 7편 「플래시 어텐션: 메모리 계층을 아는 정확한 어텐션」: HBM 왕복을 줄여 산술 강도를 높이는 것이 이 글에서 본 한계를 넘는 정석이다.
- 메모리 시스템 8편 「HBM과 GDDR: 넓게 쌓은 메모리와 빠르게 달리는 메모리」: 리틀의 법칙에 들어간 3.35TB/s를 어떻게 만드는지 다룬다.

## 정리
- CPU는 지연(W)을 줄이고 GPU는 동시에 진행 중인 일(L)을 늘린다. 둘 다 리틀의 법칙 `L = λ × W`의 한 변을 움직이는 전략이다.
- H100 SXM5에서 HBM을 쉬지 않게 하려면 칩 전체에 약 1MB, SM당 워프 60개 분량의 적재가 늘 진행 중이어야 한다.
- 스케줄러가 쉬지 않으려면 워프가 `⌈(k + L) / k⌉`개 필요하고, 적재당 명령 수 k가 작으면 어떤 점유율로도 가릴 수 없다.
- GPU는 통합 셰이더(테슬라, 2006)와 CUDA(2007)로 그래픽 칩에서 범용 처리량 기계가 되었다.
