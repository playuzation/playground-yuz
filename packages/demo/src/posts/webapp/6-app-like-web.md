## 설치 앱이 나았던 점
2005년 무렵의 웹 앱과 설치 앱을 비교하면 웹이 밀리는 곳이 분명했다. 네트워크가 끊기면 아무것도 열리지 않았고, 기기에 데이터를 많이 저장할 수 없었고, 홈 화면 아이콘이나 알림이 없었고, 영상 편집처럼 무거운 계산은 너무 느렸다. 이후 웹 표준은 이 빈칸을 하나씩 채웠다. 그 결과 지금은 "설치하지 않아도 되는 앱"과 "설치할 수도 있는 웹"의 경계가 흐려졌다.

## 브라우저 저장소: 출처마다 따로
브라우저는 데이터를 저장할 곳을 여러 개 주는데, 모두 **출처별로** 나뉜다(3편). 한 사이트가 저장한 것을 다른 사이트의 코드가 읽을 수 없다.
- **쿠키**(cookie): 작은 이름=값 쌍. 같은 사이트로 가는 요청마다 자동으로 실려 간다. 그래서 로그인 표시에 쓰지만(11편), 큰 데이터를 넣으면 모든 요청이 무거워진다.
- **localStorage**: 문자열 키와 값을 저장하는 간단한 저장소. 쓰기 쉽지만 읽고 쓰는 동안 메인 스레드를 멈추고 용량도 작다. 설정값 정도에 맞는다.
- **IndexedDB**: 객체를 색인과 함께 저장하는 비동기 데이터베이스. 메일함 수천 통, 오프라인 문서처럼 큰 구조화 데이터를 둔다.
- **캐시 저장소**(Cache Storage): 요청과 응답 쌍을 그대로 저장한다. 아래 서비스 워커가 오프라인 파일을 둘 때 쓴다.

브라우저 저장소는 기기의 공간이 부족하면 브라우저가 지울 수 있고, 사용자가 사이트 데이터를 지우면 사라진다. 그래서 최종 원본은 서버에 두고, 기기에는 빠르게 보여 주기 위한 사본과 아직 보내지 못한 변경을 둔다.

## 서비스 워커: 페이지와 네트워크 사이의 대리인
**서비스 워커**(service worker)는 페이지와 따로 도는 자바스크립트로, 그 출처의 페이지가 보내는 요청을 가로채 직접 답할 수 있다. 페이지 입장에서는 네트워크 앞에 내가 프로그래밍할 수 있는 작은 프록시가 생긴 셈이다.
```text
page ──fetch──→ service worker
                 ├─ cache hit → reply
                 └─ miss → network
```
처음 방문할 때 페이지가 서비스 워커를 등록하면, 서비스 워커는 설치 단계에서 앱의 핵심 파일(HTML, 스크립트, 아이콘)을 캐시 저장소에 넣어 둔다. 다음부터는 네트워크가 끊겨도 서비스 워커가 캐시에서 답해 앱이 열린다. 서버에서 보내는 푸시 알림을 받는 일도 서비스 워커가 한다. 요청을 가로챌 수 있을 만큼 강력하므로, 중간에서 누가 바꿔치기하지 못하게 HTTPS(10편)에서만 쓸 수 있다(개발용 localhost는 예외).

## 직접 해 보기 1: 캐시 전략 세 가지
서비스 워커가 "캐시와 네트워크 중 무엇을 먼저 볼지" 정하는 방법을 **캐시 전략**이라고 한다. 세 전략을 같은 상황에 놓아 본다. 1단계는 첫 방문, 2단계에서는 서버의 파일이 v2로 바뀌었고, 3단계에서는 네트워크가 끊겼다. 코드를 몰라도 마지막 출력 세 줄만 보면 된다.
```python
def make(strategy):
    cache, server = {}, {'v': 'v1'}
    def net(online):
        if not online:
            raise ConnectionError
        return server['v']
    def get(online):
        if strategy == '캐시 우선':
            if 'app' in cache:
                return cache['app'] + '(캐시)'
            cache['app'] = net(online)
            return cache['app'] + '(네트워크)'
        if strategy == '네트워크 우선':
            try:
                cache['app'] = net(online)
                return cache['app'] + '(네트워크)'
            except ConnectionError:
                return cache['app'] + '(캐시)' if 'app' in cache else '실패'
        # stale-while-revalidate: 캐시로 먼저 답하고, 뒤에서 새로 받아 둔다
        old = cache.get('app')
        try:
            cache['app'] = net(online)
        except ConnectionError:
            pass
        return (old + '(캐시)') if old else (cache['app'] + '(네트워크)')
    return get, server

for name in ['캐시 우선', '네트워크 우선', 'stale-while-revalidate']:
    get, server = make(name)
    steps = [get(True)]
    server['v'] = 'v2'                 # 서버가 새 버전을 배포했다
    steps.append(get(True))
    steps.append(get(False))           # 오프라인
    print(f'{name}: ' + ' → '.join(steps))
```
```text
캐시 우선: v1(네트워크) → v1(캐시) → v1(캐시)
네트워크 우선: v1(네트워크) → v2(네트워크) → v2(캐시)
stale-while-revalidate: v1(네트워크) → v1(캐시) → v2(캐시)
```
- **캐시 우선**은 가장 빠르고 오프라인에도 강하지만, 새 버전을 알아채지 못한다. 파일 이름에 버전이 들어간 스크립트·이미지처럼 내용이 절대 바뀌지 않는 파일에 맞는다(16편).
- **네트워크 우선**은 늘 최신이지만 네트워크를 기다려야 한다. 끊겼을 때만 캐시로 버틴다. 뉴스 목록, 잔액처럼 신선함이 중요한 데이터에 맞는다.
- **stale-while-revalidate**는 캐시로 즉시 답하면서 뒤에서 새 버전을 받아 둔다. 2단계에서는 옛 v1을 보여 줬지만, 3단계에는 이미 받아 둔 v2가 나왔다. 조금 늦게 바뀌어도 되는 화면에 맞는다.

## PWA: 설치할 수 있는 웹 앱
**PWA**(progressive web app)라는 말은 2015년 프랜시스 베리먼과 크롬 엔지니어 알렉스 러셀이 만들었다. 특정 기술 하나가 아니라 묶음의 이름이다. HTTPS로 제공되고, 서비스 워커로 오프라인에서도 최소한 열리며, **웹 앱 매니페스트**(manifest)라는 JSON 파일에 이름·아이콘·시작 주소·표시 방식을 적어 두면, 브라우저가 "홈 화면에 추가" 또는 "설치"를 제안한다. 설치하면 주소창 없는 별도 창으로 열리고 앱 목록에 아이콘이 생긴다. 그래도 내용은 여전히 서버의 웹 파일이라, 서버를 바꾸면 다음 실행 때 서비스 워커가 새 파일을 받아 갱신한다. 플랫폼마다 지원하는 기능(알림, 백그라운드 동기화)이 조금씩 다르므로, 꼭 필요한 기능은 대상 기기에서 확인한다.

## WebAssembly: 브라우저 안의 기계어
자바스크립트 엔진이 아무리 빨라져도(2편) 동적인 언어라 한계가 있다. **WebAssembly**(Wasm)는 브라우저가 실행하는 작은 바이너리 명령어 형식이다. C, C++, 러스트 같은 언어를 이 형식으로 컴파일하면 브라우저가 기계어에 가까운 속도로 돌린다. 샌드박스(3편) 안에서 돌고, DOM은 자바스크립트를 통해서만 만진다. 2019년 12월 5일 W3C가 WebAssembly 핵심 명세를 권고안으로 발표하며 HTML, CSS, 자바스크립트에 이은 웹의 네 번째 언어라고 소개했다. 사진·영상 편집, 게임, 설계 도구처럼 무거운 계산을 하는 웹 앱이 쓰고, 오래된 데스크톱 프로그램을 웹으로 옮길 때도 쓴다.

## 직접 해 보기 2: 41바이트 모듈 손으로 만들기
보통은 컴파일러가 `.wasm` 파일을 만들지만, 두 수를 더하는 함수 하나짜리 모듈은 바이트를 직접 적을 수 있을 만큼 작다. Node.js에도 브라우저와 같은 `WebAssembly` 객체가 있다.
```js
// 파일: add.mjs
const bytes = new Uint8Array([
  0x00, 0x61, 0x73, 0x6d, 0x01, 0x00, 0x00, 0x00,       // "\0asm", 버전 1
  0x01, 0x07, 0x01, 0x60, 0x02, 0x7f, 0x7f, 0x01, 0x7f, // 형식: (i32, i32) → i32
  0x03, 0x02, 0x01, 0x00,                               // 함수 1개, 형식 0번
  0x07, 0x07, 0x01, 0x03, 0x61, 0x64, 0x64, 0x00, 0x00, // "add"라는 이름으로 내보내기
  0x0a, 0x09, 0x01, 0x07, 0x00,                         // 함수 본문 시작
  0x20, 0x00, 0x20, 0x01, 0x6a, 0x0b,                   // a를 놓고, b를 놓고, 더하고, 끝
]);
const { instance } = await WebAssembly.instantiate(bytes);
const { add } = instance.exports;
console.log('모듈 크기:', bytes.length, '바이트');
console.log('add(2, 3) =', add(2, 3));
console.log('add(2147483647, 1) =', add(2147483647, 1));
```
```bash
node add.mjs
```
```text
모듈 크기: 41 바이트
add(2, 3) = 5
add(2147483647, 1) = -2147483648
```
모듈은 맨 앞의 표식(`\0asm`)과 버전, 함수의 형식, 내보낼 이름, 함수 본문으로 이루어진다. 본문은 "값 두 개를 쌓고(`0x20`), 더한다(`0x6a`)"는 스택 기계 명령이다. 마지막 줄이 흥미롭다. 32비트 정수의 최댓값에 1을 더하자 음수로 넘어갔다. WebAssembly는 자바스크립트의 숫자 대신 CPU처럼 크기가 정해진 정수를 쓰기 때문이다. 이 41바이트는 브라우저에서도 똑같이 돈다. 실제 앱에서는 컴파일러가 수 MB짜리 모듈을 만들고, 자바스크립트가 그것을 내려받아 실행하며 화면과 연결한다.

## 흔한 오해
- "PWA는 앱 스토어 앱과 같다": 설치와 오프라인은 되지만 쓸 수 있는 기기 기능과 배포 방식은 플랫폼마다 다르다. 반대로 스토어 심사 없이 서버만 바꿔 갱신할 수 있다는 장점이 있다.
- "WebAssembly가 자바스크립트를 대체한다": 둘은 함께 쓴다. 화면, DOM, 네트워크는 자바스크립트가 맡고, 무거운 계산 부분을 WebAssembly로 떼어 낸다.
- "브라우저에 저장했으니 안전하게 보관된다": 브라우저 저장소는 지워질 수 있고, 같은 기기를 쓰는 사람이나 그 출처에서 실행되는 스크립트가 읽을 수 있다. 원본과 비밀은 서버에 둔다.

## 어디에 쓰이나
- 메모리 시스템 1편 「메모리 계층 지도: 레지스터에서 SSD까지 지연과 대역폭」: 가까운 곳에 사본을 두고 먼 곳은 덜 찾는다는 캐시의 원리가 서비스 워커 캐시에도 그대로 적용된다.
- 언어 기초 4편 「러스트: 가비지 컬렉터 없이 메모리 안전하게」: WebAssembly로 컴파일하는 대표적인 언어이고, 크기가 정해진 정수형 이야기도 이어진다.
- 컴퓨터와 AI의 첫걸음 2편 「왜 0과 1인가: 비트와 이진법이 이긴 이유」: 32비트 정수가 넘치면 음수가 되는 이유는 비트로 수를 나타내는 방식에서 나온다.

## 정리
- 브라우저 저장소(쿠키, localStorage, IndexedDB, 캐시 저장소)는 출처별로 나뉘고, 지워질 수 있는 사본이다.
- 서비스 워커는 요청을 가로채 캐시로 답할 수 있는 대리인이다. 캐시 우선·네트워크 우선·stale-while-revalidate 중 데이터 성격에 맞게 고른다.
- PWA는 HTTPS, 서비스 워커, 매니페스트를 갖춰 설치할 수 있는 웹 앱이다.
- WebAssembly는 브라우저가 실행하는 바이너리 명령어 형식으로, 무거운 계산을 기계어에 가까운 속도로 돌린다.
