# [웹 앱의 원리 2/20] 브라우저 안에서 앱이 도는 방식: JavaScript 엔진, DOM, 이벤트 루프

> **한 줄 요약** — 브라우저는 받은 HTML을 DOM이라는 나무로 만들어 화면에 그리고, 자바스크립트 엔진이 그 나무를 고치며, 이벤트 루프가 클릭·타이머·네트워크 응답을 하나씩 꺼내 실행해 주기 때문에 문서가 앱처럼 움직인다.

## 이 글에서 다루는 것
- HTML 글자가 화면의 픽셀이 되기까지: 파싱, DOM, 레이아웃, 페인트
- 자바스크립트 엔진: 인터프리터에서 JIT 컴파일러로
- 메인 스레드 하나와 이벤트 루프, 작업 큐와 마이크로태스크
- 직접 해 보기: 실행 순서 맞히기, 메인 스레드를 막으면 생기는 일, 워커로 일 나누기
- 흔한 오해: "setTimeout(…, 0)은 바로 실행된다"

## 질문: 글자로 된 문서가 어떻게 움직이는 앱이 될까
1편의 서버가 보낸 것은 76바이트짜리 글자였다. 브라우저는 이 글자를 해석해 화면을 그리고, 버튼을 누르면 목록이 늘어나고, 몇 초마다 새 알림이 뜨게 만든다. 이 일을 하는 부품은 세 가지다. 문서를 나무 구조로 바꾸는 **렌더링 엔진**, 프로그램을 실행하는 **자바스크립트 엔진**, 그리고 둘 사이에서 "지금 무엇을 실행할지" 정하는 **이벤트 루프**다.

## 문서에서 픽셀까지
브라우저는 HTML을 앞에서부터 읽으며 태그를 **DOM**(Document Object Model)이라는 나무로 만든다. 1편의 문서는 이런 나무가 된다.
```text
document
└─ html
   ├─ head
   │  └─ title: 메모
   └─ body
      └─ p: 버전 1
```
CSS는 "어느 요소를 어떤 색과 크기로" 같은 규칙으로 읽힌다. 브라우저는 DOM과 규칙을 합쳐 요소마다 위치와 크기를 계산하고(**레이아웃**), 실제 픽셀을 칠한다(**페인트**). 화면이 바뀌는 것은 이 과정이 다시 돌기 때문이다.
```text
HTML ──parse──→ DOM tree
CSS  ──parse──→ style rules
DOM + style ──→ layout (where)
layout ──→ paint (pixels)
JS edits DOM ──→ layout again
```
자바스크립트는 DOM을 직접 고칠 수 있다. `document.querySelector('p').textContent = '버전 2'` 한 줄이면 서버에 다시 묻지 않고 글자가 바뀐다. 웹 앱의 화면 변화는 거의 모두 이 방식이다. 서버에서 데이터만 받아 와서(4편) 자바스크립트가 DOM을 고친다.

## 자바스크립트 엔진: 해석에서 컴파일로
자바스크립트는 1995년 넷스케이프에서 만들어졌다. 처음에는 버튼 검사나 간단한 효과를 위한 언어였고 엔진은 코드를 한 줄씩 해석하는 인터프리터라 느렸다. 2008년 구글이 크롬과 함께 공개한 V8 엔진은 코드를 실행하는 순간에 기계어로 바꾸는 **JIT 컴파일**(just-in-time)을 앞세워 속도를 크게 끌어올렸다. 지금의 주요 엔진(크롬의 V8, 파이어폭스의 SpiderMonkey, 사파리의 JavaScriptCore)은 모두 해석으로 빨리 시작하고, 뜨거운 코드는 최적화 컴파일러로 넘긴다. 문서 편집기나 지도 같은 무거운 앱이 브라우저에서 가능해진 데에는 이 속도 향상이 컸다. 2009년에는 V8을 브라우저 밖에서 쓰는 Node.js가 나왔고, 아래 실습은 이 Node.js로 한다. Node.js에는 화면이 없지만 이벤트 루프의 규칙은 브라우저와 매우 비슷하다.

## 메인 스레드 하나와 이벤트 루프
브라우저 탭의 자바스크립트는 기본적으로 **메인 스레드**(main thread) 하나에서 돈다. 같은 스레드가 레이아웃과 페인트도 맡는다. 동시에 들어오는 사건(클릭, 타이머 만료, 네트워크 응답)은 줄에 세워 두고, 이벤트 루프가 지금 실행 중인 코드가 끝날 때마다 하나씩 꺼낸다.
- **작업 큐**(task queue): 클릭 처리, `setTimeout` 콜백, 네트워크 응답 처리 같은 큰 일이 줄 선다.
- **마이크로태스크 큐**(microtask queue): 프로미스(Promise)의 후속 처리처럼 "지금 하던 일 직후에" 해야 하는 작은 일이 줄 선다. 작업 하나가 끝나면 다음 작업보다 먼저 마이크로태스크를 모두 비운다.

화면은 보통 1초에 60번쯤 다시 그려지므로 한 프레임에 쓸 수 있는 시간은 약 16.7ms다. 자바스크립트가 메인 스레드를 그보다 오래 붙잡으면 그동안 그리기도 클릭 처리도 멈춘다. 페이지가 "얼어붙는" 이유다.

## 직접 해 보기 1: 실행 순서 맞히기
Node.js 18 이상이면 된다. 코드를 읽지 못해도 출력의 순서만 보면 된다. 네 줄의 출력 순서를 먼저 짐작해 보자.
```js
// 파일: order.js
console.log('1 동기 코드');
setTimeout(() => console.log('4 타이머(작업 큐)'), 0);
Promise.resolve().then(() => console.log('3 프로미스(마이크로태스크)'));
console.log('2 동기 코드 끝');
```
```bash
node order.js
```
```text
1 동기 코드
2 동기 코드 끝
3 프로미스(마이크로태스크)
4 타이머(작업 큐)
```
지금 실행 중인 코드(1, 2)가 먼저 끝까지 돈다. 그다음 마이크로태스크(3)를 비우고, 그다음에야 작업 큐의 타이머(4)를 꺼낸다. 타이머를 0ms로 맞췄어도 "0ms 뒤에 줄을 선다"는 뜻일 뿐 끼어들 수는 없다.

## 직접 해 보기 2: 메인 스레드를 붙잡으면
이번에는 0ms 타이머를 걸어 두고 300ms 동안 쉬지 않고 도는 반복문으로 스레드를 붙잡는다.
```js
// 파일: block.js
const start = Date.now();
setTimeout(() => {
  const late = Date.now() - start;
  console.log('타이머 실행:', late >= 300 ? '300ms 넘게 밀림' : '제때');
}, 0);
while (Date.now() - start < 300) {} // 300ms 동안 쉬지 않고 돈다
console.log('바쁜 반복 끝');
```
```bash
node block.js
```
```text
바쁜 반복 끝
타이머 실행: 300ms 넘게 밀림
```
타이머는 0ms 뒤에 실행될 준비가 되었지만, 반복문이 스레드를 놓지 않아 300ms 넘게 기다렸다. 브라우저였다면 그 300ms 동안 스크롤도 버튼도 반응하지 않는다. 그래서 큰 계산은 잘게 나눠 여러 번에 걸쳐 하거나, 다른 스레드로 보낸다.

## 직접 해 보기 3: 워커에게 맡기기
브라우저의 **웹 워커**(Web Worker)는 메인 스레드와 따로 도는 자바스크립트 스레드다. DOM에는 손댈 수 없고 메시지로만 대화한다. Node.js의 `worker_threads`가 같은 생각을 따른다. 무거운 합계를 워커에게 맡기고, 메인 스레드에서는 50ms마다 "살아 있다"는 신호를 센다.
```js
// 파일: worker.js
const { Worker } = require('node:worker_threads');
const job = `
  const { parentPort } = require('node:worker_threads');
  const end = Date.now() + 400; let n = 0;
  while (Date.now() < end) n++;            // 400ms 동안 계산
  parentPort.postMessage(n > 0 ? '계산 완료' : '?');
`;
let ticks = 0;
const timer = setInterval(() => ticks++, 50);
const w = new Worker(job, { eval: true });
w.on('message', (msg) => {
  clearInterval(timer);
  console.log(msg);
  console.log('그동안 메인 스레드 신호:', ticks >= 4 ? '4번 이상' : ticks + '번');
  w.terminate();
});
```
```bash
node worker.js
```
```text
계산 완료
그동안 메인 스레드 신호: 4번 이상
```
계산이 400ms 걸리는 동안에도 메인 스레드는 50ms마다 신호를 셌다. 브라우저라면 그동안 화면이 계속 반응했을 것이다. 사진 필터, 큰 파일 압축, 암호 계산 같은 일을 웹 앱이 워커로 보내는 이유다.

## 흔한 오해
- "`setTimeout(…, 0)`은 바로 실행된다": 위에서 본 대로 줄 맨 뒤에 설 뿐이다. 브라우저는 중첩된 타이머의 최소 간격을 늘리기도 한다.
- "자바스크립트는 단일 스레드라 동시에 아무것도 못 한다": 내 코드는 한 줄로 실행되지만 네트워크 대기, 타이머, 디스크 읽기는 브라우저(또는 Node.js)가 다른 곳에서 처리하고 끝나면 줄에 세워 준다. 그래서 요청 수백 개를 동시에 기다릴 수 있다(4편). 계산을 동시에 하려면 워커를 쓴다.
- "화면은 코드가 바꾸는 즉시 그려진다": DOM을 여러 번 고쳐도 브라우저는 보통 현재 코드가 끝난 뒤 한 번에 레이아웃과 페인트를 한다. 그래서 위의 바쁜 반복 중에는 중간 상태가 화면에 나오지 않는다.

## 정리
- 브라우저는 HTML을 DOM 나무로 바꾸고, CSS 규칙과 합쳐 레이아웃과 페인트를 해서 화면을 만든다. 자바스크립트가 DOM을 고치면 이 과정이 다시 돈다.
- JIT 컴파일로 빨라진 자바스크립트 엔진 덕분에 무거운 앱도 브라우저에서 돈다.
- 메인 스레드는 하나다. 이벤트 루프가 현재 코드 → 마이크로태스크 → 다음 작업 순으로 꺼내 실행한다.
- 메인 스레드를 오래 붙잡으면 화면이 얼어붙는다. 큰 계산은 쪼개거나 워커로 보낸다.
