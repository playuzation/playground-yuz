# [웹 앱의 원리 20/20] 한 번의 클릭이 지나가는 길: 주소창에서 화면까지

> **한 줄 요약** — 주소창에 주소를 넣고 Enter를 누르면 캐시 확인, DNS, TCP와 TLS(또는 QUIC), HTTP 요청, CDN과 로드 밸런서, 앱 서버와 데이터베이스, 응답의 압축과 캐시 규칙, 브라우저의 파싱·렌더링·하이드레이션이 차례로 일어나고, 이 시리즈의 스무 편은 그 길의 한 구간씩이었다.

## 이 글에서 다루는 것
- 첫 방문의 전체 경로를 한 번에 따라가기
- 각 구간이 시리즈의 어느 글이었는지
- 직접 해 보기: curl로 구간별 시간 재기, 첫 방문과 다시 방문의 시간 어림
- 세 질문에 대한 답과 다음에 읽을 글

## 0. Enter를 누르기 전에 브라우저가 보는 것
브라우저는 네트워크로 나가기 전에 가까운 곳부터 확인한다. 이 사이트는 HTTPS로만 접속하라고 전에 알려 왔는가(그렇다면 http를 https로 바꾼다). 이 출처에 서비스 워커가 있는가(있다면 요청이 먼저 그쪽으로 간다, 6편). HTTP 캐시에 아직 신선한 사본이 있는가(있다면 여기서 끝난다, 16편). 가장 빠른 요청은 보내지 않는 요청이다.

## 1. 이름을 주소로
캐시에 없으면 `www.example.com`의 IP 주소가 필요하다. 브라우저와 운영체제의 DNS 캐시, 그다음 재귀 리졸버에게 묻는다(8편). 사이트가 CDN을 쓴다면 답은 CNAME을 거쳐 사용자와 가까운 엣지의 주소가 된다(16편). 같은 주소를 여러 곳에서 알리는 애니캐스트라면 패킷이 알아서 가까운 곳으로 간다(18편).

## 2. 연결과 암호
그 주소의 443번 포트로 TCP 연결을 연다. SYN, SYN+ACK, ACK의 왕복 한 번이다(7편). 그 위에서 TLS 1.3 핸드셰이크로 열쇠를 나눠 갖고, 인증서로 상대가 정말 `www.example.com`인지 확인한다. 또 왕복 한 번이다(10편). HTTP/3를 쓰면 QUIC이 이 둘을 왕복 한 번에 함께 끝낸다(15편). 엣지가 가까울수록 이 왕복들이 짧다.

## 3. 요청
연결 위로 HTTP 요청이 나간다. `GET /`, `Host` 헤더, 받을 수 있는 압축 방식(17편), 로그인 쿠키나 토큰(11편)이 실린다(9편). HTTP/2나 3라면 이 요청은 하나의 스트림이고, 같은 연결로 뒤따를 수십 개의 요청이 스트림으로 섞여 갈 것이다(15편).

## 4. 서버 쪽의 길
엣지는 캐시를 본다. 정적 파일이면 대개 여기서 답한다. 사용자별 페이지거나 사본이 없으면 엣지는 원본으로 넘긴다. 원본의 대문인 로드 밸런서가 건강한 앱 서버 하나를 고르고(18편), 레이트 리밋이 이 사용자의 몫을 확인한다(19편). 앱 서버는 세션이나 토큰으로 사용자를 확인하고 권한을 검사한 뒤(11편), 데이터베이스에서 필요한 것을 읽어 HTML을 그리거나(서버 렌더링, 5편) 데이터만 JSON으로 만든다(4편, 12편). 오래 걸리는 일이면 접수증만 주고 큐에 넘긴다(14편). 모든 바깥 호출에는 시간 제한과 서킷 브레이커가 걸려 있다(19편).

## 5. 응답
응답은 상태 코드와 헤더와 본문이다. `Content-Type`은 무엇인지, `Content-Encoding`은 어떻게 압축했는지, `Cache-Control`과 `ETag`는 다음에 어떻게 다시 받을지를 알린다(9편, 16편, 17편). 응답은 패킷으로 잘려 혼잡 제어의 속도에 맞춰 흘러오고(7편, 19편), 엣지가 캐시할 수 있는 것이면 사본을 남긴다.

## 6. 화면이 되기까지
브라우저는 HTML을 받는 대로 읽어 DOM을 만들고(2편), 그 안에서 발견한 CSS·스크립트·이미지를 같은 연결로 동시에 요청한다. 지문 넣은 파일 이름의 자원은 캐시에서 바로 나온다(16편). 레이아웃과 페인트로 첫 화면이 그려지고, 스크립트가 도착하면 하이드레이션으로 버튼에 동작이 붙는다(5편). 그 뒤로는 `fetch`가 데이터를 받아 화면 일부를 고치고(4편), 알림이 필요하면 SSE나 웹소켓 연결이 열린다(13편). 이 모든 코드는 샌드박스와 동일 출처 정책 안에서 돈다(3편). 설치는 한 번도 없었다(1편).

## 직접 해 보기 1: 구간별 시간 재기
curl은 요청 하나를 구간별 시각으로 나눠 알려 준다. 10편처럼 이 컴퓨터용 인증서로 HTTPS 서버를 띄우고, 이름 풀이·TCP 연결·TLS 완료·첫 바이트·끝을 잰다. 같은 컴퓨터 안이라 숫자는 아주 작고 실행할 때마다 다르지만, 순서는 늘 같다.
```bash
openssl req -x509 -newkey rsa:2048 -nodes -keyout ca.key -out ca.crt \
  -days 30 -subj '/CN=Toy Local CA' 2>/dev/null
openssl req -newkey rsa:2048 -nodes -keyout server.key -out server.csr \
  -subj '/CN=localhost' 2>/dev/null
printf 'subjectAltName=DNS:localhost\n' > san.ext
openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
  -out server.crt -days 30 -extfile san.ext 2>/dev/null
printf '<!doctype html><title>home</title><p>hello</p>\n' > index.html
python3 -c "
import http.server, ssl
srv = http.server.HTTPServer(('127.0.0.1', 8030), http.server.SimpleHTTPRequestHandler)
ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER); ctx.load_cert_chain('server.crt', 'server.key')
srv.socket = ctx.wrap_socket(srv.socket, server_side=True); srv.serve_forever()
" > /dev/null 2>&1 &
sleep 1
curl -s -o /dev/null --cacert ca.crt https://localhost:8030/ -w \
'이름 풀이 끝: %{time_namelookup}초\nTCP 연결 끝: %{time_connect}초\nTLS 끝: %{time_appconnect}초\n첫 바이트: %{time_starttransfer}초\n전체: %{time_total}초\n상태 %{http_code}, 본문 %{size_download}바이트\n'
```
```text
이름 풀이 끝: …초
TCP 연결 끝: …초
TLS 끝: …초
첫 바이트: …초
전체: …초
상태 200, 본문 47바이트
```
다섯 시각은 요청이 시작된 순간부터 잰 누적값이다. 이 시리즈의 8편(이름 풀이), 7편(TCP), 10편(TLS), 9편과 서버 쪽 처리(첫 바이트), 17편(본문 전송)이 차례로 끝나는 시점이다. 실제 사이트에 대고 재면 이름 풀이와 TLS 사이의 간격이 왕복 시간만큼 벌어지는 것을 볼 수 있다. 느린 사이트를 진단할 때 어느 구간이 긴지부터 보면 어느 글의 기술이 필요한지 알 수 있다.

## 직접 해 보기 2: 첫 방문과 다시 방문
같은 페이지를 처음 열 때와 다음 날 다시 열 때를 어림한다. 가까운 엣지까지 왕복 20ms, 엣지에서 원본까지 150ms, 이름 풀이 40ms, 서버 처리 50ms로 정한 가상의 값이다.
```python
EDGE, ORIGIN, DNS, WORK = 20, 150, 40, 50

first = [('이름 풀이 (8편)', DNS),
         ('TCP 연결 (7편)', EDGE),
         ('TLS 핸드셰이크 (10편)', EDGE),
         ('요청과 엣지 왕복 (9편)', EDGE),
         ('캐시 없음: 원본까지 (16편, 18편)', ORIGIN),
         ('서버 처리와 렌더링 (5편)', WORK)]
again = [('이름 풀이: 캐시', 0),
         ('연결: 재사용 (15편)', 0),
         ('HTML 확인: 엣지가 304 (16편)', EDGE),
         ('스크립트·이미지: 캐시, 요청 없음', 0)]

for title, steps in [('첫 방문', first), ('다음 날 다시 방문', again)]:
    print(f'{title}: 첫 바이트까지 {sum(ms for _, ms in steps)}ms')
    for name, ms in steps:
        print(f'  {ms:>3}ms  {name}')
```
```text
첫 방문: 첫 바이트까지 300ms
   40ms  이름 풀이 (8편)
   20ms  TCP 연결 (7편)
   20ms  TLS 핸드셰이크 (10편)
   20ms  요청과 엣지 왕복 (9편)
  150ms  캐시 없음: 원본까지 (16편, 18편)
   50ms  서버 처리와 렌더링 (5편)
다음 날 다시 방문: 첫 바이트까지 20ms
    0ms  이름 풀이: 캐시
    0ms  연결: 재사용 (15편)
   20ms  HTML 확인: 엣지가 304 (16편)
    0ms  스크립트·이미지: 캐시, 요청 없음
```
첫 방문의 300ms 가운데 절반은 엣지에서 원본까지의 먼 길이고, 나머지 대부분은 왕복이다. 계산 자체(50ms)는 작다. 다시 방문할 때는 캐시와 연결 재사용 덕분에 20ms로 줄었다. 실제로는 연결이 하루 동안 살아 있지 않으므로 TCP와 TLS가 다시 들지만, 그래도 원본까지 가지 않는다는 점이 결정적이다. 웹의 성능은 대부분 **얼마나 빨리 계산하느냐**보다 **얼마나 덜 오가느냐**의 문제다.

## 세 질문에 대한 답
1편에서 던진 세 질문으로 돌아가 보자.
- **어떻게 설치 없이 복잡한 일을 하게 되었나**: 클라이언트를 브라우저 하나로 통일하고(1편), 그 안에 빠른 자바스크립트 엔진과 이벤트 루프(2편), 안전한 울타리(3편), 데이터만 주고받는 구조(4편), 렌더링 위치의 선택(5편), 저장소·서비스 워커·WebAssembly(6편)를 채웠다.
- **어떻게 서버와 대화하며 업무를 처리하나**: 패킷과 TCP(7편), 이름 풀이(8편), HTTP의 약속(9편), 암호(10편), 로그인(11편), API 계약(12편), 실시간 통로(13편), 오래 걸리는 일과 멱등성(14편) 위에서 대화한다.
- **잦은 패킷과 트래픽을 어떻게 관리하나**: 연결을 아끼고(15편), 다시 받지 않고(16편), 작게 보내고(17편), 나눠 받고(18편), 넘치면 줄이고 거절한다(19편).

## 흔한 오해
- "웹이 느린 건 서버가 느려서다": 서버 처리는 전체 시간의 일부인 경우가 많다. 구간별로 재 보면 이름 풀이, 핸드셰이크, 먼 원본까지의 왕복, 큰 스크립트의 해석이 더 긴 경우가 흔하다.
- "이 구조는 너무 복잡해서 작은 서비스와는 상관없다": 정적 파일을 호스팅 서비스에 올리기만 해도 HTTPS, HTTP/2, CDN, 압축, 캐시 헤더가 대부분 자동으로 붙는다. 무엇이 일어나는지 알면 설정 하나를 바꿀 때 무엇이 달라지는지 안다.
- "한 번 배우면 끝이다": 프로토콜과 브라우저는 계속 바뀐다. 그래도 왕복을 줄이고, 사본을 쓰고, 넘치면 거절하는 원리는 수십 년째 그대로다.

## 정리
- 클릭 한 번은 캐시 확인 → DNS → TCP·TLS(또는 QUIC) → HTTP 요청 → CDN·로드 밸런서·앱 서버·데이터베이스 → 응답 → 파싱·렌더링·하이드레이션을 지난다.
- curl의 구간별 시각으로 어느 구간이 긴지 재면, 어느 기술이 필요한지 보인다.
- 첫 방문은 왕복과 먼 원본이 지배하고, 다시 방문은 캐시와 연결 재사용이 지배한다.
- 웹 앱의 원리는 결국 일을 나누고(1~6편), 약속대로 대화하고(7~14편), 덜 오가게 만드는(15~19편) 것이다.
