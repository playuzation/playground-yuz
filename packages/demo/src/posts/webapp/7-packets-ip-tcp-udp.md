## 질문: GET 한 줄은 어떻게 저 멀리 서버에 닿을까
1편에서 curl이 보낸 `GET /`는 같은 컴퓨터 안에서 오갔다. 진짜 서비스라면 그 몇십 바이트가 집의 공유기, 통신사의 장비 여러 대, 바다 밑 케이블을 지나 다른 대륙의 데이터센터에 닿고, 응답은 다른 길로 돌아올 수도 있다. 그 과정을 하나의 큰 장치가 맡는 것이 아니라, 각자 한 가지만 책임지는 **층**(layer)들이 나눠 맡는다.
```text
HTTP  : GET /index.html ...
TCP   : port 51000 → 443, order
IP    : 192.168.0.10 → 203.0.113.80
link  : Wi-Fi / Ethernet frame
```
보내는 쪽에서는 위층의 데이터를 아래층이 자기 머리말(헤더)을 붙여 감싸고, 받는 쪽에서는 아래층부터 벗겨 위로 올린다. 편지를 봉투에 넣고 그 봉투를 다시 우체국 행낭에 넣는 것과 비슷하다. 비유가 깨지는 곳도 있다. 편지 한 통은 한 덩어리로 가지만, 네트워크의 데이터는 잘게 잘려 조각마다 따로 간다.

## 패킷 교환과 IP
인터넷은 회선을 통째로 잡아 두는 전화와 달리 데이터를 **패킷**(packet)으로 잘라 보낸다. 이더넷과 와이파이에서 패킷 하나는 보통 최대 1,500바이트쯤이다. 패킷마다 IP 헤더가 붙고, 거기에 출발지와 목적지 **IP 주소**가 적힌다. 길 위의 **라우터**(router)는 목적지 주소만 보고 "이 방향으로 한 칸"을 정해 넘긴다. 전체 경로를 아는 장치는 없다. 각자 다음 칸만 안다. 그래서 일부 장비가 고장 나도 다른 길로 돌아갈 수 있다.

IPv4 주소는 32비트라 약 43억 개뿐이어서 집과 회사 안에서는 사설 주소(192.168.x.x 같은)를 쓰고 공유기가 바깥 주소 하나로 바꿔 내보낸다(NAT). 128비트 주소를 쓰는 IPv6가 그 부족을 근본적으로 푼다. IP 헤더의 **TTL**(time to live)은 라우터를 지날 때마다 1씩 줄어들고 0이 되면 버려지는 숫자로, 길을 잃은 패킷이 영원히 떠돌지 않게 한다.

IP는 "최선을 다해 전달한다"는 약속만 한다. 패킷은 사라질 수 있고, 순서가 바뀔 수 있고, 같은 것이 두 번 올 수도 있다. 이 불완전한 바탕 위에서 믿을 만한 통신을 만드는 것이 TCP다. 빈트 서프와 로버트 칸이 1974년 논문에서 이 구조를 제안했고, 1983년 1월 1일 미국의 연구용 네트워크 ARPANET이 TCP/IP로 전환했다.

## TCP: 끊김 없는 바이트의 흐름
**TCP**(Transmission Control Protocol)는 두 프로그램 사이에 **연결**을 만들고, 보낸 바이트에 번호(순서 번호)를 붙인다. 받는 쪽은 "여기까지 받았다"는 확인(ACK)을 돌려보내고, 확인이 오지 않은 조각은 보내는 쪽이 다시 보낸다. 받는 쪽은 번호를 보고 순서를 맞춰 프로그램에 넘긴다. 그래서 프로그램은 잘린 패킷을 의식하지 않고 파일을 읽듯 바이트를 읽는다. 받는 쪽이 감당할 만큼만 보내는 흐름 제어와, 네트워크가 막히지 않을 만큼만 보내는 혼잡 제어(19편)도 TCP가 한다.

연결을 여는 데에는 대가가 있다. 데이터를 보내기 전에 세 번의 신호를 주고받는 **3방향 핸드셰이크**를 한다.
```text
client          server
  │── SYN ──────→ │
  │←─ SYN+ACK ─── │
  │── ACK + data →│
```
클라이언트가 실제 요청을 보낼 수 있을 때까지 왕복 한 번(RTT)이 든다. 서울과 미국 동부 사이의 왕복이 대략 150~200ms라면, 연결 하나를 여는 데만 그만큼이 쓰인다. 연결을 재사용하고(15편), 서버를 사용자 가까이 두는(16편) 기술이 중요한 이유다.

## UDP와 포트
**UDP**(User Datagram Protocol)는 연결도, 순서도, 재전송도 없다. 데이터그램 하나를 보내면 그만이다. 대신 핸드셰이크가 없어 빠르고, 늦게 도착한 데이터가 쓸모없는 일(영상 통화의 지나간 프레임, 게임의 지난 위치)에 맞는다. DNS 질의(8편)와 HTTP/3의 바탕인 QUIC(15편)도 UDP 위에서 돈다.

TCP와 UDP 헤더에는 **포트**(port) 번호가 있다. IP 주소가 컴퓨터를 고른다면 포트는 그 안의 프로그램을 고른다. 16비트라 0~65535이고, 잘 알려진 번호가 있다(HTTP 80, HTTPS 443, DNS 53). 서버는 정해진 포트에서 기다리고(listen), 클라이언트는 운영체제가 그때그때 골라 준 **임시 포트**를 쓴다. TCP 연결 하나는 출발 주소, 출발 포트, 도착 주소, 도착 포트 네 가지로 구별된다. 그래서 한 서버의 443번 포트가 수만 개의 연결을 동시에 받을 수 있다.

## 직접 해 보기 1: 헤더 40바이트를 손으로
노트북(192.168.0.10)이 웹 서버(203.0.113.80, 문서용 예시 주소)의 443번 포트에 연결을 시작할 때 보내는 첫 패킷의 IP 헤더와 TCP 헤더를 직접 만든다. 코드를 몰라도 아래 해석 부분만 보면 된다.
```python
import socket, struct

def checksum(data):                    # IP 헤더 체크섬: 16비트씩 더하고 뒤집기
    total = sum(struct.unpack(f'!{len(data) // 2}H', data))
    while total >> 16:
        total = (total & 0xFFFF) + (total >> 16)
    return ~total & 0xFFFF

src, dst = socket.inet_aton('192.168.0.10'), socket.inet_aton('203.0.113.80')
ip = struct.pack('!BBHHHBBH4s4s',
                 0x45, 0, 40,          # 버전 4·헤더 20바이트, 서비스 종류, 전체 길이
                 0x1C46, 0x4000,       # 식별 번호, "자르지 말 것" 표시
                 64, 6, 0, src, dst)   # TTL, 프로토콜 6(TCP), 체크섬 자리, 주소
ip = ip[:10] + struct.pack('!H', checksum(ip)) + ip[12:]
tcp = struct.pack('!HHIIBBHHH',
                  51000, 443,          # 출발 포트(임시), 도착 포트(HTTPS)
                  1000, 0,             # 순서 번호, 확인 번호
                  5 << 4, 0x02,        # 헤더 20바이트, 플래그 SYN
                  64240, 0, 0)         # 받을 수 있는 양, 체크섬(생략), 긴급 포인터
packet = ip + tcp
for i in range(0, len(packet), 20):
    print(packet[i:i + 20].hex(' '))

v, _, total, _, _, ttl, proto, csum, s, d = struct.unpack('!BBHHHBBH4s4s', ip)
sport, dport, seq, _, _, flags, *_ = struct.unpack('!HHIIBBHHH', tcp)
print(f'IP 버전 {v >> 4}, 전체 {total}바이트, TTL {ttl}, 프로토콜 {proto}(TCP)')
print(f'{socket.inet_ntoa(s)}:{sport} → {socket.inet_ntoa(d)}:{dport}')
print(f'TCP 플래그 SYN={flags & 2 > 0}, 순서 번호 {seq}')
print(f'체크섬 0x{csum:04x}, 받는 쪽 검사 결과 {checksum(ip)} (0이면 정상)')
```
```text
45 00 00 28 1c 46 40 00 40 06 21 87 c0 a8 00 0a cb 00 71 50
c7 38 01 bb 00 00 03 e8 00 00 00 00 50 02 fa f0 00 00 00 00
IP 버전 4, 전체 40바이트, TTL 64, 프로토콜 6(TCP)
192.168.0.10:51000 → 203.0.113.80:443
TCP 플래그 SYN=True, 순서 번호 1000
체크섬 0x2187, 받는 쪽 검사 결과 0 (0이면 정상)
```
첫 줄 20바이트가 IP 헤더다. `c0 a8 00 0a`는 192.168.0.10, `cb 00 71 50`은 203.0.113.80이다. 둘째 줄이 TCP 헤더로, `c7 38`은 51000번, `01 bb`는 443번이다. 받는 쪽은 체크섬까지 포함해 다시 더해 0이 나오면 헤더가 깨지지 않았다고 판단한다. 아직 HTTP는 한 글자도 없다. 이 SYN 패킷과 핸드셰이크가 끝나야 첫 요청이 실린다.

## 직접 해 보기 2: 포트와 메시지 경계
이번에는 운영체제의 소켓으로 같은 컴퓨터 안에서 TCP와 UDP를 써 본다.
```python
import socket, threading, time

srv = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(('127.0.0.1', 8007)); srv.listen()
got = {}
def serve():
    conn, peer = srv.accept()
    got['peer'] = peer
    time.sleep(0.2)                    # 세 번 보낸 데이터가 모두 도착하게 기다림
    got['data'] = conn.recv(1024)
    conn.close()
t = threading.Thread(target=serve); t.start()

cli = socket.create_connection(('127.0.0.1', 8007))
local = cli.getsockname()
for msg in [b'hello;', b'web;', b'app;']:
    cli.sendall(msg)                   # TCP로 세 번 나눠 보낸다
t.join(); cli.close(); srv.close()
print('클라이언트 포트는 임시 번호:', local[1] >= 1024)
print('서버가 본 상대 포트도 같은 번호:', got['peer'][1] == local[1])
print('TCP 수신 한 번에 받은 것:', got['data'])

u_srv = socket.socket(socket.AF_INET, socket.SOCK_DGRAM); u_srv.bind(('127.0.0.1', 8008))
u_cli = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
for msg in [b'hello;', b'web;', b'app;']:
    u_cli.sendto(msg, ('127.0.0.1', 8008))  # UDP로 세 번 보낸다
time.sleep(0.2)
print('UDP 수신:', [u_srv.recv(1024) for _ in range(3)])
```
```text
클라이언트 포트는 임시 번호: True
서버가 본 상대 포트도 같은 번호: True
TCP 수신 한 번에 받은 것: b'hello;web;app;'
UDP 수신: [b'hello;', b'web;', b'app;']
```
TCP로 세 번 보낸 데이터가 한 번에 붙어서 읽혔다. TCP는 바이트의 순서는 지키지만 "어디까지가 메시지 하나인지"는 기억하지 않는다. 그래서 그 위의 프로토콜이 경계를 정한다. HTTP는 헤더 끝을 빈 줄로, 본문 길이를 `Content-Length`로 알려 준다(9편). UDP는 보낸 단위 그대로 받았지만, 실제 네트워크에서는 그중 일부가 사라지거나 순서가 바뀌어도 알려 주지 않는다.

## 흔한 오해
- "인터넷에는 서버까지 정해진 길이 있다": 라우터마다 다음 칸만 정하고, 길은 상황에 따라 바뀐다. 가는 길과 오는 길이 다를 수도 있다.
- "TCP는 느리고 UDP는 빠르다": UDP는 핸드셰이크와 재전송이 없을 뿐이다. 신뢰성이 필요하면 그 기능을 UDP 위에 다시 만들어야 하고, 그것이 QUIC이다(15편).
- "포트를 막으면 그 서비스가 안전하다": 포트는 프로그램을 고르는 번호일 뿐이다. 열려 있는 포트의 프로그램이 안전한지는 별개의 문제다.

## 정리
- 네트워크는 층으로 나뉜다. 링크가 옆 장비까지, IP가 목적지 컴퓨터까지, TCP·UDP가 프로그램까지, HTTP가 요청의 뜻을 맡는다.
- 데이터는 패킷으로 잘려 라우터를 한 칸씩 지난다. IP는 최선을 다할 뿐 전달을 보장하지 않는다.
- TCP는 순서 번호·확인·재전송으로 믿을 만한 바이트 흐름을 만들지만, 연결을 여는 데 왕복 한 번이 들고 메시지 경계는 기억하지 않는다.
- UDP는 보내고 잊는다. 포트 번호가 받을 프로그램을 고른다.
