# [웹 앱의 원리 1/20] 클라이언트와 서버가 나뉘기까지: 터미널, 설치형 프로그램, 그리고 웹

> **한 줄 요약** — 컴퓨팅은 "중앙의 큰 컴퓨터와 화면만 있는 터미널"에서 "각자 설치하는 프로그램"으로 갔다가, 웹 브라우저라는 범용 클라이언트 하나만 설치하면 앱은 서버에서 그때그때 받아 오는 모양으로 다시 나뉘었다.

## 이 글에서 다루는 것
- 클라이언트(client)와 서버(server)라는 역할 나누기
- 터미널 → 설치형 프로그램 → 클라이언트·서버 → 웹으로 이어진 흐름
- 웹의 세 기둥: URL, HTTP, HTML
- 직접 해 보기: 내 컴퓨터를 서버로 만들고, 설치 없이 앱 업데이트하기
- 흔한 오해: "웹 앱은 아무것도 내려받지 않는다"

## 질문: 설치하지 않은 프로그램은 어떻게 내 화면에서 돌아갈까
문서 편집기, 지도, 메일, 은행 업무를 우리는 대부분 브라우저 탭 하나로 처리한다. 설치 파일을 받은 적도, 업데이트 버튼을 누른 적도 없는데 기능은 매주 바뀐다. 이 시리즈는 그것이 어떻게 가능한지를 세 갈래로 풀어 간다. 첫째, 일을 나누는 방식(1~6편). 둘째, 나뉜 두 쪽이 대화하는 방식(7~14편). 셋째, 그 대화가 수십억 번 오갈 때 트래픽을 감당하는 기술(15~19편). 마지막 20편에서 주소창에 주소를 입력한 순간부터 화면이 뜰 때까지를 한 번에 따라간다.

먼저 낱말 두 개를 정한다. **클라이언트**는 요청하는 쪽, **서버**는 요청을 받아 처리하고 응답하는 쪽이다. 둘은 기계의 종류가 아니라 **역할**이다. 같은 노트북이 브라우저를 띄우면 클라이언트이고, 프로그램 하나를 띄워 요청을 받으면 서버가 된다. 아래 실습에서 실제로 그렇게 해 본다.

## 터미널의 시대: 계산은 모두 중앙에서
1960~70년대의 컴퓨터는 방 하나를 차지하는 비싼 기계였다. 여러 사람이 한 대를 나눠 쓰도록 **시분할**(time-sharing) 운영체제가 짧은 시간 조각을 사용자마다 돌아가며 내주었고, 사용자 앞에는 화면과 키보드만 있는 **터미널**(terminal)이 놓였다. 터미널은 누른 글자를 보내고 돌아온 글자를 보여 줄 뿐, 계산과 저장은 모두 중앙 컴퓨터가 했다. 프로그램을 고치면 중앙 한 곳만 바꾸면 되니 관리는 쉬웠지만, 중앙이 느려지면 모두가 느려졌고 화면은 글자뿐이었다.

## 개인용 컴퓨터와 설치형 프로그램
1980년대에 개인용 컴퓨터가 퍼지면서 계산이 책상 위로 내려왔다. 워드프로세서와 스프레드시트는 디스크로 사서 각자 설치했고, 그림이 있는 화면과 마우스가 표준이 되었다. 대신 배포가 어려워졌다. 새 버전이 나오면 모든 컴퓨터에 다시 설치해야 했고, 운영체제와 라이브러리 버전이 다르면 같은 프로그램이 다르게 돌았다. 회사들은 화면과 업무 규칙은 각자의 PC에 설치하고 데이터만 중앙의 데이터베이스 서버에 두는 **클라이언트·서버** 구조를 많이 썼다. 데이터는 한 곳에 모였지만 설치와 업데이트 문제는 그대로였다.

## 웹: 클라이언트를 하나로 통일하다
1989년 3월 CERN의 팀 버너스리가 정보 공유 시스템 제안서를 썼고, 1990년 말 첫 브라우저와 서버가 CERN에서 돌기 시작했으며, 1991년 8월 외부에 공개되었다. 1993년 4월 30일 CERN은 웹 기술을 누구나 쓸 수 있게 공개(퍼블릭 도메인)했다. 웹은 세 가지 약속으로 이루어진다.
- **URL**: 자원의 주소. `http://127.0.0.1:8001/index.html`은 "이 컴퓨터의 8001번 포트에 있는 서버에게 `/index.html`을 달라"는 뜻이다.
- **HTTP**: 요청과 응답을 주고받는 약속. "GET /index.html" 같은 글자로 된 요청을 보내면 상태 코드와 본문이 돌아온다(9편).
- **HTML**: 화면에 무엇을 어떻게 보여 줄지 적는 문서 형식. 브라우저가 이것을 읽어 그린다.

핵심은 클라이언트가 **브라우저 하나로 통일**되었다는 점이다. 사용자는 브라우저만 한 번 설치하고, 개별 앱은 주소를 열 때마다 서버에서 받아 온다. 서버 쪽 파일을 바꾸면 다음 요청부터 모두가 새 버전을 받는다. 터미널 시대의 "중앙에서 한 번에 고친다"는 장점과 PC 시대의 "그림 있는 화면을 내 기계가 그린다"는 장점을 함께 얻은 셈이다.
```text
1970s  terminal ──→ mainframe
       (keys, text)  (all work)
1990s  installed app ──→ DB server
       (UI + rules)      (data)
2010s  browser ──→ web server ──→ DB
       (UI, JS)    (rules, API)
```

## 직접 해 보기: 내 컴퓨터를 서버로
파이썬 3와 curl만 있으면 된다(리눅스·맥, 윈도우는 WSL). 코드를 읽지 못해도 괜찮다. 출력만 보자. 먼저 "앱" 역할을 할 HTML 파일을 만들고, 파이썬에 들어 있는 작은 웹 서버를 띄운다.
```bash
mkdir -p site && cd site
printf '<!doctype html>\n<title>메모</title>\n<p>버전 1</p>\n' > index.html
python3 -m http.server 8001 --bind 127.0.0.1 > ../server.log 2>&1 &
sleep 1
curl -s http://127.0.0.1:8001/
```
```text
<!doctype html>
<title>메모</title>
<p>버전 1</p>
```
`python3 -m http.server`가 서버 역할을, `curl`이 클라이언트 역할을 했다. 브라우저로 같은 주소를 열면 "버전 1"이 화면에 그려진다. 이제 서버 쪽 파일만 고치고, 클라이언트는 아무것도 설치하지 않은 채 같은 주소를 다시 요청한다.
```bash
sed -i.bak 's/버전 1/버전 2: 검색 기능 추가/' index.html
curl -s http://127.0.0.1:8001/ | tail -1
```
```text
<p>버전 2: 검색 기능 추가</p>
```
이것이 웹 앱의 "업데이트"다. 사용자 수가 백만 명이어도 서버 한 곳을 바꾸면 끝난다. 서버는 받은 요청을 기록해 두었다.
```bash
cat ../server.log
```
```text
Serving HTTP on 127.0.0.1 port 8001 (http://127.0.0.1:8001/) ...
127.0.0.1 - - […] "GET / HTTP/1.1" 200 -
127.0.0.1 - - […] "GET / HTTP/1.1" 200 -
```
첫 줄은 서버가 켜질 때 남긴 안내이고, 그 아래가 두 번의 요청이다. 두 요청이 모두 `GET /`이고 결과는 `200`(성공)이다. 이 한 줄에 이 시리즈의 주제가 들어 있다. 누가(127.0.0.1) 어떤 방식으로(GET, HTTP/1.1) 무엇을(/) 요청했고 서버가 어떻게 답했는지(200). 응답에 붙어 온 머리말(헤더)도 보자.
```bash
curl -sI http://127.0.0.1:8001/ | grep -iE '^(HTTP|Content-Type|Content-Length)'
```
```text
HTTP/1.0 200 OK
Content-type: text/html
Content-Length: 76
```
`Content-type: text/html`은 "이 본문은 HTML이니 화면으로 그려라"는 표시다. 브라우저는 이 표시를 보고 받은 바이트를 문서로 해석한다. 76바이트는 한글이 글자당 3바이트(UTF-8)라서 글자 수보다 크다. 첫 줄의 `HTTP/1.0`은 이 간단한 서버가 오래된 방식(요청 하나마다 연결을 닫는다)으로 답한다는 뜻인데, 그 차이가 왜 중요한지는 15편에서 다룬다.

## 얇은 클라이언트와 두꺼운 클라이언트
일을 어느 쪽이 얼마나 하느냐에 따라 클라이언트를 얇다(thin)·두껍다(thick)고 부른다. 터미널은 아주 얇은 클라이언트였고, 설치형 프로그램은 두꺼운 클라이언트였다. 초기 웹 브라우저는 문서를 보여 주기만 하는 얇은 쪽이었지만, 자바스크립트가 들어오고(2편) 화면 일부만 바꾸는 기법이 퍼지면서(4편) 다시 두꺼워졌다. 지금의 웹 앱은 화면 그리기와 입력 처리를 브라우저에서, 데이터 보관과 권한 확인과 무거운 계산을 서버에서 한다. 어디까지 나눌지는 정답이 없고, 5편에서 보듯 앱마다 고른다. 다만 한 가지 원칙은 바뀌지 않는다. 클라이언트는 사용자의 손에 있으므로 믿을 수 없고, 돈·권한·데이터의 최종 판단은 서버가 한다.

## 흔한 오해
- "웹 앱은 아무것도 내려받지 않는다": 아니다. 매번 HTML·자바스크립트·이미지를 내려받아 내 컴퓨터에서 실행한다. 다만 설치 과정이 없고, 받은 것을 캐시에 두었다가 바뀐 것만 다시 받는다(16편). "설치하지 않는다"가 정확하고, "실행하지 않는다"는 틀린 말이다.
- "서버는 특별한 컴퓨터다": 서버는 역할이다. 위에서 노트북의 파이썬 프로그램 하나가 서버였다. 데이터센터의 서버는 그 역할을 하루 종일 많은 요청에 대해 하도록 만든 컴퓨터일 뿐이다.
- "인터넷과 웹은 같은 말이다": 인터넷은 컴퓨터끼리 패킷을 주고받는 네트워크(7편)이고, 웹은 그 위에서 URL·HTTP·HTML로 문서와 앱을 주고받는 서비스 하나다. 메일과 게임 통신도 인터넷을 쓰지만 웹은 아니다.

## 정리
- 클라이언트는 요청하는 역할, 서버는 처리하고 응답하는 역할이다. 기계의 종류가 아니다.
- 터미널(중앙 처리) → 설치형 프로그램(각자 처리) → 클라이언트·서버(데이터만 중앙)를 지나, 웹은 클라이언트를 브라우저 하나로 통일했다.
- URL로 찾고, HTTP로 주고받고, HTML로 그린다. 서버 파일을 바꾸면 모든 사용자가 다음 요청에서 새 버전을 받는다.
- 웹 앱도 코드를 내려받아 내 기계에서 실행한다. 다르지 않은 것은 실행이고, 다른 것은 설치와 배포다.

## 시리즈 안내
1. **클라이언트와 서버가 나뉘기까지: 터미널, 설치형 프로그램, 그리고 웹** ← 지금 읽는 글
2. 브라우저 안에서 앱이 도는 방식: JavaScript 엔진, DOM, 이벤트 루프
3. 설치 없이도 안전한 이유: 샌드박스, 동일 출처 정책, CORS
4. 문서에서 앱으로: AJAX, fetch, 싱글 페이지 앱
5. 화면을 어디서 그릴까: 서버 렌더링, 클라이언트 렌더링, 하이드레이션
6. 설치 앱에 가까워진 웹: 브라우저 저장소, 서비스 워커, PWA, WebAssembly
7. 패킷이 목적지에 닿기까지: IP, TCP, UDP, 포트
8. 이름을 주소로 바꾸는 DNS: 질의, 캐시, TTL
9. HTTP 요청과 응답 해부: 메서드, 상태 코드, 헤더
10. HTTPS와 TLS: 암호화, 인증서, 핸드셰이크
11. 상태 없는 HTTP 위의 로그인: 쿠키, 세션, 토큰
12. API를 설계하는 방식: REST, GraphQL, gRPC
13. 실시간 통신: 폴링, 서버 전송 이벤트, 웹소켓
14. 오래 걸리는 업무 처리: 작업 큐, 재시도, 멱등 키
15. 연결을 아끼는 HTTP의 진화: keep-alive, HTTP/2, HTTP/3
16. 다시 받지 않기: 브라우저 캐시, ETag, CDN
17. 작게 보내기: 압축, 코드 분할, 페이지네이션
18. 트래픽을 나누는 장치: 리버스 프록시와 로드 밸런서
