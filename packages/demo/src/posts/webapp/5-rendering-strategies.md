# [웹 앱의 원리 5/20] 화면을 어디서 그릴까: 서버 렌더링, 클라이언트 렌더링, 하이드레이션

> **한 줄 요약** — 같은 화면도 서버가 완성된 HTML로 만들어 보낼 수 있고(서버 렌더링), 빈 틀과 자바스크립트를 보내 브라우저가 만들게 할 수도 있으며(클라이언트 렌더링), 서버가 그린 HTML에 브라우저가 나중에 동작을 붙이는 하이드레이션으로 두 장점을 섞기도 한다.

## 이 글에서 다루는 것
- 클라이언트 렌더링(CSR): 빈 틀 + 자바스크립트
- 서버 렌더링(SSR)과 정적 생성(SSG)
- 하이드레이션: 그려진 HTML에 생명 불어넣기
- 직접 해 보기: 자바스크립트를 실행하지 않는 클라이언트에게 각각 무엇이 보이나, 첫 화면까지 걸리는 시간 어림
- 무엇을 고를까

## 렌더링이란
여기서 **렌더링**(rendering)은 "데이터를 화면용 HTML(정확히는 DOM)로 바꾸는 일"을 말한다. 할 일 목록이라는 데이터 `["우유 사기", "책 반납"]`가 `<ul><li>우유 사기</li>…</ul>`가 되는 단계다. 이 일을 어디서 하느냐에 따라 사용자가 첫 화면을 보는 시점, 서버가 지는 부담, 검색 엔진이 보는 내용이 달라진다.

## 클라이언트 렌더링: 브라우저가 만든다
4편의 싱글 페이지 앱이 기본적으로 쓰는 방식이다. 서버는 `<div id="app"></div>`처럼 비어 있는 HTML과 자바스크립트 묶음을 보낸다. 브라우저는 스크립트를 받아 실행하고, 스크립트가 API로 데이터를 받아 DOM을 만든다. 서버는 정적 파일만 주면 되니 가볍고, 그 뒤 화면 전환은 빠르다. 대신 첫 화면까지 거쳐야 할 왕복이 많다. HTML을 받고, 스크립트를 받고, 스크립트를 실행하고, 데이터를 받고, 그제야 그린다.

## 서버 렌더링과 정적 생성: 서버가 만든다
**서버 렌더링**(SSR, server-side rendering)에서는 요청이 오면 서버가 데이터베이스에서 데이터를 읽어 완성된 HTML을 만들어 보낸다. 브라우저는 받자마자 내용을 그릴 수 있다. 사실 웹의 처음 방식이 이것이었다(4편의 전통적인 웹). 요청마다 서버가 HTML을 만드는 비용이 든다.

**정적 생성**(SSG, static site generation)은 요청이 오기 전, 빌드할 때 미리 HTML 파일로 만들어 두는 방식이다. 블로그 글이나 문서처럼 모든 사람에게 같은 내용을 보여 주는 페이지에 맞는다. 서버는 파일만 주면 되므로 가장 가볍고, CDN에 올려 두기도 쉽다(16편). 이 사이트의 읽기 페이지도 글을 빌드할 때 HTML로 만들어 둔 것이다. 대신 내용이 바뀌면 다시 빌드해야 하고, 사용자마다 다른 화면(내 장바구니)에는 그대로 쓸 수 없다.

## 하이드레이션: 그림에 동작을 붙이기
서버가 그린 HTML은 보이기는 하지만 그 자체로는 움직이지 않는다. 버튼을 눌렀을 때 무엇을 할지는 자바스크립트가 정한다. 그래서 요즘의 많은 프레임워크는 첫 화면은 서버가 그리고, 그다음에 같은 화면 코드를 브라우저에서도 실행해 이미 있는 DOM에 이벤트 처리기를 붙이고 상태를 이어받는다. 마른 화면에 물을 붓는다는 뜻으로 **하이드레이션**(hydration)이라고 부른다. 그 뒤로는 SPA처럼 동작한다.

하이드레이션에도 비용이 있다. 서버가 이미 그린 화면을 위해 브라우저가 같은 코드를 다시 내려받아 실행해야 하고, 그 작업이 끝나기 전에는 화면이 보이는데 눌러도 반응하지 않는 시간이 생긴다. 그래서 페이지 전체가 아니라 움직이는 부분만 골라 하이드레이션하거나(아일랜드 방식), HTML을 완성되는 대로 조각조각 흘려보내는(스트리밍) 방법들이 쓰인다. 기본 생각은 같다. 보이는 것은 빨리, 움직이는 것은 필요한 만큼만.

## 직접 해 보기 1: 자바스크립트를 실행하지 않는 클라이언트
검색 엔진 로봇이나 미리 보기를 만드는 메신저 같은 클라이언트는 자바스크립트를 아예 실행하지 않거나 늦게 실행한다. curl도 그렇다. 같은 할 일 목록을 두 방식으로 주는 서버를 만들어, curl에게 무엇이 보이는지 확인한다. 코드는 훑어만 보자.
```python
# 파일: render_server.py
import json
from http.server import BaseHTTPRequestHandler, HTTPServer

ITEMS = ['우유 사기', '책 반납', '운동']

def render(items):                       # 데이터 → HTML (서버·브라우저 공용 규칙)
    return '<ul>' + ''.join(f'<li>{t}</li>' for t in items) + '</ul>'

CSR = ('<!doctype html><div id="app"></div>'
       '<script>fetch("/api/items").then(r => r.json())'
       '.then(items => app.innerHTML = renderList(items))</script>')
SSR = '<!doctype html><div id="app">' + render(ITEMS) + '</div><script src="/app.js"></script>'

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        body = {'/csr': CSR, '/ssr': SSR,
                '/api/items': json.dumps(ITEMS, ensure_ascii=False)}[self.path].encode()
        self.send_response(200)
        self.send_header('Content-Length', str(len(body)))
        self.end_headers()
        self.wfile.write(body)

    def log_message(self, *args):
        pass

HTTPServer(('127.0.0.1', 8005), Handler).serve_forever()
```
```bash
python3 render_server.py &
sleep 1
for p in csr ssr; do
  n=$(curl -s http://127.0.0.1:8005/$p | grep -o '<li>' | wc -l)
  echo "$p: 첫 응답에 할 일 $n개"
done
curl -s http://127.0.0.1:8005/ssr | grep -o '<ul>.*</ul>'
```
```text
csr: 첫 응답에 할 일 0개
ssr: 첫 응답에 할 일 3개
<ul><li>우유 사기</li><li>책 반납</li><li>운동</li></ul>
```
클라이언트 렌더링 페이지의 첫 응답에는 할 일이 하나도 없다. 내용은 스크립트를 실행하고 API를 한 번 더 불러야 생긴다. 서버 렌더링 페이지는 첫 응답에 내용이 모두 들어 있다. 자바스크립트를 실행하는 브라우저에서는 둘 다 결국 같은 화면이 되지만, **언제** 보이느냐와 **누구에게** 보이느냐가 다르다.

## 직접 해 보기 2: 첫 화면까지의 시간 어림
왕복 한 번(RTT)이 100ms인 모바일 네트워크를 가정하고, 각 방식이 첫 내용을 보여 주기까지 몇 번 왕복하는지 세어 본다. 수치는 설명용으로 정한 가상의 값이다.
```python
RTT = 100            # 왕복 한 번(ms), 가상의 값
JS_RUN = 150         # 큰 자바스크립트 묶음 실행 시간
SERVER_RENDER = 40   # 서버가 HTML을 만드는 시간
HYDRATE = 120        # 브라우저가 하이드레이션하는 시간

csr_visible = RTT + RTT + JS_RUN + RTT            # HTML → JS → 실행 → API
csr_interactive = csr_visible
ssr_visible = RTT + SERVER_RENDER                 # 완성된 HTML 한 번
ssr_interactive = ssr_visible + RTT + HYDRATE     # 그다음 JS를 받아 하이드레이션
ssg_visible = RTT                                 # 미리 만든 파일

print(f'CSR  첫 내용 {csr_visible}ms, 반응 {csr_interactive}ms')
print(f'SSR  첫 내용 {ssr_visible}ms, 반응 {ssr_interactive}ms')
print(f'SSG  첫 내용 {ssg_visible}ms (움직임이 필요하면 SSR처럼 JS가 더 든다)')
```
```text
CSR  첫 내용 450ms, 반응 450ms
SSR  첫 내용 140ms, 반응 360ms
SSG  첫 내용 100ms (움직임이 필요하면 SSR처럼 JS가 더 든다)
```
서버 렌더링은 내용을 훨씬 빨리 보여 주지만, 보이는 순간과 눌러서 반응하는 순간 사이에 틈(140ms → 360ms)이 있다. 클라이언트 렌더링은 늦게 보이는 대신 보이는 순간 바로 반응한다. 실제 숫자는 네트워크, 기기 성능, 스크립트 크기에 따라 크게 달라지지만, 왕복 횟수를 세어 보는 습관은 그대로 쓸 수 있다. 왕복을 줄이는 기술은 15~17편의 주제다.

## 무엇을 고를까
| 방식 | 잘 맞는 화면 | 주의할 점 |
| --- | --- | --- |
| CSR | 로그인 뒤 대시보드, 편집기 | 첫 화면이 늦다 |
| SSR | 상품 목록, 검색 결과 | 요청마다 서버 비용 |
| SSG | 블로그, 문서, 소개 페이지 | 바뀌면 다시 빌드 |

한 사이트 안에서도 섞어 쓴다. 소개 페이지는 정적 생성, 상품 페이지는 서버 렌더링, 로그인한 뒤의 관리 화면은 클라이언트 렌더링처럼. 기준은 "이 화면을 누가, 얼마나 자주 바뀌는 데이터로, 얼마나 빨리 봐야 하나"다.

## 흔한 오해
- "SSR이 CSR보다 항상 빠르다": 첫 내용은 보통 빠르지만, 서버가 느린 데이터베이스를 기다리면 HTML 첫 바이트부터 늦어진다. 하이드레이션 전에는 눌러도 반응이 없을 수 있다.
- "하이드레이션은 화면을 다시 그리는 것이다": 이미 있는 DOM을 재사용하고 동작만 붙이는 것이 목적이다. 서버와 브라우저가 그린 결과가 다르면 프레임워크가 경고를 내거나 그 부분을 다시 그린다.
- "정적 사이트는 동적인 기능을 못 넣는다": 페이지는 미리 만들어 두고, 댓글이나 좋아요처럼 바뀌는 부분만 자바스크립트로 API를 불러 채울 수 있다.

## 정리
- 렌더링은 데이터를 화면용 HTML로 바꾸는 일이고, 그 장소를 고를 수 있다.
- CSR은 서버가 가볍고 전환이 빠르지만 첫 화면이 늦다. SSR은 첫 화면이 빠르지만 요청마다 서버가 일한다. SSG는 미리 만들어 가장 가볍지만 바뀌면 다시 빌드한다.
- 하이드레이션은 서버가 그린 HTML에 브라우저가 동작을 붙이는 단계다. 보이는 시점과 반응하는 시점이 달라진다.
- 왕복 횟수를 세면 각 방식의 첫 화면 시간을 어림할 수 있다.
