# [WSL 개발 환경 1/10] WSL이란: 윈도우 안의 리눅스, WSL 1과 WSL 2의 구조

> **한 줄 요약** — WSL은 리눅스용 프로그램을 윈도우에서 다시 빌드하지 않고 실행하게 하는 기능으로, WSL 1은 리눅스 시스템 호출을 윈도우 커널이 번역해 처리하고 WSL 2는 관리형 경량 VM 안에서 진짜 리눅스 커널을 돌리며, 이 구조 차이가 파일 속도·호환성·메모리 사용의 장단점을 모두 정한다.

## 이 글에서 다루는 것
- 윈도우 개발자에게 리눅스 환경이 필요한 이유와 기존 대안(VM, 듀얼 부팅, Git Bash)
- WSL 1(시스템 호출 번역)과 WSL 2(경량 유틸리티 VM + 리눅스 커널)의 구조와 장단점
- WSL을 이루는 구성 요소와 연혁
- 리눅스 쪽에서 지금 환경을 확인하는 법: `uname -r`, `/proc/version`, `/etc/os-release`

## 문제: 노트북은 윈도우, 서버는 리눅스
회사 노트북은 윈도우인데 서버와 CI는 리눅스다. 저장소의 `scripts/setup.sh`는 bash로 짜여 있고, 도커 이미지는 리눅스 커널을 전제로 하며, 설치 안내는 `apt install`로 시작한다. 이 간극을 메우던 방법은 저마다 비용이 있었다. 전통적인 가상 머신은 완전한 리눅스지만 메모리를 떼어 주고 파일·네트워크를 따로 맞춰야 한다. 듀얼 부팅은 진짜 리눅스지만 윈도우 도구를 쓰려면 재부팅해야 한다. Git Bash나 Cygwin은 리눅스 명령을 윈도우용으로 다시 빌드한 것이라 리눅스용 실행 파일(ELF)은 돌리지 못한다. **WSL**(Windows Subsystem for Linux)은 리눅스용으로 빌드된 프로그램을 수정 없이, 윈도우 데스크톱·파일과 함께 쓰게 해 준다.

## WSL 1: 윈도우 커널이 리눅스 시스템 호출을 받는다
리눅스 프로그램은 파일을 열 때 `openat` 같은 시스템 호출로 커널에 부탁한다(시스템 호출은 트랜지스터에서 자연어까지 10편 참조). WSL 1에는 리눅스 커널이 없다. 대신 윈도우 커널 드라이버(`lxcore.sys`)가 그 호출을 받아 NT 커널의 동작으로 번역한다. 리눅스 프로세스는 이 드라이버가 관리하는 가벼운 특수 프로세스로 돌고, 파일은 NTFS에 그대로 저장된다. 그래서 VM이 없어 메모리를 프로세스만큼만 쓰고, `/mnt/c`의 윈도우 파일도 빠르게 다룬다. 약점은 번역 자체다. 리눅스 시스템 호출 수백 개를 의미가 다른 NT 커널 위에 다시 구현해야 했고, 컨테이너에 필요한 네임스페이스·cgroups 같은 기능은 끝내 완전하지 않았다. 작은 파일을 많이 만드는 `git clone`·`npm install`도 NTFS와 리눅스 파일 의미의 차이 때문에 느렸다.

## WSL 2: 경량 VM 안의 진짜 리눅스 커널
WSL 2는 번역을 그만두고 진짜 리눅스 커널을 돌린다. 공식 문서의 표현으로 "관리형 경량 유틸리티 VM"이다. 사용자가 만들고 관리하는 Hyper-V 가상 머신이 아니라, 배포판을 열면 WSL이 알아서 켜고 쓰지 않으면 끄는 VM이다. 커널은 마이크로소프트가 kernel.org의 안정 브랜치로 빌드해 업데이트로 배포하고, 배포판들은 이 VM 안에서 서로 격리된 컨테이너처럼 커널 하나를 나눠 쓴다.
```text
[WSL 1]
Linux app
  | syscall
  v
lxcore.sys (translate)
  |
  v
NT kernel --> NTFS

[WSL 2]
+-- utility VM ----------------+
| Linux app                    |
|   | syscall                  |
|   v                          |
| Linux kernel --> ext4 (vhdx) |
+------------+-----------------+
             | 9P (/mnt/c)
             v
Windows NT kernel --> NTFS
```
진짜 커널이므로 시스템 호출 호환성이 완전하고(도커 엔진, systemd, FUSE가 그대로 돈다) 배포판 파일은 가상 디스크(ext4.vhdx) 위의 ext4라 리눅스 쪽 파일 작업이 빠르다. 대가는 경계다. 윈도우 드라이브(`/mnt/c`)는 VM 밖에 있어서 파일 연산 하나하나가 9P 프로토콜 메시지로 경계를 넘는다(3편). VM은 필요한 만큼 메모리를 늘려 쓰고 리눅스 페이지 캐시도 그 안에 잡히므로 작업 관리자에서 메모리를 많이 먹는 것처럼 보일 수 있다(상한 설정은 6편, 회수는 10편). 네트워크도 기본은 NAT 뒤의 VM이다(7편).

| 항목 | WSL 1 | WSL 2 |
|---|---|---|
| 리눅스 커널 | 없음(번역) | 진짜 커널 |
| 시스템 호출 호환성 | 일부 | 전체 |
| 리눅스 쪽 파일 작업 | 느림 | 빠름 |
| `/mnt/c` 파일 작업 | 빠름 | 느림(9P) |
| 메모리 | 프로세스만큼 | VM이 늘려 씀 |
| 도커 엔진 | 안 됨 | 됨 |

두 버전은 배포판마다 고를 수 있고 언제든 바꿀 수 있다(2편). 공식 문서는 WSL 2를 권하면서, 프로젝트 파일을 꼭 윈도우 파일 시스템에 둬야 하는 경우처럼 WSL 1이 나은 예외도 적어 둔다.

## 구성 요소
- `wsl.exe`: 윈도우 쪽 명령. 배포판 설치·전환·백업(2편)과 리눅스 명령 실행(5편)을 맡는다.
- 배포판(distribution): Ubuntu, Debian 같은 리눅스 사용자 공간. WSL 2에서는 배포판마다 ext4.vhdx 가상 디스크를 하나씩 가진다(3편).
- init: 배포판이 시작되면 WSL이 넣어 둔 `/init`이 먼저 떠서 마운트와 상호 운용을 준비한다. systemd는 설정으로 켠다(8편).
- 파일 공유: 윈도우에서는 `\\wsl.localhost\Ubuntu` 경로로 리눅스 파일을, 리눅스에서는 `/mnt/c`로 윈도우 드라이브를 본다(3편).
- 상호 운용: bash에서 `notepad.exe`를, PowerShell에서 `wsl ls`를 부른다(5편). 설정 파일은 배포판의 `/etc/wsl.conf`와 윈도우 사용자 폴더의 `.wslconfig`다(6편).

도커 데스크톱은 WSL의 대안이 아니라 사용자다. 윈도우에서 리눅스 컨테이너를 돌리려면 리눅스 커널이 필요하고, 도커 데스크톱은 그 커널로 WSL 2를 쓸 수 있다(9편).

## 따라 하기: 지금 어떤 리눅스인가
리눅스 쪽에서 커널과 배포판을 확인하는 명령은 어디서나 같다. 이 시리즈의 bash 예제는 WSL이 아닌 Ubuntu 24.04 클라우드 VM에서 실제로 실행한 결과다.
```bash
uname -r
uname -m
cat /proc/version
```
```text
6.18.44-fc-v139
x86_64
Linux version 6.18.44-fc-v139 (…) …
```
`uname -r`은 커널 릴리스, `/proc/version`은 커널이 빌드된 정보다. 배포판 정보는 커널이 아니라 사용자 공간의 파일에 있다.
```bash
. /etc/os-release
echo "$PRETTY_NAME ($VERSION_CODENAME)"
```
```text
Ubuntu 24.04… LTS (noble)
```
WSL 2에서는 커널 문자열에 `microsoft`가 들어간다. 아래는 마이크로소프트 Q&A에 올라온 실제 값이며, 숫자는 커널 업데이트마다 바뀐다. WSL 1은 `4.4.0-17763-Microsoft`처럼 대문자 `Microsoft`로 끝난다.
```sh
uname -r
```
```text
5.10.102.1-microsoft-standard-WSL2
```

## 검증: 스크립트로 WSL 판별하기
개발 환경 스크립트는 종종 "WSL이면 윈도우 쪽 브라우저를 연다" 같은 분기를 둔다. 커널 문자열의 대소문자로 버전을 가르는 판별기를 만들고, 가짜 문자열로 세 경우를 시험해 보자.
```bash
# 파일: wsl-kind.sh
# 사용: bash wsl-kind.sh [커널 정보 파일]
v=$(cat "${1:-/proc/version}")
case "$v" in
  *Microsoft*) echo "WSL 1" ;;
  *microsoft*) echo "WSL 2" ;;
  *) echo "WSL 아님" ;;
esac
```
```bash
echo 'Linux version 5.10.102.1-microsoft-standard-WSL2' > v2.txt
echo 'Linux version 4.4.0-17763-Microsoft' > v1.txt
bash wsl-kind.sh
bash wsl-kind.sh v2.txt
bash wsl-kind.sh v1.txt
echo "WSL_DISTRO_NAME=${WSL_DISTRO_NAME:-(없음)}"
```
```text
WSL 아님
WSL 2
WSL 1
WSL_DISTRO_NAME=(없음)
```
이 환경은 WSL이 아니므로 판별기가 그렇게 답했고, WSL이 배포판 이름을 넣어 주는 환경 변수 `WSL_DISTRO_NAME`도 비어 있다. 판별에 두 신호를 함께 쓰면 더 안전하다.

## 흔한 실수와 문제 해결
- 대소문자를 구분한 판별: 실제로 OpenJDK 빌드 스크립트는 `Microsoft`만 찾다가 WSL 2를 놓쳐 대소문자를 무시하도록 고쳤다. "WSL인가"만 궁금하면 `grep -qi microsoft /proc/version`처럼 쓴다. 커널 문자열은 공식 API가 아니어서 직접 빌드한 커널에서는 없을 수 있다.
- 도커나 `systemctl`이 안 된다: 배포판이 WSL 1로 돌고 있지 않은지 `wsl -l -v`의 VERSION 열부터 본다(2편). WSL 2인데 `systemctl`만 안 되면 systemd 설정 문제다(8편).
- `/mnt/c/Users/…` 아래 프로젝트에서 `npm install`이 유난히 느리다: WSL 2에서 경계를 넘는 파일 접근의 대가다. 프로젝트를 리눅스 쪽 홈으로 옮긴다(3편).
- 윈도우와 리눅스가 같은 파일을 다르게 해석한다: 줄바꿈 CRLF, 실행 비트, 대소문자 문제는 4편.

## 권장 설정과 체크리스트
- 새로 시작하면 WSL 2를 쓴다. `wsl --install`로 설치한 배포판은 기본으로 WSL 2다(2편).
- 코드와 `node_modules`는 리눅스 쪽 `~/` 아래에 둔다.
- WSL과 커널은 `wsl --update`로 갱신한다. 지금은 윈도우 업데이트가 아니라 스토어 패키지로 따로 배포된다.
- 윈도우 파일을 리눅스 도구로 계속 다뤄야 하는 특수한 경우에만 WSL 1을 검토한다.

## 어디에 쓰이나
- 트랜지스터에서 자연어까지 10편 「운영체제: 기계를 나눠 쓰게 하는 층」: WSL 1은 그 글의 시스템 호출 입구를 윈도우 커널이 대신 받아 번역하고, WSL 2는 그 입구를 진짜 리눅스 커널에 맡긴다.
- 언어 기초 6편 「어셈블리와 컴파일·링크: 소스 코드가 실행 파일이 되기까지」: WSL이 실행하는 것은 그 글에서 링크해 만든 리눅스 ELF 파일 그대로라서 다시 빌드할 필요가 없다.
- 도커와 컨테이너 1편 「컨테이너란: 격리된 프로세스, 이미지, 가상 머신과의 차이」: 컨테이너는 호스트 커널을 공유하므로 윈도우에서 리눅스 컨테이너를 돌리려면 WSL 2 같은 리눅스 커널이 먼저 있어야 한다.

## 정리
- WSL은 리눅스 ELF 프로그램을 수정 없이 윈도우에서 실행하고 윈도우 파일·데스크톱과 섞어 쓰게 한다.
- WSL 1은 시스템 호출 번역이라 VM이 없고 윈도우 파일이 빠르지만 호환성이 부족하다. WSL 2는 경량 VM의 진짜 커널이라 호환성과 리눅스 쪽 파일 속도를 얻고 경계 넘는 파일 접근과 메모리를 내준다.
- 커널 문자열의 `microsoft`(WSL 2는 소문자)와 `WSL_DISTRO_NAME`으로 환경을 판별하되, 대소문자를 무시하고 실패해도 동작하게 짠다.
